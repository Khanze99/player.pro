# Техническое задание — «PlayerPro / ИгрокПро» (MVP)

**Тип продукта:** платформа мониторинга состояния спортсменов и управления командой (Athlete Management System).
**Позиционирование:** импортозамещение PlayerPulse.
**Версия:** 1.0 (итоговая, MVP-скоуп).
**Языки интерфейса:** Русский, English, Español.

---

## 1. Обзор и цель

PlayerPro — мобильное приложение с облачным бэкендом для сбора субъективных данных о самочувствии и тренировочной нагрузке спортсменов и превращения их в понятные тренерскому штабу показатели готовности, нагрузки и доступности состава.

Ключевая ценность — **раннее выявление риска перетренированности и травм** через связку «ежедневный опрос самочувствия» + «RPE после нагрузки» → расчёт Readiness Score и Load Ratio (ACWR).

Пользователи: **игрок** (заполняет опросы, видит свои показатели и стрики), **тренер** (дашборд состава, аналитика, планирование, расписание), **врач** (статусы доступности и травмы), **админ** (организация, команды, роли).

Инфраструктура полностью собственная (без внешних управляемых сервисов) — под импортозамещение и хранение медицинских/персональных данных в контролируемом контуре.

## 2. Роли и модель доступа

Роль имеет два уровня: **глобальная** (в организации) и **командная** (в конкретной команде). Пользователь может состоять в нескольких командах с разными командными ролями.

### 2.1. Глобальные роли
| Роль | Права |
|---|---|
| `admin` | Управление организацией, командами, приглашение/деактивация пользователей, назначение ролей. |
| `staff` | Тренер/врач/аналитик — доступ к назначенным командам. |
| `player` | Только собственные данные + командное расписание/сообщения. |

### 2.2. Командные роли
| Роль | Права в команде |
|---|---|
| `head_coach` | Полный доступ к дашборду и аналитике, планирование, назначение тренеров. |
| `coach` | Дашборд и аналитика, ведение расписания/посещаемости. |
| `medic` | Статус доступности, травмы, просмотр wellness. |
| `athlete` | Только свои данные + командные события/сообщения. |

### 2.3. Организации и простой пользователь
- **Организация** — верхний уровень (клуб/академия), содержит команды и пользователей. Все данные изолированы по `organization_id` (мультитенантность).
- **Простой пользователь без организации** — регистрируется, ведёт личный опрос и RPE, смотрит свою статистику. Приглашение в организацию присваивает роль и открывает командный функционал.

### 2.4. Матрица доступа (ключевое)
| Сущность | athlete | coach/head_coach | medic | admin |
|---|---|---|---|---|
| Свой wellness/RPE | CRUD (свой) | R (команда) | R (команда) | R (орг) |
| Чужой wellness/RPE | — | R (команда) | R (команда) | R (орг) |
| Availability/статус | R (свой) | R + W (команда) | CRUD (команда) | R (орг) |
| Дашборд команды | — | R | R (огранич.) | R |
| Расписание | R | CRUD | R | R |
| Управление командой | — | частично | — | CRUD |

**Реализация доступа — в коде бэкенда (authz-слой), без RLS в БД.** Каждый запрос: проверка подписи access-JWT → извлечение `user_id` → проверка роли в организации/команде. Все правила в одном месте, покрыты юнит-тестами.

## 3. Функциональные требования по ролям

### 3.1. Игрок

**Ежедневный опрос самочувствия (Daily Wellness).** Раз в день (утром), push-напоминание, заполнение < 60 сек. Ввод по шкале Ликерта 1–5. Пропущенный день = данные отсутствуют (не ноль). Поля — см. раздел 7.1. Работает офлайн с отложенной синхронизацией.

**RPE после тренировки/события.** Через 15–30 мин после сессии push → игрок вводит:
- **Exertion (RPE)** — насколько тяжело было, шкала CR10 (1–10, Борг);
- **Performance** — самооценка выступления (1–5);
- фактическую длительность (подтягивается из расписания, можно скорректировать).
Расчёт `session_load = RPE × минуты`. Окно ввода — до 24 ч, позже помечается как «поздний».

**Индивидуальные события.** Игрок добавляет собственное событие (личная тренировка, кардио) с типом, длительностью и последующим RPE. Участвует в расчёте личной нагрузки.

**Счётчики и стрики.** Стрик заполнения опроса и RPE (дни подряд); счётчики опросов, сессий, суммарной нагрузки. Лёгкая геймификация (бейджи) — опционально.

### 3.2. Тренер (дашборд и аналитика)

**Экран статуса состава (Squad Status).** Обзор всех игроков на сегодня: Readiness Score (цвет-код), статус нагрузки (зона ACWR), Availability, флаги (заполнен ли опрос, травма/болезнь, отклонение пульса покоя). Сортировка/фильтр по риску.

**Аналитика.** Динамика нагрузки игрока (daily load, EWMA-острая 7 дн, EWMA-хроническая 28 дн, ACWR) — графики; динамика wellness и Readiness; командные агрегаты (средний Readiness, распределение по зонам, кол-во травм). Экспорт — пост-MVP.

**Тренировочная нагрузка и Load Ratio.** ACWR по каждому игроку с цветовой зоной (раздел 6.2–6.3).

**Доступность (Availability).** Как часто игрок был доступен для полноценного участия за предыдущие 90 дней (раздел 6.5): % и разбивка по статусам.

**Readiness Score.** Композитный показатель готовности 0–100 + цвет (раздел 6.4).

### 3.3. Врач
- Установка/изменение статуса доступности (полностью доступен / ограниченно / недоступен).
- Ведение травм (тип, локация, тяжесть, даты, статус).
- Просмотр wellness и пульса покоя команды.
- Расширенная медкарта — пост-MVP.

### 3.4. Админ
- Создание/редактирование организации и команд.
- Приглашение пользователей, назначение глобальных и командных ролей, деактивация.
- Настройки команды: локации/площадки, типы событий, тайм-зона, единицы.

### 3.5. Управление командой и организацией
- Настройка команды, площадок (мест), типов событий.
- Управление ролями тренеров.
- Расписание и посещаемость + push-уведомления о событиях.
- Мессенджер — упрощённый в MVP (объявления/канал команды), полноценный (личные чаты) — пост-MVP.
- Синхронизация календарей (Google/Apple) — пост-MVP.

## 4. Пользовательские сценарии

1. **Игрок, утро:** push «Заполни самочувствие» → 40 сек ввода → видит свой Readiness и стрик.
2. **Игрок, после тренировки:** через 20 мин push «Оцени нагрузку» → RPE + performance → видит session load.
3. **Тренер, перед тренировкой:** Squad Status → видит красных игроков (низкий Readiness, ACWR > 1.5) → корректирует план.
4. **Врач:** отмечает игрока «недоступен» → игрок исчезает из доступного состава, Availability% пересчитывается.
5. **Админ:** создаёт команду, приглашает тренера и игроков, назначает роли.

## 5. Аутентификация

**Принцип:** вход по **4-значному PIN**, но PIN — это локальный код разблокировки на устройстве, а **не пароль**. Сервер про PIN ничего не знает. С нового/неизвестного устройства войти по одному PIN нельзя — требуется повторное подтверждение через OTP (телефон/email). Настоящий серверный «якорь» доверия к устройству — refresh-токен.

### 5.1. Регистрация и первый вход
1. Пользователь вводит **телефон или email**.
2. Бэк создаёт `pending`-пользователя, генерирует **OTP (6 цифр, TTL 5 мин)** (хранится в Redis), отправляет по SMS/email. Лимиты запросов по номеру/email/IP.
3. Пользователь вводит OTP → аккаунт `active`.
4. Бэк выдаёт **access-JWT** (~15 мин) + **refresh-токен** (долгий, отзываемый, привязан к `device_id`). Refresh-токен сохраняется на устройстве в secure-storage.
5. Пользователь задаёт **4-значный PIN** — хранится только на устройстве (хэшом, в secure-storage).

### 5.2. Последующие входы (то же устройство)
1. Приложение просит 4 цифры.
2. PIN проверяется локально → разблокирует сохранённый refresh-токен.
3. Refresh-токен обменивается на новый access-JWT.

### 5.3. Новое / потерянное устройство
На устройстве нет refresh-токена → PIN бесполезен → повторное подтверждение через **OTP** → новый refresh-токен → задаётся новый локальный PIN.

### 5.4. Где что хранится
| Данные | Где |
|---|---|
| PIN (хэш) | Только на устройстве (secure-storage) |
| Refresh-токен (сырой) | На устройстве (secure-storage) |
| Refresh-токен (хэш) | В БД (Postgres), отзываемый |
| OTP-код | В Redis, TTL 5 мин, лимит попыток |

### 5.5. Эндпоинты
| Метод | Путь | Назначение |
|---|---|---|
| POST | `/auth/otp/request` | `{identifier}` → создать/найти юзера, выслать OTP |
| POST | `/auth/otp/verify` | `{identifier, code, device_id}` → активировать, выдать access + refresh |
| POST | `/auth/token/refresh` | `{refresh_token, device_id}` → новый access-JWT |
| POST | `/auth/logout` | `{refresh_token}` → отозвать токен устройства |
| GET | `/auth/me` | защищённый; текущий пользователь |

Один и тот же `otp/request` + `otp/verify` покрывает первичную регистрацию и повторную привязку нового устройства.

## 6. Аналитика и формулы (ядро продукта)

### 6.1. Session Load
```
session_load (AU) = RPE(1–10) × длительность_минут
```
Пример: RPE 6 × 90 мин = 540 AU.
`daily_load` игрока = сумма `session_load` всех событий за день (командные + индивидуальные). День отдыха без событий = 0 AU (важно для EWMA — это ноль, а не пропуск).

### 6.2. EWMA острой и хронической нагрузки
```
λ = 2 / (N + 1)
λ_острая        = 2 / (7 + 1)  = 0.25
λ_хроническая   = 2 / (28 + 1) ≈ 0.0690

EWMA_today = load_today × λ + EWMA_yesterday × (1 − λ)
```
Инициализация: в первый день `EWMA = load` первого дня. Хроническая метрика осмысленна после ~28 дней данных → до этого в UI бейдж «накопление данных».

### 6.3. Load Ratio (ACWR) и статус нагрузки
```
ACWR = EWMA_острая / EWMA_хроническая
```
| ACWR | Зона | Смысл | Цвет |
|---|---|---|---|
| < 0.8 | Детренинг / недогруз | Недостаточная нагрузка | Серый |
| 0.8 – 1.3 | Норма (sweet spot) | Оптимальная зона | Зелёный |
| 1.3 – 1.5 | Перетренированность | Повышенная нагрузка | Жёлтый |
| > 1.5 | Риск травмы | Высокий риск | Красный |

Пороги конфигурируемы на уровне команды. Защита от деления на ноль: при `EWMA_хроническая ≈ 0` — статус «недостаточно данных».

### 6.4. Readiness Score
Композитный показатель 0–100 на основе утреннего опроса. Прозрачная настраиваемая формула (проприетарность — в весах и калибровке, хранящихся на сервере).

**Шаг 1. Нормализация к 0–100** (100 = наилучшее состояние), при шкале 1–5:
```
positive_norm = (значение − 1) / 4 × 100     # сон, энергия, настроение
negative_norm = (5 − значение) / 4 × 100     # мышечная боль, стресс
```
**Шаг 2. Взвешенное среднее** (веса по умолчанию, сумма 1.0; настраиваются):
| Компонент | Вес |
|---|---|
| Качество сна | 0.25 |
| Энергия / усталость | 0.25 |
| Мышечная боль (обратн.) | 0.20 |
| Стресс (обратн.) | 0.15 |
| Настроение | 0.15 |

```
readiness_base = Σ (norm_i × вес_i)
```
**Шаг 3. Модификаторы:**
- Пульс покоя выше личного базового на порог (напр. +7 bpm или +1 SD) → −10..−15 и флаг.
- Заявлена травма/болезнь → жёсткий флаг «недоступен/риск» независимо от балла.

```
readiness = clamp(readiness_base + модификаторы, 0, 100)
```
Цвет-код: ≥ 75 зелёный, 55–74 жёлтый, < 55 красный (настраивается).

### 6.5. Availability (доступность за 90 дней)
Статус дня ставится вручную врачом/тренером (или наследуется от последнего). Статусы: `full`, `modified`, `unavailable`.
```
availability_% = (дней 'full' за 90 дн) / (дней с любым статусом за 90 дн) × 100
```
Показываем разбивку full / modified / unavailable в днях и %.

## 10. Архитектура и стек

Всё на собственной инфраструктуре, без внешних управляемых сервисов.

| Слой | Технология |
|---|---|
| Бэкенд | **FastAPI (Python)** — единственная точка входа; клиент не ходит в БД напрямую |
| БД | **PostgreSQL** (self-hosted / РФ-контур); локальная разработка — PostgreSQL в Docker |
| Кэш/эфемерное | **Redis** — OTP, rate limiting, pub/sub для WebSocket |
| Realtime | **WebSocket на FastAPI**, масштабирование через Redis pub/sub |
| Аналитика | модуль/воркер в FastAPI (numpy/pandas), ночной пересчёт `DailyMetric` (планировщик) |
| Мобилка | **React Native + Expo**; React Query + Zustand; i18next; графики Victory Native; токены/PIN в `expo-secure-store` |

**Поток данных:**
```
[RN/Expo клиент]
   │  REST/JSON + WebSocket, Bearer access-JWT
   ▼
[FastAPI]  ── authz в коде (JWT + роль в орг/команде)
   ├── Auth: OTP (Redis) + refresh-токены (Postgres)
   ├── CRUD: wellness / RPE / события / доступность / расписание
   ├── WebSocket: дашборд + мессенджер (Redis pub/sub)
   └── Аналитика: ночной пересчёт DailyMetric
   ▼
[PostgreSQL]  +  [Redis]
```

## 11. Нефункциональные требования

**Безопасность и приватность.**
- Доступ — через authz-слой в коде (JWT + роль), клиент не имеет прямого доступа к БД. TLS в транзите, шифрование покоя на уровне БД/диска.
- Аутентификация: OTP (6 цифр, TTL 5 мин); 4-значный PIN — локальный код устройства (на сервере нет); refresh-токены отзываемые.
- Анти-абьюз: rate limiting OTP и входа (номер/email/IP), локальная блокировка PIN после N неудач → откат на OTP, ротация/отзыв токенов.
- Разграничение медицинской детали (врач) от тренерской (агрегаты/статусы).
- Аудит-лог изменений статусов доступности/травм.
- Вся инфраструктура self-hosted → хранение в РФ-контуре при необходимости.

**Производительность.** Дашборд команды (до ~40 игроков) < 2 c за счёт предрасчитанной `DailyMetric`. Ночной пересчёт организации — батчем в приемлемое окно.

**Надёжность расчётов.** Идемпотентный пересчёт (перезапуск за любой день без дублей), защита от деления на ноль, обработка пропусков дней.

**Офлайн.** Ежедневный опрос и RPE заполняются офлайн, ставятся в очередь, синхронизируются при появлении сети.

## 12. Границы MVP

**Входит:**
- Роли + организации/команды + приглашения.
- Собственная авторизация (OTP-регистрация по телефону/email → PIN на устройстве → JWT + refresh-токены).
- Игрок: ежедневный опрос, RPE, индивидуальные события, стрики.
- Расчёты: session load, EWMA, ACWR/зоны, Readiness, Availability.
- Тренер: Squad Status, базовая аналитика, Load Ratio.
- Врач: статусы доступности, травмы.
- Расписание + посещаемость + push-напоминания.
- Локализация RU/EN/ES.
- Офлайн-ввод опросов/RPE.

**Phase 2 (после MVP):**
- Полноценный мессенджер (личные чаты) — в MVP только объявления/канал команды.
- Синхронизация календарей Google/Apple.
- Экспорт отчётов (CSV/PDF), расширенная аналитика/тренды.
- Геймификация (бейджи, лидерборды).
- Медкарта с расширенными правами, интеграции с носимыми устройствами.
- Реальный SMS-шлюз (на MVP возможен только email-OTP), Redis-hardening, ротация токенов, Alembic-миграции, биллинг.

## 13. Открытые вопросы

1. **Шкала опроса** — фиксируем 1–5 Ликерт? (заложено 1–5).
2. **Веса и пороги Readiness** — дефолты из 6.4 на старт; финальная калибровка на пилоте.
3. **Формулировки вопросов wellness** — нужны финальные тексты на RU/EN/ES с якорями шкалы.
4. **Availability — кто ставит статус** — врач и/или тренер (по умолчанию оба, врач приоритетнее).
5. **SMS-провайдер для OTP** — или только email на MVP?
6. **RPE performance-шкала** — 1–5 или 1–10?
7. **Пороги пульса покоя** — абсолютный +N bpm или +1 SD.
8. **`device_id`** — формат/генерация на клиенте, стабильность на устройство; лимит числа доверенных устройств.

## 14. Этапы разработки

1. **Спринт 0:** схема БД + собственная авторизация (OTP → PIN на устройстве → JWT + refresh) + authz-слой + онбординг (орг/команда/роли).
2. **Спринт 1:** ежедневный опрос + RPE + индивидуальные события + стрики (клиент + запись в БД, офлайн-очередь).
3. **Спринт 2:** аналитика (session load → EWMA → ACWR → Readiness → Availability) + ночной пересчёт + `DailyMetric`.
4. **Спринт 3:** Squad Status + графики аналитики + цветовые зоны.
5. **Спринт 4:** расписание + посещаемость + пуши + локализация RU/EN/ES.
6. **Спринт 5:** стабилизация, пилот на 1 команде, калибровка весов/порогов.
