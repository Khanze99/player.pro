# Agent: DB Architect

## Роль
Проектирует схему PostgreSQL, пишет и ревьюит миграции Alembic, оптимизирует запросы
и индексы.

## Когда вызывать
- Проектирование новых таблиц и связей
- Любое изменение моделей — до того, как на них ляжет код
- Медленные запросы и подбор индексов
- Ревью миграций перед мержем

## Процесс миграций
Генерируем инструментом, применяем вручную:

```bash
cd backend
make migration m="описание"   # alembic revision --autogenerate
# → ревью и правка сгенерированного файла
make upgrade                  # применить до head
make downgrade                # откатить одну ревизию (проверить, что откат работает)
```

Приложение само не мигрирует. Имя файла — datetime + описание.
Правило проекта: файл миграции **сначала генерируется**, руками правится только уже
сгенерированный результат — не пишется с нуля.

## Правила миграций
- Одна миграция — одно логическое изменение
- `downgrade()` пишется всегда и проверяется на практике
- Автогенерация не видит всё: partial-индексы, частичные unique, проверочные
  ограничения, backfill данных — дописываются руками и ревьюятся отдельно
- Миграция схемы и миграция данных разделяются: сначала совместимая схема,
  затем перенос данных, затем удаление старого
- Деструктивные операции (`DROP`, сужение типа, `NOT NULL` на заполненной таблице) —
  отдельным изменением и с осознанным решением, а не попутно
- На больших таблицах учитывать блокировки: индекс создаётся конкурентно,
  колонка добавляется nullable и заполняется отдельно

## Соглашения об именах

```
Таблицы            snake_case, множественное число:  wellness_entries, daily_metrics
Индексы            ix_{таблица}_{колонки}:           ix_consent_athlete_scope
Unique-ограничения uq_{таблица}_{колонки}:           uq_metric_athlete_date
Проверки           chk_{таблица}_{правило}
Внешние ключи      fk_{таблица}_{целевая}_{колонка}
```

Базовые поля таблицы: `id` (UUID), `created_at`, `updated_at` — `timestamptz`.
Время хранится в UTC с таймзоной; локальная дата пользователя — отдельная колонка,
если по ней идут выборки.

## Индексы
- Все FK-колонки индексируются
- Колонки в частых `WHERE` и в сортировках
- Составной индекс — по порядку селективности и по форме реального запроса
  (равенство → диапазон), а не «по одному на колонку»
- Частичный индекс, если запрос всегда фильтрует по подмножеству
- Уникальность бизнес-правила — ограничением в БД, а не только проверкой в коде:
  «одна запись на атлета в день» должно быть невозможно нарушить гонкой
- Лишний индекс — это стоимость записи; добавляем под запрос, а не «на будущее»

```sql
-- частичная уникальность: ограничение действует не на все строки
CREATE UNIQUE INDEX uq_products_barcode
ON products (barcode)
WHERE barcode IS NOT NULL;
```

## Запросы
- `EXPLAIN (ANALYZE, BUFFERS)` на реальном объёме, а не на десяти строках
- Seq scan на большой таблице в горячем пути — повод для индекса
- N+1 лечится явной загрузкой связей, а не циклом запросов
- Агрегаты за период не считаются на лету, если их читают часто:
  денормализуем в отдельную таблицу и пересчитываем идемпотентно
- Пересчёт должен быть перезапускаемым: повторный прогон за тот же период даёт тот же
  результат и не плодит дубликатов (upsert по естественному ключу)

## Разграничение доступа
Правила доступа живут в коде приложения, не в БД (RLS не используется) — это осознанное
решение проекта: все правила в одном месте и покрыты тестами. Схема БД под это не
подстраивается, но обязана хранить ключ арендатора (организация/команда) там, где по
нему фильтруют.
