# План: веб-админка для тренера/врача (белый клинический стиль)

Статус: **реализовано и вручную проверено на реальных данных** (шаги 1–6 из
декомпозиции; 7–9 — см. примечание внизу). Дата составления: 2026-09-23,
реализация — 2026-09-23.

Дополняет ТЗ: продуктовый веб-клиент в разделе 11 ТЗ и `docs/functionality.md`
(«Экспорт, мессенджер, веб-клиент — пост-MVP») зафиксирован как отложенный, без
детализации. Этот план впервые детализирует именно тот зарезервированный слот —
`web/` (Next.js), про который `CLAUDE.md` говорит только «зарезервировано».
**Не путать** с `docs/plan-web-pwa.md` — там веб-доставка того же мобильного
Expo/RN-приложения как устанавливаемого PWA; там же прямо написано «не строит
зарезервированный `web/`». Этот план — как раз про него.

Текущее состояние — `docs/functionality.md` раздел 6 («Что видит тренерский штаб»):
весь нужный функционал уже есть **на бэкенде и в мобильном клиенте**; здесь — только
второй, веб-фронт поверх того же API.

Решения, принятые в обсуждении 2026-09-23:

- **Next.js в `web/`**, не Django admin и не SQLAdmin. Обоснование: `web/` уже
  зарезервирован архитектурно (`CLAUDE.md`) и разведён технически (Next.js 16 +
  Tailwind 4 уже в `package.json`); бьёт в тот же FastAPI REST API, что и мобилка —
  авторизация и правила доступа (`core/authz.py`) не дублируются и не переизобретаются.
  Django admin потребовал бы либо отдельного сервиса со вторым ORM поверх той же
  Postgres (риск разъезда с Alembic-миграциями), либо ручного проброса через тот же
  API — но тогда это просто более бедный Next.js. SQLAdmin — тот же класс проблемы:
  готовый CRUD-редактор таблиц, а не дашборд; Squad Status и разбивка Readiness —
  **вычисляемые** сервисным слоем данные, а не сырые строки таблиц, кастомную вёрстку
  под них пришлось бы городить поверх чужого рантайма в любом случае.
- **Обнаружено и отклонено:** в `web/src/{app,lib,types}` уже лежит прошлый черновик
  (`login/page.tsx`, `lib/api.ts`, `lib/auth.ts`, `types/index.ts`, компоненты
  `Navbar`/`Card`/`StatusDot`). Он бьёт в **несуществующий контракт** — пароль-логин
  `/api/v1/auth/login`, роли `doctor/coach/masseur/athlete`, сущности
  `MedicalClearance`/`MedicalNote`/`Questionnaire`. В реальном бэкенде — только
  OTP (`/auth/otp/*`), роли `admin/staff/player` + командные `head_coach/coach/medic/
  athlete`, сущности `WellnessEntry`/`RpeEntry`/`DailyMetric`. Код не переиспользуем —
  переписывается заново; забирается только тулчейн (`package.json`, `next.config.ts`,
  `tailwind`/`eslint`-конфиги, `app/layout.tsx` как каркас) и общая идея компонентов
  (`Card`, статус-точка), но не их вёрстка/палитра (там тёмная, нужна белая) и не типы.
- **Auth — Next.js как BFF, httpOnly-cookie**, не клиентское хранение токена (как у
  мобильного веб-PWA, `docs/plan-web-pwa.md`). Там PIN+PBKDF2+AES-GCM понадобились
  именно потому, что токен обязан жить в JS-доступном `localStorage`; на BFF токен
  browser JS вообще не видит — Route Handlers/Server Components держат
  `refresh_token` и служебный `device_id` в `httpOnly; Secure; SameSite=Lax`
  cookie, `access_token` рефрешится на сервере Next.js по мере необходимости.
  Компьютер в ординаторской/кабинете тренера — более вероятная цель XSS/чужого
  доступа к вкладке, чем личный телефон, поэтому для медицинских данных решили
  не экономить на архитектуре. Плата — чуть больше кода (route handlers на
  otp/request, otp/verify, refresh, logout) и отдельный набор тестов на этот слой
  (по аналогии с `vault.web.test.ts` у мобилки).
- **Побочный эффект BFF: CORS не трогаем вообще** — Next.js сервер ходит в FastAPI
  server-to-server, browser JS никогда не обращается к бэкенду напрямую. В отличие
  от `plan-web-pwa.md`, где CORS не нужен из-за same-origin, здесь — из-за того, что
  браузер вообще не участвует в вызовах API.
- **Доступ — coach + medic + admin**, та же аудитория и то же разделение, что уже
  описано в `docs/functionality.md` разделе 6: тренер видит статусы/агрегаты, врач —
  дополнительно медицинскую деталь, admin — всё по организации. Ничего нового в
  `core/authz.py` не добавляется — это уже готовое правило
  (`ensure_can_view_athlete`, тот же, что и у мобильных `/analytics/*`, `/dashboard/*`).
  Игрок (`global_role: player`) в веб-интерфейс не пускается — экран логина сразу
  сообщает, что интерфейс не для него.
- **v1 — только просмотр**, без записи. Никаких новых эндпоинтов не требуется вообще:
  весь функционал v1 уже существует и отдаётся существующим API. Запись (статусы
  доступности, травмы, ручной recalc) — сознательно вне объёма; список того, что можно
  добавить вторым заходом — в «Открытые вопросы», не в декомпозиции.
- **Не берём `GET /wellness/athletes/{id}` напрямую.** В `docs/plan-readiness-breakdown.md`
  (раздел «Риски») уже зафиксирована смежная проблема: этот эндпоинт отдаёт
  `injury_details`/`symptom_details`/`pain_points`/`comment` любому штабу с общей
  командой, не только медику — воспроизводить эту дыру во втором клиенте не нужно.
  Для отчёта по игроку веб берёт только `analytics/*/metrics`,
  `analytics/*/readiness-breakdown(/average)` и `rpe/athletes/{id}` — там мед.
  детали нет структурно (raw wellness-числа без описаний травм/карты боли).
- **Язык интерфейса — только русский в v1.** Аудитория — тренерский штаб российского
  клуба (в отличие от игрок-ориентированной мобилки с ru/en/es под миграцию
  спортсменов). i18next в Next.js не заводим; если понадобится — отдельная
  небольшая задача, ключи можно вынести позже без переписывания компонентов.

## Зачем

Тренеру и врачу пришёл фидбэк, что детальный отчёт по каждому спортсмену — на
телефоне тесно и неудобно листать перед планёркой или на приёме; нужен полноэкранный
вид за рабочим столом. Всё содержимое уже спроектировано и посчитано на бэкенде
(Squad Status, командная сводка, разбивка Readiness по критериям — раздел
`docs/plan-readiness-breakdown.md`), не хватает только второго клиента.

## API

Не применимо — новых эндпоинтов нет, используется существующий контракт (список
выше). Единственное серверное добавление — не в FastAPI, а в Next.js: Route Handlers,
которые проксируют `otp/request` → `otp/verify` → `token/refresh` → `logout` и
проставляют/читают httpOnly-куки.

## Права доступа

- Вся фактическая фильтрация — на бэкенде, без изменений (`ensure_can_view_athlete`,
  командные роли). Веб ничего не решает сам за бэкенд.
- Next.js middleware — только грубый гейт: нет валидной сессии → редирект на `/login`;
  `global_role === "player"` после `/auth/me` → отдельный экран «интерфейс не для
  игроков», сессия не создаётся.
- `httpOnly`-cookie недоступна для чтения из JS вкладки — снижает поверхность атаки
  по сравнению с `localStorage` у мобильного веб-PWA.

## Веб-клиент (структура)

```
web/src/
  middleware.ts                     гейт по наличию сессии-cookie
  app/
    login/page.tsx                  OTP-логин (identifier → code), 2 шага
    api/auth/
      otp/request/route.ts          proxy → POST /auth/otp/request
      otp/verify/route.ts           proxy → POST /auth/otp/verify;
                                     Set-Cookie device_id + refresh_token (httpOnly)
      refresh/route.ts              proxy → POST /auth/token/refresh (по истечении access)
      logout/route.ts               proxy → POST /auth/logout; чистит куки
    (staff)/layout.tsx              серверная проверка сессии+роли, Navbar, выбор команды
    (staff)/teams/[teamId]/page.tsx        Squad Status + командная сводка (одна страница,
                                            как CoachHome + dashboard.tsx в мобилке)
    (staff)/teams/[teamId]/athletes/[athleteId]/page.tsx
                                            отчёт по игроку: нагрузка/тренд/разбивка
                                            Readiness (день/7д/28д) — веб-аналог
                                            mobile/src/app/athlete/[id].tsx
  lib/
    session.ts    server-only: читает httpOnly-куки, рефрешит access при необходимости
    api.ts         server-only fetch-обёртка к FastAPI с access-токеном из session.ts;
                    единая обработка 401 (один retry после рефреша) и 403
  components/
    SquadTable.tsx, TeamSummaryPanel.tsx, ReadinessBreakdownPanel.tsx,
    LoadChart.tsx, ReadinessTrendChart.tsx, StatusDot.tsx, Navbar.tsx …
```

Визуальные компоненты (`ReadinessBreakdownPanel`, `LoadChart`, `ReadinessTrendChart`) —
веб-версии тех же идей, что уже реализованы в мобилке
(`ReadinessBreakdownCard`/`LoadBars`/`ReadinessSparkline`, включая недавние правки
ясности — единицы AU, подписи дат, бар по `normalized`, а не по `deficit`, см. историю
изменений), просто на HTML/SVG вместо React Native. Логика (что откуда берём, как
считаем ширину бара) переносится буквально, вёрстка — под белую палитру. При
реализации графиков — заново пройти навык `dataviz` (форма/цвет/подписи), а не
копировать тёмную палитру мобилки механически.

## Персональные и медицинские данные

- Мед. детализация (карта боли, описания травм) в v1 **не показывается вообще** —
  экран использует только `analytics/*` и `rpe/athletes/{id}`, где её структурно нет
  (см. решение выше про `GET /wellness/athletes/{id}`).
- В аудит-лог ничего нового не пишем — только чтение, действий не производится.
- Не логировать: `refresh_token`, `device_id`, тело OTP-запросов.
- Токен не покидает Next.js-сервер — браузер получает уже готовый HTML/JSON без
  токена внутри.

## Выкатка

- **Фича-флаг не нужен** — отдельный веб-артефакт, собран и выложен или нет
  (тот же принцип, что в `plan-web-pwa.md`).
- **Хостинг — отдельная задача, не блокирует разработку.** По аналогии с
  `infra/nginx/playerpro.conf` можно поднять как путь на существующем
  `app.player-pro.ru` (напр. `/staff/`) или отдельный поддомен — решается ближе к
  деплою, вынесено в открытые вопросы.
- Совместимость с мобилкой и веб-PWA не затрагивается: новый независимый фронт,
  бэкенд не меняется.

## Тесты

- Backend — **не требуется**, контракт не менялся; уже покрыт тестами из
  `plan-readiness-breakdown.md` и раньше.
- Web — новый слой с секретами (auth BFF) нужно тестировать так же серьёзно, как
  `vault.web.test.ts` у мобилки: `lib/session.ts` (рефреш при истёкшем access,
  поведение при невалидном/отсутствующем refresh-cookie), route handlers
  (`Set-Cookie` с `httpOnly`/`Secure`/`SameSite`, очистка кук на logout).
  Фреймворк — то, что подтянется с Next.js (Vitest/Jest); `web/package.json` сейчас
  без тестового раннера, завести с нуля.

## Этапность

1. **Auth BFF** — без него ни один экран не открыть; middleware, route handlers,
   `lib/session.ts`, `/login`.
2. **Squad Status + командная сводка** — самый частый экран, всё на одном API-вызове
   каждый (`squad-status`, `summary`), меньше движущихся частей, чем у отчёта по
   игроку с графиками.
3. **Отчёт по игроку с разбивкой Readiness** — переиспользует уже отлаженную на
   мобилке логику (переносится, не изобретается заново), но графики на вебе с нуля.
4. **Полировка**: пустые состояния, ошибки сети, `security-auditor`, `code-reviewer`.

## Риски

- **Стейл-прототип может ввести в заблуждение**, если его частично оставить —
  явное решение выше: контракт переписывается с нуля, не патчится.
- **Next.js 16 — необычно новая версия** (`web/AGENTS.md`: «Read the relevant guide in
  `node_modules/next/dist/docs/` before writing any code» — API/конвенции могут
  отличаться от типового обучающего материала). На шаге 1 декомпозиции — прочитать
  актуальный App Router / Route Handlers / `cookies()` API из документации в самом
  `node_modules`, а не полагаться на память.
- **Второй auth-стек (BFF) — новая поверхность для багов** сессии, которой нет
  больше нигде в проекте (ни мобилка, ни веб-PWA так не делают). Компенсируется
  отдельным тестовым покрытием (шаг 7) и обязательным `security-auditor` (шаг 8).
- **Хостинг не продуман до конца** (см. открытые вопросы) — не блокирует
  разработку, только первую реальную выкладку.

## Открытые вопросы

- Добавлять ли `GET /dashboard/teams/{id}/injuries` в v1 (готовый эндпоинт, нулевая

- Нужен ли RU-only интерфейс постоянным решением, или на горизонте появятся
  русскоязычные и не-русскоязычные штабы одновременно (i18n тогда стоит закладывать
  раньше, чем «когда понадобится»).
