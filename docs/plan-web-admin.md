# План: веб-админка для тренера/врача (белый клинический стиль)

Статус: **реализовано и вручную проверено на реальных данных** (шаги 1–6 из
декомпозиции; 7–9 — см. примечание внизу). Дата составления: 2026-09-23,
реализация — 2026-09-23.

Дополняет ТЗ: продуктовый веб-клиент в разделе 11 ТЗ и `docs/functionality.md`
(«Экспорт, мессенджер, веб-клиент — пост-MVP») зафиксирован как отложенный, без
детализации. Этот план впервые детализирует именно тот зарезервированный слот —
`web/` (Next.js), про который `CLAUDE.md` говорит только «зарезервировано».
**Не путать** с `docs/plan-web-pwa.md` — там веб-доставка того же мобильного
Expo/RN-приложения как устанавливаемого PWA; там же прямо написано «не строит
зарезервированный `web/`». Этот план — как раз про него.

Текущее состояние — `docs/functionality.md` раздел 6 («Что видит тренерский штаб»):
весь нужный функционал уже есть **на бэкенде и в мобильном клиенте**; здесь — только
второй, веб-фронт поверх того же API.

Решения, принятые в обсуждении 2026-09-23:

- **Next.js в `web/`**, не Django admin и не SQLAdmin. Обоснование: `web/` уже
  зарезервирован архитектурно (`CLAUDE.md`) и разведён технически (Next.js 16 +
  Tailwind 4 уже в `package.json`); бьёт в тот же FastAPI REST API, что и мобилка —
  авторизация и правила доступа (`core/authz.py`) не дублируются и не переизобретаются.
  Django admin потребовал бы либо отдельного сервиса со вторым ORM поверх той же
  Postgres (риск разъезда с Alembic-миграциями), либо ручного проброса через тот же
  API — но тогда это просто более бедный Next.js. SQLAdmin — тот же класс проблемы:
  готовый CRUD-редактор таблиц, а не дашборд; Squad Status и разбивка Readiness —
  **вычисляемые** сервисным слоем данные, а не сырые строки таблиц, кастомную вёрстку
  под них пришлось бы городить поверх чужого рантайма в любом случае.
- **Обнаружено и отклонено:** в `web/src/{app,lib,types}` уже лежит прошлый черновик
  (`login/page.tsx`, `lib/api.ts`, `lib/auth.ts`, `types/index.ts`, компоненты
  `Navbar`/`Card`/`StatusDot`). Он бьёт в **несуществующий контракт** — пароль-логин
  `/api/v1/auth/login`, роли `doctor/coach/masseur/athlete`, сущности
  `MedicalClearance`/`MedicalNote`/`Questionnaire`. В реальном бэкенде — только
  OTP (`/auth/otp/*`), роли `admin/staff/player` + командные `head_coach/coach/medic/
  athlete`, сущности `WellnessEntry`/`RpeEntry`/`DailyMetric`. Код не переиспользуем —
  переписывается заново; забирается только тулчейн (`package.json`, `next.config.ts`,
  `tailwind`/`eslint`-конфиги, `app/layout.tsx` как каркас) и общая идея компонентов
  (`Card`, статус-точка), но не их вёрстка/палитра (там тёмная, нужна белая) и не типы.
- **Auth — Next.js как BFF, httpOnly-cookie**, не клиентское хранение токена (как у
  мобильного веб-PWA, `docs/plan-web-pwa.md`). Там PIN+PBKDF2+AES-GCM понадобились
  именно потому, что токен обязан жить в JS-доступном `localStorage`; на BFF токен
  browser JS вообще не видит — Route Handlers/Server Components держат
  `refresh_token` и служебный `device_id` в `httpOnly; Secure; SameSite=Lax`
  cookie, `access_token` рефрешится на сервере Next.js по мере необходимости.
  Компьютер в ординаторской/кабинете тренера — более вероятная цель XSS/чужого
  доступа к вкладке, чем личный телефон, поэтому для медицинских данных решили
  не экономить на архитектуре. Плата — чуть больше кода (route handlers на
  otp/request, otp/verify, refresh, logout) и отдельный набор тестов на этот слой
  (по аналогии с `vault.web.test.ts` у мобилки).
- **Побочный эффект BFF: CORS не трогаем вообще** — Next.js сервер ходит в FastAPI
  server-to-server, browser JS никогда не обращается к бэкенду напрямую. В отличие
  от `plan-web-pwa.md`, где CORS не нужен из-за same-origin, здесь — из-за того, что
  браузер вообще не участвует в вызовах API.
- **Доступ — coach + medic + admin**, та же аудитория и то же разделение, что уже
  описано в `docs/functionality.md` разделе 6: тренер видит статусы/агрегаты, врач —
  дополнительно медицинскую деталь, admin — всё по организации. Ничего нового в
  `core/authz.py` не добавляется — это уже готовое правило
  (`ensure_can_view_athlete`, тот же, что и у мобильных `/analytics/*`, `/dashboard/*`).
  Игрок (`global_role: player`) в веб-интерфейс не пускается — экран логина сразу
  сообщает, что интерфейс не для него.
- **v1 — только просмотр**, без записи. Никаких новых эндпоинтов не требуется вообще:
  весь функционал v1 уже существует и отдаётся существующим API. Запись (статусы
  доступности, травмы, ручной recalc) — сознательно вне объёма; список того, что можно
  добавить вторым заходом — в «Открытые вопросы», не в декомпозиции.
- **Не берём `GET /wellness/athletes/{id}` напрямую.** В `docs/plan-readiness-breakdown.md`
  (раздел «Риски») уже зафиксирована смежная проблема: этот эндпоинт отдаёт
  `injury_details`/`symptom_details`/`pain_points`/`comment` любому штабу с общей
  командой, не только медику — воспроизводить эту дыру во втором клиенте не нужно.
  Для отчёта по игроку веб берёт только `analytics/*/metrics`,
  `analytics/*/readiness-breakdown(/average)` и `rpe/athletes/{id}` — там мед.
  детали нет структурно (raw wellness-числа без описаний травм/карты боли).
- **Язык интерфейса — только русский в v1.** Аудитория — тренерский штаб российского
  клуба (в отличие от игрок-ориентированной мобилки с ru/en/es под миграцию
  спортсменов). i18next в Next.js не заводим; если понадобится — отдельная
  небольшая задача, ключи можно вынести позже без переписывания компонентов.

## Зачем

Тренеру и врачу пришёл фидбэк, что детальный отчёт по каждому спортсмену — на
телефоне тесно и неудобно листать перед планёркой или на приёме; нужен полноэкранный
вид за рабочим столом. Всё содержимое уже спроектировано и посчитано на бэкенде
(Squad Status, командная сводка, разбивка Readiness по критериям — раздел
`docs/plan-readiness-breakdown.md`), не хватает только второго клиента.

## API

Не применимо — новых эндпоинтов нет, используется существующий контракт (список
выше). Единственное серверное добавление — не в FastAPI, а в Next.js: Route Handlers,
которые проксируют `otp/request` → `otp/verify` → `token/refresh` → `logout` и
проставляют/читают httpOnly-куки.

## Права доступа

- Вся фактическая фильтрация — на бэкенде, без изменений (`ensure_can_view_athlete`,
  командные роли). Веб ничего не решает сам за бэкенд.
- Next.js middleware — только грубый гейт: нет валидной сессии → редирект на `/login`;
  `global_role === "player"` после `/auth/me` → отдельный экран «интерфейс не для
  игроков», сессия не создаётся.
- `httpOnly`-cookie недоступна для чтения из JS вкладки — снижает поверхность атаки
  по сравнению с `localStorage` у мобильного веб-PWA.

## Веб-клиент (структура)

```
web/src/
  middleware.ts                     гейт по наличию сессии-cookie
  app/
    login/page.tsx                  OTP-логин (identifier → code), 2 шага
    api/auth/
      otp/request/route.ts          proxy → POST /auth/otp/request
      otp/verify/route.ts           proxy → POST /auth/otp/verify;
                                     Set-Cookie device_id + refresh_token (httpOnly)
      refresh/route.ts              proxy → POST /auth/token/refresh (по истечении access)
      logout/route.ts               proxy → POST /auth/logout; чистит куки
    (staff)/layout.tsx              серверная проверка сессии+роли, Navbar, выбор команды
    (staff)/teams/[teamId]/page.tsx        Squad Status + командная сводка (одна страница,
                                            как CoachHome + dashboard.tsx в мобилке)
    (staff)/teams/[teamId]/athletes/[athleteId]/page.tsx
                                            отчёт по игроку: нагрузка/тренд/разбивка
                                            Readiness (день/7д/28д) — веб-аналог
                                            mobile/src/app/athlete/[id].tsx
  lib/
    session.ts    server-only: читает httpOnly-куки, рефрешит access при необходимости
    api.ts         server-only fetch-обёртка к FastAPI с access-токеном из session.ts;
                    единая обработка 401 (один retry после рефреша) и 403
  components/
    SquadTable.tsx, TeamSummaryPanel.tsx, ReadinessBreakdownPanel.tsx,
    LoadChart.tsx, ReadinessTrendChart.tsx, StatusDot.tsx, Navbar.tsx …
```

Визуальные компоненты (`ReadinessBreakdownPanel`, `LoadChart`, `ReadinessTrendChart`) —
веб-версии тех же идей, что уже реализованы в мобилке
(`ReadinessBreakdownCard`/`LoadBars`/`ReadinessSparkline`, включая недавние правки
ясности — единицы AU, подписи дат, бар по `normalized`, а не по `deficit`, см. историю
изменений), просто на HTML/SVG вместо React Native. Логика (что откуда берём, как
считаем ширину бара) переносится буквально, вёрстка — под белую палитру. При
реализации графиков — заново пройти навык `dataviz` (форма/цвет/подписи), а не
копировать тёмную палитру мобилки механически.

## Персональные и медицинские данные

- Мед. детализация (карта боли, описания травм) в v1 **не показывается вообще** —
  экран использует только `analytics/*` и `rpe/athletes/{id}`, где её структурно нет
  (см. решение выше про `GET /wellness/athletes/{id}`).
- В аудит-лог ничего нового не пишем — только чтение, действий не производится.
- Не логировать: `refresh_token`, `device_id`, тело OTP-запросов.
- Токен не покидает Next.js-сервер — браузер получает уже готовый HTML/JSON без
  токена внутри.

## Выкатка

- **Фича-флаг не нужен** — отдельный веб-артефакт, собран и выложен или нет
  (тот же принцип, что в `plan-web-pwa.md`).
- **Хостинг — отдельная задача, не блокирует разработку.** По аналогии с
  `infra/nginx/playerpro.conf` можно поднять как путь на существующем
  `app.player-pro.ru` (напр. `/staff/`) или отдельный поддомен — решается ближе к
  деплою, вынесено в открытые вопросы.
- Совместимость с мобилкой и веб-PWA не затрагивается: новый независимый фронт,
  бэкенд не меняется.

## Тесты

- Backend — **не требуется**, контракт не менялся; уже покрыт тестами из
  `plan-readiness-breakdown.md` и раньше.
- Web — новый слой с секретами (auth BFF) нужно тестировать так же серьёзно, как
  `vault.web.test.ts` у мобилки: `lib/session.ts` (рефреш при истёкшем access,
  поведение при невалидном/отсутствующем refresh-cookie), route handlers
  (`Set-Cookie` с `httpOnly`/`Secure`/`SameSite`, очистка кук на logout).
  Фреймворк — то, что подтянется с Next.js (Vitest/Jest); `web/package.json` сейчас
  без тестового раннера, завести с нуля.

## Этапность

1. **Auth BFF** — без него ни один экран не открыть; middleware, route handlers,
   `lib/session.ts`, `/login`.
2. **Squad Status + командная сводка** — самый частый экран, всё на одном API-вызове
   каждый (`squad-status`, `summary`), меньше движущихся частей, чем у отчёта по
   игроку с графиками.
3. **Отчёт по игроку с разбивкой Readiness** — переиспользует уже отлаженную на
   мобилке логику (переносится, не изобретается заново), но графики на вебе с нуля.
4. **Полировка**: пустые состояния, ошибки сети, `security-auditor`, `code-reviewer`.

## Риски

- **Стейл-прототип может ввести в заблуждение**, если его частично оставить —
  явное решение выше: контракт переписывается с нуля, не патчится.
- **Next.js 16 — необычно новая версия** (`web/AGENTS.md`: «Read the relevant guide in
  `node_modules/next/dist/docs/` before writing any code» — API/конвенции могут
  отличаться от типового обучающего материала). На шаге 1 декомпозиции — прочитать
  актуальный App Router / Route Handlers / `cookies()` API из документации в самом
  `node_modules`, а не полагаться на память.
- **Второй auth-стек (BFF) — новая поверхность для багов** сессии, которой нет
  больше нигде в проекте (ни мобилка, ни веб-PWA так не делают). Компенсируется
  отдельным тестовым покрытием (шаг 7) и обязательным `security-auditor` (шаг 8).
- **Хостинг не продуман до конца** (см. открытые вопросы) — не блокирует
  разработку, только первую реальную выкладку.

## Примечание о реализации (2026-09-23)

Шаги 1–6 сделаны в этом заходе: стейл-прототип снесён, белая клиническая палитра
(с проверкой контраста/CVD через `dataviz`-скилл), auth BFF (`proxy.ts`,
`app/api/auth/*`, `lib/session.ts`, `lib/api.ts`), Squad Status + командная сводка
(`(staff)/teams/[teamId]`), отчёт по игроку с разбивкой Readiness (день/7д/28д,

### Зачем и что согласовано запросом

- Каждый командный спортсмен изначально без ограничений, без ручного заполнения
  врачом всего состава. Это продуктовый начальный статус, **не медицинское заключение**.
- Изменение доступно тренеру (`coach`, `head_coach`) и врачу (`medic`) своей команды.
  Игрок себе статус не меняет; глобальная роль admin сама по себе права не даёт.
  Admin с командной ролью тренера/врача действует именно в этой роли.
- При смене статуса обязателен комментарий, включая возврат в `full`.
- Одинаковая логика и история в веб-кабинете и приложении.
- Два поля: обязательный комментарий и необязательный диагноз / медицинское
  пояснение. Тренер тоже читает диагноз; добавляет его врач.
- Ограничения взаимно независимы: тренер не снимает ограничение врача, врач не
  снимает ограничение тренера. Итоговая доступность — более строгий из двух статусов.
- Начало учёта для существующих спортсменов без истории — дата миграции данных.
  Фича-флагов нет. Существующие ручные статусы и история сохраняются.

### UX: где менять статус

**Mobile:** «Команда / состав → спортсмен → Доступность». Блок сразу под именем,
до длинной аналитики. Не отдельная вкладка, не настройки профиля и не FAB игрока.
В строке состава остаётся цветной статус; переход ведёт в ту же карточку.

**Web:** «Команда → спортсмен → Доступность». Блок под шапкой, перед
`MedicalExamsCard`; кнопка «Изменить». В таблице состава — статус и переход в
карточку, без смены одним кликом без комментария.

Предлагаемое содержимое:

```text
Доступность: Недоступен

Врач: С ограничениями · с 19 ноября
Без прыжков и контактной нагрузки
Диагноз: медицинское пояснение врача
Автор · время

Тренер: Недоступен · с 19 ноября
Временно исключён из общей тренировки
Автор · время

Изменить тренерский статус
История изменений
Доступность за 90 дней: 82% · учтено 28 дней
```

Для начального состояния: «Без ограничений · по умолчанию», пояснение
«Ограничения штабом не установлены». Не «Врач допустил» и не «Здоров».
Готовность Readiness и доступность не объединять: это разные показатели.

Форма: три статуса, дата действия (по умолчанию сегодня в часовом поясе организации),
обязательный комментарий, кнопки «Сохранить / Отмена». В mobile — модальная форма
с учётом клавиатуры, в web — раскрывающаяся форма по образцу медосмотров.
Редактируется статус своего направления: «Медицинский» или «Тренерский», а не
общий итог. Для медика дополнительно поле «Медицинское пояснение / диагноз» с
подписью «Видно спортсмену, врачам и тренерам его команды». Тренер читает диагноз,
но не редактирует. У каждой строки — свой автор, дата и комментарий.

Если после снятия своего ограничения другое остаётся, показать результат явно:
«Ваше ограничение снято. Игрок остаётся недоступен: действует ограничение тренера»
(или врача). У сотрудника с обеими разрешёнными ролями выбор направления явный;
одно сохранение меняет только выбранное направление, не оба сразу.

История показывает дату действия, время внесения, автора, статус и разрешённый
комментарий. Два изменения в один день не должны стирать предыдущую причину.
Ошибки: загрузка, повтор запроса, 403 после потери роли, 409 при устаревшей форме,
422 у поля, ошибка сети без потери введённого текста. На время сохранения кнопка
заблокирована; статус не показывается сохранённым до ответа сервера.

### Начальный статус и аналитика — согласованное решение

- Новые спортсмены: начало учёта в дату первого вступления в команду как `athlete`.
- Существующие без действующей истории: начало учёта в дату миграции данных,
  не дата регистрации и не искусственное заполнение предыдущих 90 дней.
  Дата вычисляется в часовом поясе организации и сохраняется; повторный запуск
  миграции её не передвигает.
- Существующие ручные статусы не менять, особенно `modified` / `unavailable`.
  Запланированные будущие записи не удалять; начальный статус до них допустим,
  если на дату миграции нет действующего ручного статуса.
- Перевод внутри организации / вторая команда не сбрасывают статус и начало учёта.
- Личный режим без команды не получает автоматический статус штаба.
- Начальное значение хранить на сервере, не вычислять из текущего membership:
  membership удаляется при переводе, значит его дата неустойчива для истории.
- Формула прежняя: `full_days / known_days * 100`; начальный `full` учитывается
  только начиная с даты начала учёта. На первом дне это 100% за **1 учтённый день**,
  а не доказательство 90 дней здоровья. Отображать число учтённых дней.
- После начала нового учёта по каждому направлению наследуется последнее решение;
  если решения в этом направлении ещё нет, оно равно `full` по умолчанию.
  Итог: `max(медицинский, тренерский)` по порядку
  `full < modified < unavailable`. День `full` только если оба направления `full`.
- Оба направления сводятся одной функцией для summary, состава и истории дней.
  До миграции сохраняется прежняя история; до начала учёта и без ручной истории
  сохраняется `None`, не ложное 100%.
- `DailyMetric`, Readiness и ACWR не менять: Availability сейчас считается отдельно
  при чтении. Celery-пересчёт не нужен; нужны обновление запросов и кэшей клиентов.
- Опрос с травмой/болью остаётся сигналом рядом, не отменяет и не создаёт ручной
  статус. При `full` и тревоге из опроса показывать оба, не скрывать тревогу.

### Данные и миграции

**Не хранить два направления в одной перезаписываемой строке.** Проверки роли
последнего автора недостаточно: новая запись тренера не должна стирать действующее
решение врача, и наоборот.

Существующий `AvailabilityRecord` с unique `(athlete_id, date)` сохраняется как
источник старой истории. После миграции источником истины становятся независимые
действия направлений. Не вести одновременно два конкурирующих writable источника;
старые GET сохраняют формат, но после границы миграции читают вычисленный итог.
Для совместимости id/set_by дневного ответа берутся из определяющего ручного
действия (при равенстве строгости — последнее по времени/id). Системный baseline
не выдаётся за ручную запись; он виден в state/summary, а не как фиктивный set_by.

Новые сущности:

1. Начало учёта (`availability_baselines`): UUID, `athlete_id` (unique, FK),
   `org_id` происхождения (FK), `start_date`, `created_at`, источник
   `enrollment` / `migration`. Для существующих — граница перехода на новую модель,
   для новых — дата вступления. До этой даты действует старая история, если есть.
   Это два начальных `full` без выдуманного автора, а не ежедневные записи.
2. История решений (`availability_changes`): UUID, `athlete_id`, `org_id`,
   `direction` (`medical` / `coaching`), дата действия, статус этого направления,
   `actor_id`, роль автора на момент записи, `comment`, `medical_note`,
   `created_at`, `request_id`; для импорта — nullable `legacy_record_id` (unique)
   и источник `manual` / `legacy`. Append-only: исправление — новое действие.
   Комментарий обязателен для новых действий; у legacy может отсутствовать,
   UI пишет «Причина не указана в старой записи». Диагноз вносит только врач в
   medical-направлении. Снятие тренерского ограничения не стирает медицинскую запись.

Статус направления на дату — последняя запись с effective date не позже этой даты;
для нескольких записей за день побеждает последняя по `created_at, id`.
Полная история внутридневных изменений остаётся доступной. Уникальности
`athlete_id + date` у новой истории нет: два направления и несколько решений за день
допустимы. Итог вычисляется, а не редактируется напрямую. При изменении задним числом
пересчитывается итоговая последовательность на чтении до следующего решения этого
направления; действующее ограничение другого направления остаётся в силе.

Индексы: FK; `(athlete_id, direction, date, created_at, id)` для статуса,
`(athlete_id, created_at, id)` для истории. Unique request_id (с проверкой владельца
и payload при повторе), unique legacy_record_id для идемпотентного импорта.
Пределы: комментарий 1–1000 символов после trim, диагноз до 2000; manual-записи
проверяются Pydantic и CHECK в БД. Не добавлять индексы без соответствующего запроса.

История действия, аудит и уведомление — одна транзакция. Блокировка по спортсмену
и expected_version предотвращают гонки. Повтор request_id не создаёт дублей и
не раскрывает чужое действие. Если собственное ограничение снято, а итог остался
прежним, API возвращает оба статуса; уведомление не утверждает, что игрок допущен.
Существующее уведомление о доступности отправляется при смене итогового статуса,
не при каждом изменении комментария/направления.

**Перенос старых данных:** до миграции остаются прежние значения, без восстановления
вымышленной истории двух направлений. На границе миграции действующий ручной статус
переносится в направление автора; второе направление начинается с `full`.
Будущие старые записи импортируются с исходной датой, не удаляются.
Старые данные содержат set_by, но не историческую командную роль: текущая роль
автора не доказывает роль в момент записи. Preflight должен выявить неоднозначные
случаи (admin без роли, сменивший роль/удалённый автор, несколько ролей). Их
направление явно классифицируется ответственным сотрудником до переноса; миграция
не должна молча назначать категорию или снимать такие ограничения. Неразрешённые
случаи блокируют миграцию, отчёт содержит только технические id, без медтекста.
Старое значение не позволяет восстановить ранее затёртые чужие ограничения;
гарантия независимости действует с перехода на новую модель.

Миграция схемы — autogenerate и ревью; затем отдельная миграция данных, не seed/reset.
Дата начала записывается при первом выполнении по часовому поясу организации.
Preflight и повторный прогон на копии/тестовой БД обязательны. Инициализация новых
athlete-memberships идемпотентна; перевод внутри организации ничего не сбрасывает.
FK и новые таблицы включить в удаление аккаунта. Перевод в другую организацию не
раскрывает прежние комментарии/диагнозы: проверять org происхождения, а не только
текущую общую команду. Перенос медистории между организациями вне этой итерации.

Откат схемы проверяется на отдельной тестовой БД. После появления реальных причин
удаление новых таблиц уничтожит их: при откате релиза сначала выключить новые записи,
сохранить данные и откатить приложение; разрушительный downgrade не запускать
автоматически. Baseline и ограничения не должны теряться при откате клиента.
Выключение записи при аварии — остановка обслуживающих процессов / техническое
обслуживание, а не введение фича-флага.

### API — предварительный контракт

Не менять формат существующих GET (список дней и summary), не добавлять туда диагноз.
Summary можно дополнить `tracked_days` без удаления старых полей. Начальный статус
применяется в серверных вычислениях, а не фиктивной записью с подставным `set_by`.

Новый контракт действий — отдельный от старого дневного PUT:

- `GET /api/v1/availability/athletes/{id}/state`: итоговый статус, состояния
  `medical` и `coaching` (статус, дата действия, источник, комментарий, автор),
  версия состояния, `editable_directions`, summary. Начальное состояние имеет
  автора null. Admin без командной роли не получает тексты комментариев.
  Поле editable_directions вычисляет сервер по всем применимым ролям, не клиент.
- `GET /api/v1/availability/athletes/{id}/changes`: разрешённая история без диагноза;
  `date_from` / `date_to`, по умолчанию 90 дней; `page`, `size` (1–100),
  `{items, total, page, size}`, устойчивый порядок по времени внесения и id.
- `GET /api/v1/availability/athletes/{id}/medical-notes`: отдельный защищённый
  медицинский ответ, те же фильтры и пагинация. Не параметр `include_medical=true`
  общего ответа. Доступен самому спортсмену и тренерам/врачам общей команды
  соответствующей организации, не admin без командной роли. Не включать диагноз
  в командные списки, гейджи и уведомления.
- `POST /api/v1/availability/changes`: `athlete_id`, `direction`, `date`, `status`,
  `comment`, необязательный `medical_note` только для medical-направления врача,
  `expected_version`, `request_id`. Direction сверяется с правами: подмена в JSON
  не даёт врачу изменять coaching, тренеру — medical. 201: созданное действие без
  диагноза и актуальное state с обоими направлениями и итогом. Повтор request_id
  возвращает исходный результат без нового действия, другой payload с тем же id — 409.

Обычные ошибки: 401, 403 (нет права/переход запрещён), 404 (чужой tenant или ресурс
не существует), 409 (устаревшая форма), 422 (пустой комментарий, неверная дата/статус).
Ошибки не содержат исходный текст медицинского поля, включая Pydantic `input`.

**Совместимость записи:** старый `PUT /api/v1/availability` позволяет обойти
обязательную причину. Не оставлять его таким после включения нового правила.
В коде текущих mobile/web его вызовов нет, но это не доказывает отсутствие внешних
клиентов: перед выпуском проверить использование. Старый PUT объявить deprecated;
после согласованного переключения отвечать 410 с кодом `retired`.
Если обнаружатся используемые интеграции, сначала мигрировать их на новый endpoint;
до этого новое правило не считается выпущенным. Нельзя тихо подставлять
«Комментарий не указан» и заявлять, что требование выполнено.

Даты: первая итерация редактирует сегодня и прошедшие дни не раньше baseline
(даты миграции / вступления). Старую историю до перехода на два направления не
редактируем через новую модель. Новые будущие назначения вне объёма; старые будущие
записи сохраняются при переносе. Backend использует календарную дату организации, не UTC
`date.today()`. При историческом исправлении API возвращает актуальное состояние
сегодня; не обещает, что оно обязательно изменилось.

### Права и медицинские данные

| Кто | Статус и комментарий штабу | Смена | Медицинская заметка |
|---|---|---|---|
| Спортсмен о себе | Читает | Нет | Своя: чтение |
| Тренер / главный тренер общей команды | Читает | Только coaching | Читает, не изменяет |
| Врач общей команды | Читает | Только medical | Читает / добавляет в своём направлении |
| Admin без командной роли | Статус/агрегат; без текстов причин | Нет | Нет |
| Другой игрок / чужой штаб / чужая организация | Нет | Нет | Нет |

Согласованное разделение: `comment` — причина и рекомендации по нагрузке;
`medical_note` — диагноз/медицинское основание, **виден и тренеру**.
Подписи у полей прямо называют аудиторию. Только medic вносит диагноз.
Разграничение на сервере, а не только скрытие поля в UI.
Свободный текст сам по себе не гарантирует отсутствие диагноза: подсказка не заменяет
правила работы штаба и обучение. Весь текст причин считать чувствительным.

Проверять согласие на обработку здоровья самого спортсмена, не только CurrentUser
сотрудника. Без действующего согласия не начинать сбор новой медицинской записи;
ответ 403 с нейтральным кодом. Отдельный новый scope `DataConsent` для этой итерации
не предлагается: сначала сверить покрытие действующим health-consent и текстами
политики; до релиза подтвердить юридическую формулировку для диагноза и его чтения
тренером. Это изменение прежнего правила «тренер не видит меддетали»: ТЗ и правила
проекта обновлены. По финальному решению пользователя обновление политики и
текстов согласия из этой итерации убрано, остаётся редакция `2026-11-08`.
Продуктовую договорённость не выдаём за заключение о юридической достаточности.
Уточнение пользователя 20.11.2026: новые редакции не должны мешать всему приложению.
Уже подписанные `terms`/`health_data` принимаются независимо от версии, в том числе
`2026-09-03`; не переподписываем и не выдаём их за новую редакцию. Отсутствие/отзыв
по-прежнему закрывает доступ в рамках первичного гейта и чувствительных операций.
Миграция доступности вообще не проверяет согласия и не изменяет их записи.
Это продуктовая совместимость релиза, а не заключение о юридической достаточности
прежнего текста; юридическое ревью охвата доступа остаётся отдельной задачей.

Аудит: actor, athlete, дата, старый/новый статус, id действия; **без комментария и
диагноза**. Уведомление игроку — существующие статус/дата, без медицинского текста.
Автоматическое начало учёта не создаёт массовую рассылку. Успешное изменение
обновляет state, историю, summary и состав всех затронутых команд (а не только
открытой вкладки). BFF не раскрывает токен, проверяет сессию и same-origin запрос;
чувствительные ответы не кэшируются публично.

### Решения обсуждения 2026-11-19 и открытые вопросы

Все три продуктовых вопроса закрыты:

1. Комментарий и диагноз разделены, тренер тоже видит диагноз. Отклонён вариант
   скрытого от тренера диагноза для этой функции; права записи остаются разными.
2. Запрет снимать чужое ограничение симметричен. Два независимых направления
   сохраняют ответственность обеих сторон; итог выбирается по строгости.
   Отклонены единое перезаписываемое поле и проверка только последнего автора.
3. Начало учёта — миграция данных, без фича-флагов и без вымышленной ретроспективы.
4. Уточнение 20.11.2026: действующие подписанные документы не требуют повторного
   подписания для этого релиза; сохраняем фактические версии и даты. Миграции
   не зависят от согласий. Старый клиент не блокируется только из-за новой редакции.

Таблица итогов (строка — медицинский статус, столбец — тренерский):

| | Без ограничений | С ограничениями | Недоступен |
|---|---|---|---|
| Без ограничений | Без ограничений | С ограничениями | Недоступен |
| С ограничениями | С ограничениями | С ограничениями | Недоступен |
| Недоступен | Недоступен | Недоступен | Недоступен |

Пример: врач выставил modified, тренер unavailable. Врач меняет своё решение
на full — итог всё ещё unavailable. Тренер затем снимает своё ограничение — full.
В обратном порядке тренер сначала снимает своё — итог modified до решения врача.

Рабочее допущение: «своя зона ответственности» означает направление, а не
персональную блокировку на конкретного сотрудника. Другой уполномоченный врач
может заменить решение врача, другой тренер — тренера, с комментарием и аудитом.
Это нужно на случай отпуска/увольнения; отдельные замки по автору не добавляем.
Роль в одной общей команде не даёт автоматически роль другого направления.

Технические проверки до реализации/релиза: классификация legacy-ограничений,
согласия на новый доступ к диагнозу, наличие внешних потребителей старого PUT.
Неопределённые legacy-записи не классифицировать догадкой, согласия не обходить.

### Принятые рабочие допущения и границы

- Один итоговый статус спортсмена, вычисляемый из двух направлений, не отдельные
  статусы для каждой тренировки/команды. Перевод внутри организации сохраняет оба.
- Каждый статус направления действует до следующего решения в этом направлении;
  автоматического возврата в `full` нет. Снятие одного не снимает другое.
- Нет массовой смены всего состава, новых связок с травмами/питанием/медосмотрами,
  календаря реабилитации и загрузки медицинских файлов.
- Не называем `full` доказательством здоровья; не подменяем Readiness.
- История причин сохраняется; общие логи не становятся медицинским архивом.
- Отдельный экран игроку сейчас не проектируем; его существующее уведомление
  сохраняем. API своих данных учитывает права на чтение и удаление.

### Фактическая реализация и проверки, 19.11.2026

Уточнение интерфейса 20.11.2026: в карточках web/mobile убраны дата начала учёта,
сводка за 90 дней, кнопки и списки истории изменений / прошлых диагнозов и пояснений.
Финальный компактный вариант: один цветной итоговый статус, подпись «Ограничение
врача / тренера / обоих» и одна кнопка изменения. Отдельные плашки направлений,
подробные комментарии и диагноз из свёрнутой карточки убраны. Два направления
сохраняются на сервере; форма выбирает своё по роли, при двух ролях показывает
переключатель с отдельными черновиками. Обязательная причина и необязательный
диагноз врача в форме сохранены. При снятии своего ограничения пользователь
видит предупреждение, если чужое останется.
Данные и серверные API истории не удалены; отдельный интерфейс истории отложен.
Проверки компактного UI: web lint/types/build, mobile lint/types и 33 Jest-теста;
браузерный прогон врача/тренера, 9 сочетаний источников ограничения, режима чтения,
двух ролей с сохранением черновиков и конфликтов. Светлая/тёмная темы и узкая
веб-карточка проверены; нативный UI на устройстве не проверялся. Сохранения в
браузерных проверках перехвачены, доступность в БД не менялась.
Описанная ниже пагинация истории относится к API, а не текущей карточке.

- Backend: `availability_baselines` (PK athlete_id, граница перехода, org, version)
  и append-only `availability_changes`. Итог рассчитывает `availability_timeline`,
  одинаково для карточки, истории дней, состава и гейджа. Выборки состава батчевые;
  `DailyMetric` не менялся. День карточки и дашборда — календарный день организации.
- Разрешения: только направление соответствующей командной роли; проверяются
  все общие роли и athlete-membership, а не первая попавшаяся роль. Admin без
  командной роли получает агрегат без причин. Тренер читает диагноз, не пишет.
- Комментарий обязателен, два изменения за день сохраняются. Optimistic version
  и блокировка baseline защищают от потери изменений; advisory lock по request_id
  защищает также от гонки одинакового ключа между разными спортсменами.
  Повтор возвращает то же действие и **актуальный** state, без новой записи.
- История решений и медицинских пояснений пагинируется. `medical-notes` также
  возвращает `current`: действующий диагноз остаётся видимым, даже если внесён
  больше 90 дней назад. Старые даты/неопределённые прошлые дни не выдумываются.
- Аудит содержит направление и старый/новый итог, но не текст причины/диагноза.
  Уведомление без диагноза — только при изменении итоговой доступности. Добавлены
  новые сущности в удаление аккаунта; чужие записи автора сохраняются за надгробием.
- Web: `AvailabilityCard` в карточке спортсмена, BFF с same-origin проверкой
  (учтены Host и X-Forwarded-Proto из nginx), no-store, токен остаётся на сервере.
  Mobile: аналогичная карточка, модальная форма, ru/en/es, обновление запросов
  доступности и всех командных сводок. При 409 форма сохраняет текст и предлагает
  явно обновить текущие статусы перед повторным сохранением.
- По финальному решению пользователя 20.11.2026 обновление политики для этой
  итерации **отменено**: landing/privacy, мобильные тексты и обе версии документов
  возвращены к исходной редакции **2026-11-08**. Добавленные параметр версии
  клиента и проверка с 409 удалены; контракт принятия — прежние `kind` / `granted`.
  Любое ранее подписанное не отозванное согласие принимается независимо от версии,
  включая `2026-09-03` и уже созданные локальные записи `2026-11-19`.
  Их строки, версии и даты не переписываются. Повторное подписание не требуется.
  Первичное согласие и отзыв сохраняются; новая доступность и её миграции не требуют
  отдельного согласия или обновлённой редакции. Миграции не читают и не изменяют

Перед миграцией данных нужен preflight на копии БД. Если есть старое действующее
ограничение или будущая запись, миграция требует подтверждения направления
**по id записи**, а не угадывает историческую роль по текущей. Ошибка перечисляет
технические id и откатывает транзакцию. Для подтверждённых случаев аргумент
Alembic `-x availability_legacy_directions` принимает JSON-объект
`{record_id: "medical" | "coaching"}`. Затем запускается `upgrade head`.
Для БД без таких записей достаточно `make upgrade` из `backend/`.
Не использовать seed/reset и не подставлять произвольные направления ради
успешной миграции. Откат data-миграции отказывается уничтожать manual-записи.
