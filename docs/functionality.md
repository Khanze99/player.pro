# Функциональность PlayerPro: что собираем, что считаем и когда

Документ описывает **реализованное поведение** (по коду, не по ТЗ) на 2026-08-24.
Источник истины по замыслу — `PlayerPro_TZ_final.md`; здесь — как оно работает на самом деле.

---

## 1. Петля данных

Всё держится на двух коротких вводах игрока в день:

```
утро          Daily Wellness  ──┐
                                ├──►  DailyMetric (денормализованные метрики дня)
после занятия RPE-оценка      ──┘         │
                                          ├──► экран игрока: Readiness, нагрузка, стрики
                                          └──► дашборд тренера: Squad Status, сводка команды
```

`DailyMetric` — одна строка на игрока и день (`uq_metric_athlete_date`). Это витрина: ни один
экран не считает формулы на лету, все читают готовые значения. Строка пересчитывается двумя
путями — сразу при сабмите и ночным прогоном (раздел 5).

## 2. Daily Wellness — утренний опрос

`POST /api/v1/wellness` → `wellness_service.create_entry`

| Поле | Тип | Примечание |
|---|---|---|
| `mood`, `energy`, `sleep_quality` | 1–10 | больше = лучше |
| `stress`, `soreness` | 1–10 | больше = хуже |
| `sleep_hours` | 0–24, необяз. | справочно, в Readiness не входит |
| `injury` / `injury_details` | bool / текст | жёсткий флаг недоступности |
| `symptom` / `symptom_details` | bool / текст | болезнь, тот же флаг |
| `resting_hr` | 20–250, необяз. | сравнивается с базовым из профиля |
| `comment` | до 1000 симв. | |
| `pain_points` | до 40 точек, `severity` 1–10 | карта боли |

Правила:

- **Один опрос в день.** Повтор за ту же дату → `409 «Опрос за этот день уже заполнен»`.
  Редактирования нет: запись за день неизменна.
- **Карта боли на Readiness не влияет** — в балл входит только общий `soreness`.
  Точки нужны врачу как детализация, а не как ещё один вес в формуле.
- В ответ сразу приходят `readiness`, зона и текущий стрик — игрок видит результат,
  не дожидаясь ничего.
- Пропущенный день — это **отсутствие данных**, а не ноль: Readiness за него просто нет.
  (В отличие от нагрузки, см. ниже.)

## 3. RPE — оценка после нагрузки

`POST /api/v1/rpe` → `rpe_service.create_entry`

| Поле | Тип | Примечание |
|---|---|---|
| `exertion` | 1–10 | шкала Борга CR10: насколько тяжело |
| `performance` | 1–10 | самооценка выступления |
| `duration_min` | 1–600 | фактическая длительность |
| `event_id` | необяз. | привязка к событию расписания |

Правила:

- **`session_load = exertion × duration_min`** (AU, arbitrary units).
- Оценка привязывается к сессии расписания: **одна запись на событие** (повтор → `409`),
  и **только после его окончания** (раньше → `422`). Список сессий дня с флагами
  `finished` / `rpe_submitted` отдаёт `GET /rpe/sessions?day=…&tz_offset_min=…` —
  день считается локальный для игрока, иначе после полуночи в MSK в «сегодня»
  попадали бы вчерашние тренировки.
- Позже **24 часов** после окончания запись принимается, но помечается `is_late = true`.
- Без событий в дне остаётся свободный ввод без `event_id` — это личный режим
  (игрок без организации) и индивидуальные тренировки.
- За день может быть несколько записей: `daily_load` — их сумма.

## 4. Что из этого считается

Все формулы — чистые функции в `app/core/calculations.py`, покрыты тестами
(`tests/test_calculations.py`).

### 4.1. Нагрузка: daily load → EWMA → ACWR

| Величина | Формула |
|---|---|
| `daily_load` | сумма `session_load` за день; **день без записей = 0 AU, а не пропуск** |
| EWMA острая | λ = 2/(7+1) = **0.25**; `EWMA = load × λ + EWMA_вчера × (1 − λ)`, первый день `= load` |
| EWMA хроническая | λ = 2/(28+1) ≈ **0.069**, та же рекуррента |
| `acwr` | острая / хроническая; `null`, если хроническая ≈ 0 (нет данных) |

Зоны `load_zone`:

| ACWR | Зона | Цвет | Смысл |
|---|---|---|---|
| < 0.8 | `undertraining` | серый | недогруз, форма теряется |
| 0.8 – 1.3 | `optimal` | зелёный | нагрузка в коридоре подготовленности |
| 1.3 – 1.5 | `overreaching` | жёлтый | резкий прирост, зона внимания |
| > 1.5 | `high_risk` | красный | классический предиктор травмы |
| нет данных | `no_data` | — | хроническая ещё не набралась |

Ключевая идея: **ноль за день — это тоже данные**. Именно поэтому нагрузка не может
считаться «по факту записей»: без нулей за пустые дни острая EWMA не падает, и ACWR
показывал бы нагрузку, которой уже нет.

### 4.2. Readiness — готовность 0–100

Нормализация к 0–100: прямая шкала `(v − 1) / 9 × 100`, обратная (боль, стресс)
`(10 − v) / 9 × 100`. Дальше взвешенное среднее:

| Показатель | Вес |
|---|---|
| Качество сна | 0.25 |
| Энергия | 0.25 |
| Боль (обратная) | 0.20 |
| Стресс (обратная) | 0.15 |
| Настроение | 0.15 |

Модификатор: если `resting_hr ≥ базовый + 7 уд/мин` — **−12 баллов** и флаг `hr_flag`
(без базового пульса в профиле модификатор не применяется). Итог обрезается в 0–100.

Зоны: **≥ 75 зелёный**, **55–74 жёлтый**, **< 55 красный**.

Флаг `unavailable_flag` ставится при `injury` или `symptom` — он не зависит от балла:
игрок с высоким Readiness и отметкой травмы всё равно виден тренеру как выпавший.

### 4.3. Прочие показатели

- **`daily_performance`** — среднее `performance` за день (1–10). Зоны: ≥ 7 зелёный,
  5–7 жёлтый, ниже красный.
- **Availability** (`availability_service.summary_90d`) — доля дней `full` от дней с любым
  статусом за **90 дней**. Статус дня наследуется от последней записи не позже этого дня,
  дни до самой первой записи в расчёт не идут. Зоны: ≥ 85 % зелёный, 70–85 % жёлтый, ниже красный.
- **Стрики** (`streaks_service`) — отдельно по wellness и RPE. День подряд → `+1`, разрыв
  больше одного дня → сброс в 1, запись задним числом или повтор стрик не меняют.

### 4.4. Строка DailyMetric

`daily_load`, `daily_performance`, `ewma_acute`, `ewma_chronic`, `acwr`, `load_zone`,
`readiness`, `readiness_zone`, `hr_flag`, `unavailable_flag`.

## 5. Когда это считается

### 5.1. Live-пересчёт при сабмите

И `wellness_service.create_entry`, и `rpe_service.create_entry` вызывают
`analytics_service.recalc_athlete` **в той же транзакции**, что и саму запись, с
`end_date = max(дата записи, сегодня)`. Игрок видит новый Readiness и новую зону нагрузки
сразу, тренерский дашборд — тоже.

Пересчёт всегда идёт **с первого дня данных игрока**, а не только за затронутый день:
EWMA рекуррентна, и запись задним числом меняет весь последующий ряд.

### 5.2. Ночной пересчёт

`app/main.py:_nightly_recalc_loop` — asyncio-задача, поднимается вместе с приложением
(`lifespan`), спит до ближайших **02:00 UTC** (`NIGHTLY_RECALC_HOUR_UTC`, выключается
`NIGHTLY_RECALC_ENABLED=false`) и вызывает `analytics_service.recalc_all`: все игроки,
у кого есть хоть одна запись wellness или RPE, каждый — с первого дня данных по сегодня.

**Зачем он нужен, если есть live-пересчёт:**

1. **Дни, в которые никто ничего не вводил.** Главная причина. Если игрок неделю не
   тренировался и не заполнял опрос, ни одного запроса к API не было — а нагрузка за эти
   дни равна нулю и острая EWMA должна падать. Без ночного прогона ACWR застыл бы на
   значении недельной давности, и тренер видел бы нагрузку, которой давно нет.
2. **Записи задним числом.** «Поздний» RPE или опрос за вчера пересчитывают весь ряд —
   ночной прогон гарантирует, что ряд согласован, даже если live-пересчёт прошёл в момент,
   когда более поздние дни ещё не существовали.
3. **Изменения в профиле.** Базовый пульс покоя участвует в Readiness прошлых дней:
   поменяли базовый — прошлые баллы и `hr_flag` должны поменяться следом.
4. **Страховка.** Если live-пересчёт не отработал (упал запрос, ошибка в транзакции),
   ночью данные приводятся в порядок сами.

**Пересчёт идемпотентен**: строка на пару (игрок, день) уникальна, повторный прогон
обновляет её, а не плодит дубли. Запустить его сколько угодно раз безопасно.

### 5.3. Ручной запуск

`POST /api/v1/analytics/recalc` — только админ организации, отдаёт `202` и число
пересчитанных «игроко-дней». Нужен после правки данных или после простоя стенда.

### 5.4. Ограничения текущей реализации

- Это цикл внутри процесса API, а не планировщик. При нескольких воркерах uvicorn
  пересчёт запустится в каждом — на стенде и в проде воркер один (`docs/deploy.md`).
  Полноценный планировщик — пост-MVP.
- `recalc_all` каждую ночь пересчитывает всю историю каждого игрока целиком.
  На MVP-объёмах это дёшево, но с годами данных станет узким местом — тогда понадобится
  инкрементальный пересчёт от последней изменённой даты.
- Время фиксировано в UTC: 02:00 UTC — это 05:00 MSK.

## 6. Что видит тренерский штаб

`dashboard_service`, доступ — по командной роли (`app/core/authz.py`).

- **Squad Status** (`GET /dashboard/teams/{id}/squad-status`) — строка на каждого игрока команды:
  Readiness и зона, ACWR и зона нагрузки, нагрузка за день и за 7 дней, средний перфоманс за 7 дней,
  статус и процент доступности, флаги `wellness_filled`, `active_injury`, `hr_flag`.
- **Сводка команды** (`/summary`) — агрегаты за окно, посещаемость и RPE по событиям,
  список «у кого что не так» с кодами причин (текст подставляет клиент).
- **Травмы команды** (`/injuries`) — записи о травмах плюс болезни из флага `symptom` в опросе,
  одним списком.
- **Аналитика игрока** — `GET /analytics/athletes/{id}/metrics` за период (по умолчанию 28 дней).

Медицинская детализация (карта боли, описания травм) отделена от тренерской: тренер видит
статусы и агрегаты, подробности — у медика.

## 7. Остальная функциональность

| Блок | Состояние |
|---|---|
| Аутентификация | OTP по телефону/почте → access-JWT (15 мин) + отзываемый refresh на устройство; PIN — локальный код на устройстве, сервер о нём не знает. Регистрация показывается только при первом входе (`is_new_user` в ответе на верификацию) |
| Расписание и посещаемость | События команды и личные, посещаемость, привязка RPE к событию |
| Доступность и травмы | Статусы `full` / `modified` / `unavailable`, ведение травм, аудит-лог изменений |
| Организации, команды, роли | Глобальные роли `admin` / `staff` / `player`, командные `head_coach` / `coach` / `medic` / `athlete` |
| Приглашения | Одноразовая ссылка с ролью и TTL, применяется при первом входе |
| Стрики | wellness и RPE, отдельными счётчиками |
| Дневник питания | Реализован (поиск, штрихкод, «повторить приём», цель по калориям и БЖУ), строго личный — витрин для тренера и врача нет. **Выключен флагом `FEATURE_NUTRITION_ENABLED`** |
| Женское здоровье (цикл) | Реализован, доступ только по явному согласию (`DataConsent`). **Выключен флагом `FEATURE_CYCLE_ENABLED`** |
| Офлайн | Убран: без сети экран сообщает «Нет сети» и ждёт повторного нажатия, ничего не копится локально |
| SMS-канал OTP | Каркас есть, провайдер не подключён — работает только email (Yandex Postbox) |
| Экспорт, мессенджер, веб-клиент | Не реализованы, пост-MVP |
