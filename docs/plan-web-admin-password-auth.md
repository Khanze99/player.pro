# План: вход по паролю в веб-админке (после первого входа по коду)

Статус: **проектирование, код не начат.** Дата составления: 2026-09-23.

Дополняет `PlayerPro_TZ_final.md` и `CLAUDE.md` — оба фиксируют аутентификацию как
**только** OTP + локальный PIN на устройстве («сервер про PIN не знает»). Пароля в
системе не существует вообще: ни поля в модели, ни зависимости для хэширования.
Это решение вводит **второй, отдельный от мобильного, механизм** — пароль — но
**только для веб-кабинета штаба** (`docs/plan-web-admin.md`). Мобильное приложение
не трогается: OTP + PIN там остаются как есть.

Текущее состояние — `docs/plan-web-admin.md` (раздел «Auth»): веб-кабинет уже вёрстан
на OTP-логине через собственный BFF (Next.js Route Handlers, httpOnly-куки,
`device_id`). Этот план **не меняет транспорт сессии** (те же access/refresh-JWT,
те же куки) — меняет только то, *чем* эту сессию получают: паролем вместо кода.

Решения, принятые в обсуждении 2026-09-23:

- **После установки пароля вход по коду для постоянного пользования не
  предлагается** — так решил пользователь явно, специально для веб-админки (в
  мобильном OTP как был, так и остаётся). Экран логина по умолчанию показывает
  email + пароль.
- **Но OTP на бэкенде не отключается совсем** — иначе забытый пароль чинить
  нечем, а строить отдельную email-ссылку-восстановление (токен, страница,
  TTL) — это заново изобретать то, что OTP уже даёт. Решение: на экране логина
  остаётся неприметная ссылка **«Забыли пароль? Войти по коду»** — она не
  позиционируется как равноценная альтернатива паролю (это противоречило бы
  прямому решению пользователя), а именно как путь восстановления. Технически
  это тот же `/auth/otp/verify`, что и раньше.
- **Задать пароль после первого входа по коду — один раз, необязательно**
  (второе решение пользователя). После **любого** успешного входа по коду
  (первый вход ИЛИ восстановление после «забыл пароль» — с бэкенда это
  неотличимо, и не должно быть отличимо, см. ниже) показывается один
  дисмиссable экран/баннер «Задать пароль» с полем нового пароля. Пропустить
  можно; повторно не навязываем — только постоянный пункт «Задать/сменить
  пароль» в шапке кабинета.
- **Set-password вместо смены пароля через старый.** Экран после OTP-входа не
  спрашивает старый пароль (его специально для этого и не спрашивают — часто
  пользователь тут именно потому, что забыл пароль) — он просто перезаписывает
  `password_hash`. Это тот же самый экран и тот же эндпоинт что для «первого
  раза», что и для «забыл» — разделять их пользователю незачем, оба сценария
  заканчиваются одинаково: «вот ваш новый пароль». Отдельная **смена** пароля
  из настроек (когда текущий пароль помнишь) — другой эндпоинт, требует
  старый пароль.
- **Set-password ограничен коротким окном после OTP, не любым валидным
  access-токеном.** Без этого ограничения угнанный (хоть и живущий всего
  15 мин) access-токен любого происхождения мог бы тихо перезаписать пароль
  без знания старого — расширение поверхности угона токена на постоянный
  захват аккаунта. Механика: `verify_otp` кладёт в Redis одноразовый флаг
  `password-set-allowed:{user_id}` с TTL 5 мин; `POST /auth/password/set`
  требует этот флаг и гасит его при использовании. Дёшево (переиспользует
  Redis, тот же TTL-паттерн что у OTP-челленджа), закрывает основной риск.
- **Хэширование — bcrypt**, новая зависимость (`bcrypt` в `requirements.txt`).
  Не PBKDF2-через-stdlib (как в `plan-web-pwa.md` для PIN на клиенте) и не
  argon2: bcrypt — стандартный выбор для серверного хранения паролей, простой
  API (`hashpw`/`checkpw`), не требует ручного управления солью/итерациями в
  коде сервиса.
- **Требования к паролю — длина, не сложность.** Минимум 10 символов, без
  принудительных классов символов (заглавная/цифра/спецсимвол) — современная
  рекомендация (NIST 800-63B) в пользу длины вместо правил сложности, которые
  раздражают и не помогают. Проверка на «частые пароли» — не в этом плане, см.
  «Открытые вопросы».
- **Rate limiting входа по паролю — обязателен, отдельно от OTP.** В отличие
  от OTP (код разовый, живёт 5 мин), статичный пароль можно перебирать сколько
  угодно раз без сети — лимит попыток по идентификатору обязателен
  (`core/authz`/`CLAUDE.md`, раздел «Безопасность»: «лимит попыток ввода
  кода» — тот же принцип, применённый к паролю). Механика — тот же паттерн
  Redis/memory-стора, что у `core/otp.py` (`OtpStore`), но отдельные ключи и
  конфиг: не делим счётчик с запросами OTP-кода, иначе они мешают друг другу.
- **Не фича-флаг.** Затрагивает только веб-кабинет (новый, изолированный
  клиент); мобильное приложение не видит новых полей и не может их вызвать
  осмысленно. Ничего не нужно выключать для существующих пользователей — поле
  `password_hash` пустое по умолчанию, весь старый OTP-флоу работает как раньше.

## Зачем

Тренер/врач заходит в веб-кабинет чаще одного раза и не хочет каждый раз ждать
письмо с кодом — пароль быстрее для повторных заходов. OTP делает вход
безопасным при первом разе и остаётся единственным путём восстановления,
не дублируя инфраструктуру.

## Что уже есть

| Есть | Где | Что даёт |
|---|---|---|
| OTP-логин, access+refresh JWT, `RefreshToken` с хэшем в БД | `app/services/auth_service.py`, `app/core/security.py` | Вся инфраструктура выдачи/ротации токенов — переиспользуется, не переизобретается |
| `OtpStore` (Redis/memory) — TTL-челлендж + rate limit + лимит попыток | `app/core/otp.py` | Образец для рейт-лимита попыток пароля — тот же паттерн, отдельные ключи |
| Веб-BFF (httpOnly-куки, `device_id`, `proxy.ts`) | `web/src/{proxy.ts,lib/*,app/api/auth/*}` | Транспорт сессии не меняется — пароль лишь ещё один способ её получить |
| `MeOut` уже отдаёт `terms_accepted`/`health_consent_accepted` | `app/schemas/auth.py` | Тот же паттерн для нового `has_password: bool` |
| `require_consented` не применяется к `/auth/*` | `app/api/v1/router.py` | Новые пароль-эндпоинты естественно встают в тот же освобождённый от гейта роутер |

**Пароля, хэширования, rate-limit попыток входа — нет нигде.** Это первая
реализация в проекте.

## Данные и миграции

- `User.password_hash: str | None` (nullable, `String(255)` — под bcrypt-хэш,
  60 символов, с запасом). Аддитивная миграция, тривиальный откат (`DROP
  COLUMN`). `make migration m="add password_hash to users"` → ревью → `make
  upgrade`.
- Индекс не нужен — поле не участвует в поиске (ищем по email/phone, как и
  сейчас).

## API

Новые эндпоинты в `app/api/v1/auth.py` (тот же роутер, без `require_consented`,
как и текущие `/auth/otp/*`):

- **`POST /auth/password/login`** — `{identifier, password, device_id}` →
  `TokenPairOut` (тот же контракт, что у `otp/verify`, `is_new_user` всегда
  `false`). `401` с одинаковым нейтральным текстом и на «нет такого
  пользователя», и на «неверный пароль», и на «пароль не задан» — не палим,
  какая часть неверна. `429` при превышении лимита попыток.
- **`POST /auth/password/set`** — `{identifier, new_password}`, **без Bearer**
  (проверяется одноразовый Redis-флаг `password-set-allowed:{user_id}`,
  выставленный свежим `verify_otp`) → `TokenPairOut` (сразу логинит новым
  паролем, отдельно логиниться после не нужно). `403`, если флаг истёк/не
  выставлен — «сессия для установки пароля истекла, войдите по коду ещё раз».
- **`POST /auth/password/change`** — `{old_password, new_password}`, Bearer
  (`CurrentUser`) → `204`. Для смены известного пароля из настроек. `400` при
  неверном `old_password`, `400` если пароль ещё не задан (тогда это `set`,
  не `change`).
- **`GET /auth/me`** — добавить `has_password: bool` в `MeOut`
  (`user.password_hash is not None`) — веб-клиенту нужно решить, что показать
  по умолчанию на логине, и метить пункт в профиле «задать»/«сменить».

Рефактор `auth_service.py`: общий кусок «выдать пару токенов на device_id»
(ревокация старого `RefreshToken` того же устройства → новый refresh → access)
сейчас живёт только внутри `verify_otp`; выносится в `_issue_token_pair(db,
user, device_id)`, используется и `verify_otp`, и `login_with_password`, и
`set_password` — не дублировать логику ревокации/ротации токенов.

## Права доступа

- Без изменений в `core/authz.py` — как и раньше, кто есть кто решает
  `global_role`/`TeamRole` после выдачи токена, способ получения токена
  (код/пароль) на это не влияет.
- `password/set` — единственный эндпоинт с нестандартной моделью доступа
  (не Bearer, а одноразовый Redis-флаг) — обосновано выше, ограничено по
  времени (5 мин) и по количеству использований (одноразовое).

## Мобильный клиент

**Не применимо.** Экраны/API мобилки не меняются, пароль там не появляется и
не запрашивается — `password_hash` в `MeOut` мобильный клиент просто не
использует (поле есть, экран его не читает).

## Персональные и медицинские данные

- Пароль никогда не логируется, не возвращается в ответах API (только пишем,
  никогда не читаем обратно raw).
- В аудит-лог (`audit_service`) стоит писать факт смены/установки пароля
  (кто, когда) — не сам пароль. Решение зафиксировано, реализация — в
  декомпозиции.

## Тесты

- `password_hash` не задан → `password/login` даёт нейтральный `401`, не
  раскрывая, что пароля нет.
- Верный/неверный пароль; счётчик неудачных попыток → `429`; сброс счётчика
  после успешного входа.
- `password/set` без флага (не было свежего OTP) → `403`; с флагом — успех,
  флаг одноразовый (повторный вызов тем же флагом уже не проходит).
- `password/change` с неверным `old_password` → `400`; с верным — пароль
  реально меняется (следующий логин старым паролем уже не пускает).
- `has_password` в `/auth/me` отражает реальное состояние до/после
  set/change.
- Рефактор `_issue_token_pair` не ломает существующие OTP-тесты
  (`test_authz.py`, `test_analytics.py` и т.д. — там `register_user` дергает
  OTP-флоу, должен продолжать работать как раньше).
- Миграция: `make upgrade` и `make downgrade` проходят.

## Этапность

Один заход, без промежуточных релизов — фича замкнутая и небольшая по
объёму (одно поле, три эндпоинта, переверстка одной страницы).

## Риски

- **Set-password без старого пароля — сознательно.** Смягчено коротким
  Redis-окном после свежего OTP (5 мин, одноразовое), а не проверкой возраста
  access-токена — угнанный, но уже немолодой access-токен (даже в рамках
  своих честных 15 минут) не даст переписать пароль без нового похода через
  OTP. Остаточный риск — угон токена **в первые секунды** после легитимного
  OTP-входа; тот же порядок риска, что и у самого OTP-письма, не увеличивает
  поверхность атаки существенно.
- **Пароль в системе, где раньше его не было вообще** — новый класс данных
  (пусть только хэш), новый класс атаки (подбор пароля офлайн при утечке БД).
  bcrypt с дефолтным cost factor — стандартная защита, `security-auditor`
  проверяет обязательно (шаг 7).
- **Разделение «забыл пароль» и «просто ещё не задавал»** на бэкенде
  специально неразличимо — оба ведут в один и тот же `password/set`. Если
  захочется различать тексты на экране («Восстановление» vs «Первая
  настройка») — это чисто клиентская формулировка по `has_password` в
  `/auth/me`, бэкенд трогать не нужно.

## Открытые вопросы

- Проверка нового пароля по списку «частых/утёкших» паролей (напр.
  Have I Been Pwned k-anonymity API) — не в объёме этого плана, длины
  (10 симв.) для MVP достаточно.
- Точные числа rate-limit попыток входа паролем (сколько попыток / за какое
  окно / на сколько блокировка) — взять по аналогии с `otp_max_attempts`/
  `otp_requests_per_hour`, финализировать на шаге 3 реализации, не блокирует
  проектирование.
- Показывать ли в профиле дату последней смены пароля — не запрошено, можно
  добавить позже без изменения схемы (есть `updated_at`? уточнить при
  реализации, у `User` сейчас только `created_at`).
