# План: наполнение справочника продуктов

Статус: **этапы 1–4 сделаны (2026-08-31), импорт готов к проду.** Дата составления: 2026-08-29.

Решения по открытым вопросам: грузим только Россию; строки без штрихкода пропускаем.

Дневник питания работает, но справочник маленький: 162 позиции. Ниже — что можно
залить, чего это будет стоить и какие ловушки ждут по дороге. Реализация
`import_foods.py` частично уже есть, но в текущем виде запускать её нельзя (см. «Дубли»).

---

# 1. Текущее состояние

| Что | Сейчас |
|---|---|
| Позиций в каталоге | 162, все `source=curated`, `barcode` пустой |
| Категории | у всех `other` — ни `CURATED`, ни импорт их не проставляют *(закрыто этапом 3)* |
| Импорт Open Food Facts | код есть (`import_off`), **ни разу не запускался** *(закрыто этапом 5)* |
| Пользовательские продукты | 2 шт., `source=custom`, видны только автору |

Модель — `app/models/nutrition.py`: `FoodItem` с `barcode`, `source`
(`curated` / `open_food_facts` / `custom`), `created_by` (NULL у общего справочника),
`verified`. Съеденное (`FoodLogEntry`) хранит **снимок** нутриентов на момент записи,
поэтому изменение справочника задним числом историю питания не ломает — это важно,
оно развязывает нам руки при перезаливке.

# 2. Что даёт Open Food Facts

- **35 570 продуктов** в российском разделе (на 2026-08-29).
- Дамп CSV: `https://static.openfoodfacts.org/data/en.openfoodfacts.org.products.csv.gz`,
  **0.9 ГБ** в gzip, ~9 ГБ распакованным. Всего в базе ~4 млн товаров по 150 странам.
- Импорт уже умеет читать его потоково и фильтровать по `countries_en`.

Реально доедет меньше 35 тысяч: фильтр отбрасывает строки без `energy-kcal_100g`, а в
OFF таких много — это краудсорс, часть карточек заполнена только фото и штрихкодом.
Ожидаемый порядок — 15–25 тысяч, точную цифру покажет первый прогон.

**Лицензия — ODbL** (сама база), DbCL (содержимое), CC-BY-SA (фото). Атрибуция
обязательна: упоминание Open Food Facts должно появиться в приложении. ODbL — copyleft:
при публичном распространении производной базы её положено открывать под той же
лицензией. С платной подпиской из `plan-billing-and-modes.md` это стоит решить
осознанно, а не по умолчанию.

# 3. Дубли: три разных источника

Главная причина, по которой импорт нельзя запускать как есть.

**3.1. Повторный запуск.** `import_off` считает уже импортированные записи и печатает
число, но по строкам ничего не проверяет — просто `db.add()`. Второй прогон дампа
удвоит каталог, третий утроит.

**3.2. Дубли внутри самого дампа.** Один штрихкод может встретиться в файле дважды.
Если сделать «в лоб» upsert батчем, PostgreSQL ответит
`ON CONFLICT DO UPDATE command cannot affect row a second time` — дедупликация нужна
ещё и **внутри батча**, до отправки в БД.

**3.3. Записи без штрихкода.** Часть строк OFF приходит с пустым `code`. По штрихкоду
их не развести. Варианты: пропускать (проще, и такие записи в сканере всё равно
бесполезны) либо дедуплицировать по паре «название + бренд».

# 4. Решение

**Уникальный индекс — частичный, и это принципиально.**

Нельзя вешать `UNIQUE (barcode)` на всю таблицу. Пользователь может завести свой
продукт с тем же штрихкодом (`source=custom`), и тогда глобальный индекс либо
заблокирует импорт OFF-записи, либо upsert затрёт чужой продукт. Ограничение должно
покрывать только импортированный слой:

```
UNIQUE (barcode) WHERE source = 'open_food_facts' AND barcode IS NOT NULL
```

Миграция — **только через `make migration m="…"`** с последующим ревью файла, руками
ревизию не писать.

**Upsert.** `sqlalchemy.dialects.postgresql.insert(...).on_conflict_do_update(...)`.
Обновлять при конфликте: название, бренд, нутриенты, размер порции. **Не трогать**
`created_by`, `verified`, `custom_kind` — иначе перезаливка сбросит ручную разметку.

**Дедуп внутри батча.** Складывать строки в `dict[barcode]` и отправлять `.values()`;
последняя запись в дампе выигрывает.

**Лимит.** Сейчас `--limit 50000` по умолчанию. Сделать `0` = без ограничения,
иначе «максимум» упрётся в неявный потолок.

# 5. Чего это будет стоить

**По России** (~25 тыс. записей) — операция дешёвая: минуты на парсинг, база
подрастёт на несколько десятков мегабайт.

**Без фильтра по стране** (~4 млн) — другая история. Разбор 9 ГБ CSV, батчи по 500
дадут ~8 тысяч коммитов; понадобится батч побольше и, возможно, `COPY`. Но главное не
это, а следующий пункт.

**Поиск не выдержит.** Сейчас `ix_food_items_name` — обычный B-tree, а поиск по
названию неизбежно `LIKE '%…%'`, который таким индексом не пользуется. На 25 тысячах
seq scan незаметен, на 4 миллионах — нет. Понадобится `pg_trgm` + GIN.

# 6. Риск, который перевешивает всё остальное

**Больше записей ≠ лучше дневник.** OFF — краудсорс. Там сорок вариантов «Coca-Cola»
с разным написанием, названия вида `Молоко 3,2% 900мл (шт)`, пустые бренды,
продублированные позиции от разных участников. Игрок вводит «овсянка» и получает
двести брендовых упаковок вместо одной строки «Овсянка на воде».

Отсюда два обязательных условия, без которых заливку делать не стоит:

1. **Ранжирование выдачи**: `curated` выше `open_food_facts`, `verified` выше
   остального, совпадение с начала строки выше совпадения в середине.
2. **Категории**. У OFF есть `categories_tags` — их надо маппить на `FoodCategory`
   (13 значений в `app/models/enums.py`). Сейчас всё лежит в `other`, поле уже торчит
   в `src/api/types.ts`, и фильтр в UI покажет одну кучу.

# 7. Два слоя каталога

OFF закрывает только половину задачи — **упакованные товары со штрихкодом**. Основная
масса записей в дневнике спортсмена — базовые продукты и блюда: «гречка варёная»,
«куриная грудка», «борщ». У них нет штрихкода, и в OFF они либо отсутствуют, либо
лежат мусорными дублями.

| Слой | Чем закрывается | Состояние |
|---|---|---|
| Базовые продукты и блюда | ручной `CURATED` | 162 позиции, мало |
| Упакованные товары | Open Food Facts | 1 663 позиции (весь вклад OFF по России) |

Источники для первого слоя: таблицы Скурихина и Тутельяна (канон для России, но это
книга 2007 года под авторским правом — переносить значения по одному можно, тянуть
оцифрованный дамп нельзя), [база ФИЦ питания](http://web.ion.ru/food/FD_tree_grid.aspx),
[USDA FoodData Central](https://fdc.nal.usda.gov/) (public domain, качество выше всех,
но продукты американские и названия английские).

Субъективно: расширение первого слоя со 162 до 400–600 позиций даст пользователю
больше, чем заливка 25 тысяч штрихкодов, и юридически чище.

# Результат прогона (2026-08-31)

Дамп от 2026-08-31, 1.27 ГБ в gzip (не 0.9), 4 535 554 строки. Прогон по России —
**1 минута 49 секунд**, таблица `food_items` выросла до 1.1 МБ.

## Доехало на порядок меньше, чем ожидалось

Оценка в разделе 2 («15–25 тысяч») **не подтвердилась**. Воронка по дампу:

| Шаг | Строк |
|---|---|
| `countries_en` содержит russia | 34 422 |
| из них со штрихкодом | 34 422 |
| + с названием | 30 595 |
| + с непустым `energy-kcal_100g` | 1 652 |
| + ккал в диапазоне 0–900 | 1 639 |
| + кириллица там, где страна не проставлена (**импортировано**) | **1 663** |

Дело не в фильтрах импорта: **у 95% российских карточек OFF просто нет нутриентов**.
Дотянуть их из килоджоулей нельзя — `energy-kj_100g` заполнен у 1 605 записей, почти
у тех же самых, и добавил бы всего **6** строк. Российский раздел OFF — это в основном
карточки с фото и штрихкодом.

Импорт идемпотентен на боевом дампе: прогоны подряд дают одно и то же число.

## Кириллица — не признак российского товара

Проверялась гипотеза, что `countries_en` заполнен плохо и русскоязычные товары
теряются. **Она не подтвердилась.** Отбор «любая кириллица в названии» даёт 6 816
записей вместо 1 639, но прирост — чужой ассортимент:

| Страна у кириллических записей без пометки russia | Строк |
|---|---|
| Болгария | 1 175 |
| Украина | 618 |
| Германия | 443 |
| Ирландия | 337 |
| Франция | 310 |

Верхние дубли в таком каталоге — `кисело краве мляко 3.6%` (16 карточек) и
`краве кисело мляко 3.6%` (10). Тег страны в OFF как раз заполняют: пустой
`countries_en` всего у **24** годных записей. Поэтому `--cyrillic` оставлен только
как доводка этих 24 — там, где страна не проставлена, — и не перебивает чужой тег.

Отдельно: 916 записей с русскими буквами `ы`/`э` помечены чужой страной. Это
российские товары в зарубежных магазинах; на полке в России их не отсканируешь,
в отбор не берём.

## Что это меняет

- **`pg_trgm` не нужен.** Полторы тысячи строк — seq scan незаметен.
- **Риск «заливка утопит поиск» снят.** Проверено на «овсянка», «творог», «банан»,
  «молоко»: выверенные позиции идут первыми во всех четырёх, импорт — под ними.
- **Вывод раздела 7 усиливается.** OFF даёт 1 663 упакованных товара, и это весь его
  вклад. Расширение `CURATED` до 400–600 позиций теперь не «субъективно полезнее»,
  а единственный способ заметно улучшить дневник.

## Что вылезло на реальных данных

- **Названия HTML-экранированы**: `Творог &quot;Мягкий&quot;`. Игрок увидел бы сущности
  в дневнике — распаковываем через `html.unescape` (тест `test_parse_row_unescapes_html_entities`).
- **У 761 из 1 639 записей `categories_tags` пуст** — эти неизбежно лежат в `other`.
  Из 878 размеченных маппинг не покрывает 93: это соусы и снеки, которым `other`
  и положен (отдельной категории под них в `FoodCategory` нет).
- **Часть карточек размечена русскими тегами** (`ru:мясной-продукт`, `ru:сыр`) —
  в `OFF_CATEGORY_RULES` добавлены русские подстроки.
- **Кавычки в дампе.** Это сырой TSV, кавычка в нём — часть значения. Поле,
  начинающееся с `"`, при разборе по умолчанию тянется через перевод строки и съедает
  записи ниже. На российской выборке таких не нашлось, но в дампе они есть: читаем
  с `csv.QUOTE_NONE`, регрессия закрыта тестом.

## Открытые вопросы — ответы

1. **Только Россия.** Без фильтра — 4 млн записей ради того же качества выдачи.
2. **Строки без штрихкода пропускаем** (3 827 российских записей без названия и все
   без `code`): в сканере бесполезны, развести по дублям нечем.
3. **Реимпорт безопасен** после этапов 1–2 — upsert обновляет карточки и не трогает
   `verified` / `created_by` / `custom_kind`. Прогон стоит две минуты; кто запускает —
   вопрос открыт.
4. Расширение `CURATED` — открыт.

# Риски

- **Заливка без ранжирования ухудшает поиск.** Самый вероятный сценарий провала:
  залили 25 тысяч, поиск по «молоко» стал бесполезен, откатывать поздно.
- **Глобальный `UNIQUE (barcode)` вместо частичного** сломает пользовательские
  продукты и заблокирует часть импорта. Ловушка неочевидная, ошибиться легко.
- **ODbL и платная подписка.** Не блокер, но решение нужно принять до релиза
  монетизации, а не после.
- **Качество нутриентов в OFF никто не гарантирует.** Для дневника спортсмена, где
  по этим числам считается энергетический баланс, ошибка в карточке — это ошибка в
  рекомендации. Отсюда флаг `verified` и приоритет `curated`.

# Открытые вопросы

1. Грузим только Россию или всё? Всё — это 4 млн записей, `pg_trgm` и заметно худшая
   выдача; России хватает для сканера штрихкодов.
2. Что делать со строками без штрихкода — пропускать или дедуплицировать по
   «название + бренд»?
3. Нужен ли периодический реимпорт (OFF обновляется ежедневно) или разовой заливки
   достаточно? Реимпорт после этапов 1–2 безопасен, вопрос в том, кто его запускает.
4. Расширять `CURATED` руками — беру на себя или отдаём диетологу?
