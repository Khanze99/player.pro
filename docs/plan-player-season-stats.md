# План: статистика матчей по сезонам (паспорт игрока)

Статус: **бэкенд реализован и покрыт тестами** (миграция, модели, authz,
сервис, роуты, 11 тестов — `make lint`/`make test` зелёные), веб-клиент
(сайдбар, страница паспорта, радар) ещё не начат. Дата составления: 2026-11-04.

Дополняет `PlayerPro_TZ_final.md` — там этого домена нет вообще (продукт
целиком про wellness/RPE/Readiness/ACWR, раздел 6, не про технико-тактическую
статистику матчей). Пересекается с бэклог-идеей «Паспорт игрока» из
`docs/academy-vertical-manezh.md` (пункт 1) — но там это синоним уже
реализованного `mobile/src/app/athlete/[id]/index.tsx` (агрегатор
Readiness/ACWR/травм/нагрузки, без новой модели данных). Эта фича — другой
домен (реальная статистика матчей) и, по итогам обсуждения 2026-11-05,
**отдельный модуль в веб-админке** — свой маршрут и пункт сайдбара, не
вкладка на существующем отчёте (решение «один экран» ниже отменено, см.
актуальное в разделе «Веб-клиент»). Игрок в этом модуле — тот же
пользователь, что и везде в продукте: `season_player_stats.athlete_id`
ссылается на `users.id`, никакого отдельного ростера/идентичности под
статистику не заводим — связь с профилем/медопросом игрока держится на
одном и том же ID, не на синхронизации данных между модулями.

Референс по структуре/визуалу — скриншот профессиональной скаутинг-платформы
(клубный сезон + сезон сборной, статистика, радар-чарт, рыночная стоимость).

## Решения, принятые в обсуждении 2026-11-04

- **Реальный новый домен данных, не только визуальный стиль.** Удары, пасы,
  единоборства — вводятся вручную (видео/трекинг-интеграции в продукте нет и
  не планируется), новая модель, отдельная от `DailyMetric`.
- **Сезонные агрегаты, не по матчу.** Одна запись = итоги игрока за сезон в
  одном контексте (своя команда или внешняя — сборная), без записи каждого
  отдельного матча. Дешевле вводить и поддерживать, ровно тот уровень
  детализации, что в референсе (там тоже сезонные тайлы, не список матчей
  с разбивкой).
- **Тренер/врач вводят, но пишет только тренер.** Матчевая статистика —
  тренерская/скаутинговая область, не медицинская: writes только у
  `head_coach`/`coach` команды игрока (`authz.require_team_coach`, тот же
  паттерн, что у событий). Читают — тренер, врач, сам игрок (переиспользуем
  `authz.ensure_can_view_athlete`, уже разрешает ровно этот набор).
- **Рыночная стоимость — не делаем.** Про-скаутинг-метрика (агентская/
  трансферная оценка), не часть задачи мониторинга здоровья/готовности —
  это решение по содержанию метрики, не по уровню футбола (продукт не
  ограничен детско-юношеским/любительским сегментом, есть и
  профессиональный уровень).
- ~~Один экран, не два «паспорта» (вкладка на существующем отчёте)~~ —
  **отменено 2026-11-05.** Паспорт — отдельный модуль веб-админки: свой
  маршрут, свой пункт сайдбара, не вкладка на `athlete/[id]/index.tsx`/
  веб-отчёте. Чтобы не терять связность — страницы перелинкованы (кнопка
  со страницы отчёта на паспорт и обратно), но это два разных экрана, не
  один с переключателем. Актуальная версия — раздел «Веб-клиент» ниже.
- **Игрок в паспорте — тот же пользователь, не отдельная идентичность.**
  `season_player_stats.athlete_id` → `users.id`, тот же ID, что в
  Readiness/опросах/составе команды. Никакого отдельного ростера или
  сопоставления по имени между модулями — паспорт и медотчёт смотрят на
  одну и ту же строку в `users`.
- ~~Метрики — суженный, реально считаемый вручную набор, без xG/
  прогрессивных действий/обводок/возвратов мяча~~ — **расширено 2026-11-05**
  до полного набора черновика-артефакта (14 метрик вместо 8): добавлены
  xG, прогрессивные передачи, прогрессивные действия, обводки успешные,
  возвраты мяча, выносы. Формальное «вручную не посчитать с трибуны»
  уступило приоритету «как в референсе» — тренер/аналитик, ведущий такую
  детализацию, обычно смотрит повтор матча, не считает вживую. Два пункта
  черновика-артефакта **не** перенесены как отдельные метрики каталога, а
  не потому что отброшены содержательно:
  - «Голы/90» — дублирует уже существующее core-поле `score` записи
    (голы за сезон), отдельная метрика каталога создала бы два источника
    одного числа.
  - «xG+передачи (xGA)/90» — композит из xG и *ожидаемых* передач (xA);
    поле «ожидаемые передачи» в самом референсе не было, так что xGA
    нечем вычислить. Если понадобится — через отдельную метрику `xa`
    (ожидаемые передачи) первым шагом, не прямым вводом xGA.

  Итоговый каталог (сид в миграции, `backend/app/services/
  season_stats_service.py:FOOTBALL_METRICS`):

  | Категория | Метрики |
  |---|---|
  | Общие (core, не каталог) | матчи, минуты, голы, голевые передачи, жёлтые/красные карточки |
  | Удары | удары, удары в створ, **xG** |
  | Пасы | пасы, точные пасы, ключевые передачи, **прогрессивные передачи** |
  | Единоборства | единоборства, единоборства выигранные, отборы, **выносы** |
  | Обводки | **обводки успешные** |
  | Владение | **возвраты мяча**, **прогрессивные действия** |

  **Терминологическая развилка внутри референса:** на скриншоте слово
  «передачи» означает в одном месте голевые передачи (ассисты, верхний ряд
  тайлов), в другом — общий объём отданных пасов (строка радара). В модели
  и в UI это два разных поля с разными подписями: «голевые передачи»
  (общий блок) и «пасы» / «точные пасы» (категория «Пасы»), чтобы не
  повторять чужую путаницу в терминах.
- **Удары в створ / точные пасы / единоборства выигранные — опциональные.**
  Базовые (матчи, минуты, голы, карточки) обязательны, детализация по
  категориям — нет: часть тренеров не ведёт такую точность, пустое поле не
  должно блокировать сохранение записи.
- **Без привязки к Readiness/ACWR/DailyMetric.** Чисто информационная
  запись, пересчёт метрик не требуется (см. «Аналитика» ниже).
- **Радар-чарт — в объёме, не отложен.** Изначально предлагал вынести в
  открытые вопросы («полировка поверх данных»), пользователь явно попросил
  его вернуть — в референсе статистика показана не только числами. Радар
  строится из тех же per-90/%, что и текстовый блок рядом (один источник
  чисел, не дублирующий расчёт) — **8 осей** по `on_radar_default` каталога
  (расширен 2026-11-05 до 9, сужен обратно до 8 по запросу 2026-11-06 —
  «единоборства» на радаре один показатель, не два, см. ниже): удары/90,
  точность ударов, xG/90, прогрессивные передачи/90, единоборства
  выигранные (%), обводки успешные/90, возвраты мяча/90, прогрессивные
  действия/90. `tackles` (отборы) остался в каталоге и виден в текстовом
  списке/чекбокс-панели «Показатели», просто больше не входит в радар по
  умолчанию — его можно включить вручную. Домен (потолок) каждой оси —
  разумное фиксированное число, не персентиль среди
  игроков: базы
  для сравнения с другими игроками пока нет (см. «Открытые вопросы»).
  Отрисован (черновик-артефакт) как SVG — сетка-кольца + спицы + полигон,
  подписи осей текстовым тоном (не цветом серии), ровно по тем правилам,
  что у `dataviz`-скилла для одной серии: без легенды (подписывает
  заголовок секции), значение прямо у вершины.
  Если на сезон не заполнены удары/пасы/отборы (мало категорий) — радар не
  рисуется, карточка остаётся простым списком (решает сам экран по
  наличию данных, не отдельная настройка).
- **Не только футбол — мультиспорт с самого начала.** `Team.sport` в модели
  уже свободный текст (`backend/app/models/team.py`), не футбол-энум; в
  базе уже есть команды с разными/пустыми значениями. Зашивать удары/пасы/
  единоборства как столбцы — завязка на один вид спорта. Вместо этого:
  общее ядро записи (матчи/минуты/результативность/карточки-нарушения)
  одинаково для любого спорта, а разбивка по категориям — по каталогу
  метрик конкретного спорта (`sport_metric_defs`), не фиксированным
  столбцам. Каталог для футбола — тот список, что уже согласовали выше.
  Каталоги для других видов спорта — не в объёме этого плана, заводятся
  отдельной миграцией/сидом, когда понадобится конкретный спорт.
- **Каталог метрик — зашит в сидах/миграциях, не редактируется тренером
  через UI.** Проще и быстрее в MVP; экран управления метриками (создание
  категорий, настройка радара) — отдельная, более дорогая фича, не нужна
  прямо сейчас.
- **Подписи метрик/категорий — не в БД, как и весь остальной проект.**
  Бэкенд отдаёт только машиночитаемые ключи (`shots`, `shooting`, ...),
  тексты — словарь на клиенте. Тот же приём, что уже в проекте для
  `AlertReason` (`web/src/lib/reasons.ts`: «сервер отдаёт только
  машиночитаемые коды… текст подставляет клиент», тот же список
  продублирован в `mobile/src/i18n/ru.ts`).
- **Веб-админка, не мобилка.** Пользователь явно попросил сделать в
  `web/` — левый сайдбар с иконками-вкладками, как в референсе. Сейчас в
  админке сайдбара нет вообще (`web/src/app/(staff)/layout.tsx` — просто
  `Navbar` + центрированный контент), это будет первая вкладка нового
  левого навигационного шелла, не точечная правка одной страницы.
  Мобильный `athlete/[id]/index.tsx` в этом плане больше не трогаем — его
  правка, если понадобится, отдельная задача.

## Зачем

Тренер/врач сейчас не может зафиксировать результативность игрока по
сезонам в самом PlayerPro — эти цифры либо не ведутся вообще, либо в
отдельной таблице/памяти тренера. Разовый ручной ввод после сезона/турнира,
видно на одном экране с остальным отчётом по игроку.

## Что уже есть

Отчёт по игроку уже есть в обоих клиентах — мобильный `mobile/src/app/
athlete/[id]/index.tsx` (Readiness, ACWR, нагрузка, тренд, разбивка дня,
вес/ИМТ, цикл; открывается тапом из `CoachHome`/`dashboard.tsx`, только
что добавили туда ссылки, `docs/plan-pulse-loader.md`-соседний коммит
`feat(дашборд)`) и веб `web/src/app/(staff)/teams/[teamId]/athletes/
[athleteId]/page.tsx` (та же витрина, серверный компонент). Эта фича идёт
в веб-версию (см. решения выше) — отдельным модулем, перелинкованным с
этой страницей, не секцией на ней (решение пересмотрено 2026-11-05).
`AthleteProfile` уже хранит `position` (амплуа) — переиспользуется в
шапке, новое поле не нужно. `Team.sport` (`backend/app/models/team.py`)
уже свободный текст — основа для мультиспорт-каталога метрик.

## Данные и миграции

Три таблицы: справочник метрик по спорту + общее ядро записи + значения
метрик этой записи по справочнику.

```
-- Справочник: что вообще можно вводить для спорта, сидится миграцией,
-- не правится через UI (см. решения выше).
sport_metric_defs
  id                uuid, pk
  sport             varchar(32)   — "football"; тот же свободный текст,
                                     что Team.sport, без ограничения values
  key               varchar(64)   — "shots", "key_passes", "tackles", ...
                                     подпись — словарь на клиенте, не тут
  category_key      varchar(32)   — "shooting" / "passing" / "duels", ...
                                     тоже код, подпись на клиенте
  unit              varchar(16), nullable  — null (счётчик) | "percent"
  pct_of_key        varchar(64), nullable  — для unit=percent: ключ
                                     метрики-знаменателя в этом же спорте
                                     ("shots_on_target" → pct_of_key="shots")
  on_radar_default  boolean, default false
  radar_max         numeric(8,2), nullable — потолок оси радара (см.
                                     «Открытые вопросы» — не персентиль)
  sort_order        smallint, default 0
  UNIQUE(sport, key)

-- Общее ядро — одинаково для любого спорта
season_player_stats
  id                uuid, pk
  athlete_id        uuid, FK users.id, index
  sport             varchar(32)   — спорт команды игрока на момент записи
                                     (Team.sport), фиксируется, не меняется
                                     задним числом при смене спорта команды
  season            varchar(16)   — "2024/25", произвольный текст
  team_label        varchar(128)  — "Основа" / "Сборная Татарстана U16" —
                                     текст, не FK: своя команда или внешняя
  competition       varchar(128), nullable
  matches           smallint, default 0
  minutes           int, default 0
  score             smallint, default 0   — голы/очки/шайбы (generic)
  assists           smallint, default 0   — результативные передачи
  penalty_minor     smallint, default 0   — ЖК / малый штраф (generic)
  penalty_major     smallint, default 0   — КК / удаление (generic)
  created_by        uuid, FK users.id
  created_at, updated_at

-- Значения метрик каталога для конкретной записи
season_player_stat_values
  id                uuid, pk
  season_stat_id    uuid, FK season_player_stats.id, ON DELETE CASCADE
  metric_key        varchar(64)   — смысловая ссылка на sport_metric_defs
                                     (sport уже зафиксирован записью, не
                                     физический FK ради простоты)
  value             numeric(10,2)
  UNIQUE(season_stat_id, metric_key)
```

Подписи полей core-блока (`score`/`assists`/`penalty_minor`/`penalty_major`)
тоже per-sport («Голы» для футбола, «Очки» для баскетбола) — не в БД,
словарь на клиенте по `sport`, тем же приёмом, что у `sport_metric_defs`.

Без уникального ограничения на (athlete_id, season, team_label) в
`season_player_stats` — тренер может завести несколько записей на один
сезон/команду под разные турниры, запрещать это лишняя жёсткость. Индексы:
`athlete_id` (список по игроку — основной запрос), `season_stat_id` на
`season_player_stat_values`.

`make migration m="season_player_stats"` создаёт все три таблицы разом +
сид футбольного каталога (тот список категорий/метрик, что согласовали
выше) data-миграцией в том же файле. Ревью → `make upgrade`. Откат —
`make downgrade` (пустые таблицы, без риска для существующих данных).

## Каталог метрик футбола: диапазоны и как считается балл

Тренер вводит **сырое значение за сезон** (`value` — целое число случаев:
«20 ударов», «331 передача»), не per-90 и не %. Всё остальное — per-90,
% и позиция на оси радара — считается из него на лету при показе
(`SeasonStatOut`/`SeasonStatCard`), нигде не хранится отдельно.

**Формула балла на радаре** (один и тот же код что для счётчиков, что
для % — `unit` метрики выбирает, какая величина идёт в знаменатель деления
на `radar_max`):

- **Счётчик** (`unit = null`, например «удары», «отборы»): сначала
  `per_90 = value × 90 ÷ minutes` (нормировка на игровое время — иначе
  игрок с 1200 минут нечестно сравнивался бы с игроком с 300), затем
  **балл = per_90 ÷ radar_max**, обрезан до диапазона 0–1 (значение выше
  потолка просто упирается в край паутины, не прорывает его).
- **Процент** (`unit = percent`, например «точность ударов»): сначала
  `pct = value ÷ value(метрики-знаменателя из pct_of_key)` (например
  точность ударов = «удары в створ» ÷ «удары»; без знаменателя или при
  знаменателе = 0 — `null`, ось не рисуется), затем **балл = pct** напрямую
  — у всех процентных метрик `radar_max = 1`, то есть шкала уже 0–100%,
  делить второй раз не на что.

`radar_max` — **не персентиль среди игроков и не статистический
максимум**, а вручную подобранный разумный потолок (сколько ударов за
матч вообще реалистично для нападающего и т.п.) — простой стартовый
выбор, персентильная шкала — открытый вопрос ниже.

⚠️ **Баг, пойманный и исправленный 2026-11-06**: подпись у вершины оси
(«50%» vs «1.77») определялась по `radar_max ≤ 1`, не по реальному `unit`
метрики — у xG `radar_max = 1` **просто потому что xG/90 обычно меньше
единицы**, не потому что это процент. Результат: xG = 1.01 показывался
как «101%». Исправлено в `SeasonStatRadar.tsx`/`computeRadarAxes` —
`RadarAxis` теперь несёт настоящий `isPercent` (из `def.unit ===
"percent"`), угадывание по потолку оси убрано.

| Категория | Показатель | Что вводит тренер | Шкала балла (0–100% паутины) | На радаре по умолчанию |
|---|---|---|---|---|
| Удары | Удары | счётчик/сезон | 0–6 ударов **за 90 минут** | да |
| Удары | Точность ударов | счётчик/сезон (удары в створ) | 0–100% (= в створ ÷ все удары) | да |
| Удары | xG (ожидаемые голы) | счётчик/сезон | 0–1 xG **за 90 минут** | да |
| Пасы | Передачи | счётчик/сезон | 0–60 передач **за 90 минут** | нет |
| Пасы | Точные передачи | счётчик/сезон | 0–100% (= точные ÷ все передачи) | нет |
| Пасы | Ключевые передачи | счётчик/сезон | 0–3 **за 90 минут** | нет |
| Пасы | Прогрессивные передачи | счётчик/сезон | 0–10 **за 90 минут** | да |
| Единоборства | Единоборства (всего) | счётчик/сезон | 0–12 **за 90 минут** | нет |
| Единоборства | Единоборства выигранные | счётчик/сезон | 0–100% (= выигранные ÷ все единоборства) | да |
| Единоборства | Отборы | счётчик/сезон | 0–4 **за 90 минут** | нет |
| Единоборства | Выносы | счётчик/сезон | 0–3 **за 90 минут** | нет |
| Обводки | Обводки успешные | счётчик/сезон | 0–4 **за 90 минут** | да |
| Владение | Возвраты мяча | счётчик/сезон | 0–12 **за 90 минут** | да |
| Владение | Прогрессивные действия | счётчик/сезон | 0–14 **за 90 минут** | да |

Метрики без «на радаре по умолчанию» никуда не делись — видны в текстовом
списке под радаром и доступны в чекбокс-панели «Показатели», просто не
включены в 8 осей по умолчанию (2026-11-06: категория «Единоборства»
сведена к одному показателю на радаре, не двум — см. «Решения» выше).

## API

Реализовано (роуты в `app/api/v1/season_stats.py`, под префиксом
`/season-stats`, по образцу существующих неймспейсов — каждый свой
префикс, не общий верхнеуровневый `/athletes/...`):

- `GET /season-stats/sports/{sport}/metrics` — каталог метрик спорта
  (ключи, категории, unit, радар-конфиг). Публично для авторизованных —
  справочник, не персональные данные. Клиент кэширует, по нему строит и
  форму ввода, и группировку карточки, и оси радара — не хардкодит набор
  полей под футбол.
- `GET /season-stats/athletes/{athlete_id}` — список записей (с
  вложенными `metrics`, per-90/% уже посчитаны), сортировка по сезону
  убыв. Доступ — `authz.ensure_can_view_athlete` (коуч/врач команды + сам
  игрок, не чужой игрок/посторонний).
- `POST /season-stats` — создать (`athlete_id` в теле; `sport` сервис
  берёт из команды игрока, не из запроса; нет команды или у команды не
  указан `sport` → 422). Сервис валидирует, что все ключи в `values`
  существуют в `sport_metric_defs` для этого спорта — неизвестный ключ =
  422. Доступ — `authz.ensure_can_manage_season_stats`.
- `PATCH /season-stats/{stat_id}` — править (частично, `exclude_unset`;
  замена `values` — явный DELETE+flush перед INSERT, не переприсвоение
  коллекции, см. риски). Та же проверка через команду записи.
- `DELETE /season-stats/{stat_id}` — удалить (204). Та же проверка.

Производные per-90 (на `minutes`) и % (`value / значение pct_of_key`)
считаются в схеме ответа на лету, не хранятся: записей на игрока единицы,
кэшировать нечего, а денормализация добавила бы риск рассинхрона без
выгоды в производительности. `minutes == 0` → все per-90 `null`, не
деление на ноль; то же для % с `pct_of_key`-знаменателем = 0.

## Права доступа

- Чтение — `ensure_can_view_athlete` (уже используется у метрик/wellness-
  истории игрока, ничего нового придумывать не нужно).
- Запись (create/update/delete) — новая `authz.ensure_can_manage_season_stats`:
  `head_coach`/`coach` общей с игроком команды или admin организации игрока;
  не `medic` (это не медицинская запись) и не сам игрок. Реализована и
  покрыта тестами (`test_season_stats.py`).
- Не медицинские/специальные персональные данные (не `body_metrics`) —
  `DataConsent`/согласие не требуется, видимость уже закрыта обычным
  правилом доступа к отчёту игрока.

## Риски

- **Качество ручных данных.** Без источника истины (видео/статистик на
  матче) цифры настолько точны, насколько аккуратен тренер — это осознанный
  компромисс ручного ввода, не баг дизайна.
- **Разные тренеры — разная методика подсчёта** (например, что считать
  «ключевой передачей»). Не решаем в этой фиче — как минимум стоит
  задокументировать определения в самой форме (подсказки под полями) на
  этапе 7.
- **Автоматической подгрузки данных нет, проверено.** Разведал два
  источника (2026-11-04):
  - `rustatsport.ru` (RUSTAT, платформа РФС) — покрывает РПЛ и Первую
    лигу, то есть профессиональный уровень нам подходит содержательно, но
    доступ только у зарегистрированных клубов/аналитиков РФС, публичного
    API или программы для партнёров не нашёл; сайт не отвечает на
    автоматические запросы вообще (похоже на блокировку ботов).
  - `yflrussia.ru` (ЮФЛ, детско-юношеский уровень) — есть открытые без
    логина страницы игроков с разбивкой по сезонам/матчам, но только
    базовые метрики (игры/голы/передачи/карточки), и `robots.txt` сайта
    явно запрещает автоматический доступ именно к `/player`, `/matches`,
    `/participants` — строить на этом интеграцию означало бы идти против
    прямого запрета владельца.

  Вывод: ручной ввод тренером — не временное решение «до интеграции», а
  единственный реалистичный путь на обозримое время, независимо от
  уровня футбола (про/юношеский/любительский).

  просто, но «плоский» радар не покажет, хорош ли результат относительно
  сверстников. Персентиль был бы честнее, но нужна база сравнения (другие
  игроки той же возрастной группы/позиции) — её пока нет и это отдельная
  работа (минимум — отбор пиров по амплуа+возрасту, хватит ли данных по
  немногочисленным ручным записям). Не блокирует MVP, фиксированный потолок
  — осознанный стартовый компромисс.
