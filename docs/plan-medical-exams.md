# План: учёт УМО/ТМО (медосмотры игрока)

Статус: **реализовано и проверено на реальных данных.** Дата составления:
2026-09-24, реализация — 2026-09-24.

Дополняет ТЗ — раздела про медосмотры в `PlayerPro_TZ_final.md` нет вообще (только
Availability/InjuryRecord, раздел 6.5 и 7.3). УМО (Углублённое медицинское
обследование) и ТМО (Текущий медицинский осмотр) — обязательные для российских
спортивных организаций периодические осмотры, не описанные в исходном ТЗ.

Текущее состояние — `docs/functionality.md`, раздел «Доступность и травмы»: похожая
по форме сущность уже есть (`InjuryRecord` — история, `created_by`, без
редактирования задним числом), эта фича повторяет её устройство, не изобретает
новое.

Решения, принятые в обсуждении 2026-09-24:

- **Кому видно** — весь штаб с доступом к игроку (тренер/врач/admin организации),
  то же правило, что у остального веб-кабинета (`ensure_can_view_athlete`). Сами
  даты — не мед. детализация уровня карты боли/описания травмы: это факт допуска
  к нагрузке, который тренеру нужен так же, как врачу.
- **Кому можно ставить/редактировать — только врач (`medic`)**, явное решение
  пользователя. **Admin организации НЕ проходит** — тот же принцип, что уже
  сформулирован в `core/authz.ensure_can_view_sensitive`: «админ организации это
  менеджер клуба, а не медработник». Coach/head_coach тоже не пишет, хотя видит.
- **История, не текущая запись.** Несколько записей на игрока и тип за время,
  устройство один в один как `InjuryRecord` (append-only, `created_by`,
  `created_at`). Текущий статус («действует до», «истёк», «нет данных») —
  **производное значение**: самая свежая по `passed_date` запись каждого типа,
  а не отдельное поле — тот же принцип, что у Availability («статус дня
  наследуется от последней записи»).
- **Без редактирования/удаления прошлых записей.** Ошибку в дате чинят новой
  записью, не правкой старой — это медицинский журнал, история должна быть
  неизменной (аудируемой), а не переписываемой. `POST` — единственная операция
  записи. Если понадобится корректировка задним числом — отдельная фича с
  собственным решением (см. «Открытые вопросы»), не в этом плане.
- **Один общий тип таблицы на оба вида осмотра** (`kind: umo | tmo`), не два
  отдельных — они структурно идентичны (дата прохождения + срок действия),
  то же решение, что уже принято для `PolicyConsent.kind` в проекте: не плодить
  две почти одинаковых модели/схемы/сервиса ради двух разных названий.
- **Только веб-админка, мобильного клиента не касается** — явное решение
  пользователя. `MeOut`/мобильные экраны не меняются.
- **Не фича-флаг.** Новая таблица, новый роут — ничего не меняет в существующем
  поведении, включать/выключать нечего.

## Зачем

Врач должен видеть и фиксировать, когда игрок в последний раз проходил
обязательные медосмотры и до какого числа они действительны — сейчас в системе
для этого вообще нет места (только текущий статус доступности/травмы, не
периодические осмотры со сроком действия).

## Что уже есть

| Есть | Где | Что даёт |
|---|---|---|
| `InjuryRecord` — история травм, `created_by`, без правки задним числом | `app/models/injury.py` | Образец устройства: та же форма (append-only мед. запись на игрока) |
| `AvailabilityRecord` — статус дня наследуется от последней записи | `app/models/availability.py`, `availability_service.py` | Образец «текущее = самое свежее» — тот же приём для «действует до» |
| `ensure_can_view_sensitive` — admin не проходит, `medic`/`coach` разведены | `core/authz.py` | Образец правила «только врач», admin исключён |
| `PolicyConsent.kind` — один тип на несколько видов согласия | `app/models/policy_consent.py` | Образец «kind вместо двух таблиц» |
| Веб-кабинет, отчёт по игроку (`teams/[teamId]/athletes/[athleteId]`) | `docs/plan-web-admin.md` | Готовое место для новой карточки — расширение уже существующей страницы |
| `MeOut.teams: MembershipOut[]` — командная роль текущего пользователя | `app/schemas/auth.py`, уже приходит в вебе через `api.me()` | Веб-клиент узнаёт, `medic` ли текущий пользователь в этой команде — без нового эндпоинта |

**Медосмотров, самого понятия — нет нигде.** Первая реализация.

## Данные и миграции

- `MedicalExamKind(str, Enum)`: `umo`, `tmo` — в `app/models/enums.py`.
- `MedicalExam` (`app/models/medical_exam.py`):
  ```
  id            uuid, pk
  athlete_id    uuid, fk users, index
  kind          MedicalExamKind (String(8), как InjuryStatus — не нативный PG enum)
  passed_date   date
  valid_until   date
  created_by    uuid, fk users
  created_at    datetime, server_default now()
  ```
  Без уникального ограничения — история, много строк на (athlete_id, kind).
  Валидация `valid_until >= passed_date` — на уровне Pydantic-схемы (как и у
  `InjuryRecord.end_date`, без DB CHECK).
- `make migration m="add medical_exams table"` → ревью → `make upgrade`.
  Откат — `DROP TABLE`, тривиален.

## API

Новый роутер `app/api/v1/medical_exams.py`, регистрируется в `router.py` под тем
же `_consented`, что и остальные бизнес-роутеры:

- **`GET /athletes/{athlete_id}/medical-exams`** — `list[MedicalExamOut]`, вся
  история, отсортирована новыми сверху. Доступ — `ensure_can_view_athlete`
  (как у `/analytics/athletes/{id}/metrics`).
- **`POST /athletes/{athlete_id}/medical-exams`** — `{kind, passed_date,
  valid_until}` → `MedicalExamOut`, `201`. Доступ — новая
  `ensure_can_manage_medical_exams` (только `medic` в общей команде, `403`
  иначе, включая admin). `400` при `valid_until < passed_date`.

Схемы (`app/schemas/medical_exam.py`): `MedicalExamIn` (kind, passed_date,
valid_until + валидатор дат), `MedicalExamOut` (+ id, athlete_id, created_by,
created_at).

Сервис (`app/services/medical_exam_service.py`): `create(...)`,
`list_for_athlete(...)`, и небольшой хелпер `current_status(exams) ->
dict[MedicalExamKind, MedicalExamOut | None]` — самая свежая запись по каждому
типу, чтобы веб-клиент не считал это сам (даты сортировки/сравнения — на
бэкенде, не на фронте).

## Права доступа

Новое правило в `core/authz.py`:

```python
async def ensure_can_manage_medical_exams(db, viewer: User, athlete_id: uuid.UUID) -> None:
    """УМО/ТМО — пишет только врач (medic). Admin НЕ проходит — тот же принцип,
    что в ensure_can_view_sensitive: админ организации — менеджер клуба, не
    медработник."""
    athlete = await db.get(User, athlete_id)
    if athlete is None:
        raise HTTPException(status_code=404, detail="Игрок не найден")
    role = await _shared_team_staff_role(db, viewer.id, athlete_id)
    if role == TeamRole.medic:
        return
    raise _forbidden()
```

Чтение — существующий `ensure_can_view_athlete`, без изменений.

## Мобильный клиент

**Не применимо** — явное решение пользователя, только веб-админка. `MeOut` и
мобильные экраны не трогаем.

## Персональные и медицинские данные

- Даты УМО/ТМО — не спецкатегория уровня карты боли/описания травмы (это факт
  допуска, не диагноз), поэтому видно всему штабу с доступом к игроку, без
  `DataConsent`.
- В аудит-лог (`audit_service`) — факт создания записи (кто, когда, какой тип,
  на кого) уже покрывается тем, что `created_by`/`created_at` хранятся в самой
  записи; отдельного `AuditLog`-события не заводим, если не попросят отдельно
  (то же решение, что у `InjuryRecord`, там тоже нет отдельного аудит-лога).

## Тесты

- `medic` создаёт запись — `201`, дата валидна.
- `coach`/`admin`/`athlete` пытаются создать — `403` у всех троих (admin
  тоже — важно проверить отдельно, это неочевидное правило).
- `valid_until < passed_date` — `400`.
- `GET` отдаёт историю новыми сверху; доступен coach/medic/admin, недоступен
  постороннему (как у существующих `ensure_can_view_athlete`-тестов).
- `current_status`: несколько записей одного типа → возвращает самую свежую по
  `passed_date`; тип без записей → `None`; `valid_until` в прошлом → статус
  «истёк», не «действует».
- Миграция: `make upgrade`/`make downgrade` проходят.

## Риски

- **Admin не проходит на запись — неочевидное правило**, легко забыть при
  ревью или тестировании руками («я же админ, должен мочь всё») — явно
  проверяется тестом (шаг 5) и явно вынесено в комментарий кода, не только в
  этот план.
- **Нет редактирования истории** — если врач опечатался в дате, единственный
  путь исправления сейчас — добавить новую корректную запись поверх. Это
  сознательное решение (аудируемость), но стоит проверить на практике: если
  окажется неудобно, можно завести `PATCH` на последнюю запись отдельным
  небольшим добавлением, не переделывая план целиком.

## Открытые вопросы

- Показывать ли просроченный/скоро истекающий УМО/ТМО как флаг на Squad Status
  или в командной сводке (`_alerts`) — сознательно не в этом плане (только
  карточка на странице игрока). Данные уже в форме, годной для такого флага
  (`current_status`) — если понадобится, это отдельный маленький заход поверх
  готового.
- Нужен ли `PATCH`/удаление последней ошибочной записи — см. риск выше, не
  решаем заранее, ждём практики.
- Вложение файла (скан медицинской справки) — не запрошено, не в объёме.

## Примечание о реализации (2026-09-24)

Все 8 шагов декомпозиции сделаны за один заход. Отличие от плана: путь эндпоинтов —
`/medical-exams/athletes/{id}` (GET/POST), а не `/athletes/{id}/medical-exams` как
было в черновике плана — поправлено под фактическую конвенцию проекта
(wellness/rpe/injuries тоже `/<ресурс>/athletes/{id}`, не наоборот).

Backend: `MedicalExamKind` + `MedicalExam` (миграция `20260924_1621`, upgrade/downgrade
оба проходят), `ensure_can_manage_medical_exams`, `medical_exam_service.py`,
роуты, тесты (`test_medical_exams.py` + 2 теста в `test_authz.py`). Полный набор —
246 тестов зелёных, `ruff check`/`format` чисты.

Веб-клиент: `MedicalExamsCard` (плашки УМО/ТМО + история + форма для врача),
`canEdit` считается на странице по `me.teams` (без нового эндпоинта). `tsc`/`eslint`/
`next build` чисты.

Проверено на реальных данных (живой backend + веб на портах, реальные HTTP-запросы,
включая headless-браузер с реальным кликом по кнопкам формы — не только curl):
- Врач видит кнопку «Добавить осмотр»; тестовый тренер (у него `global_role: admin` +
  `team_role: head_coach` — сид `seed_demo.py` делает тренера org-admin'ом) — кнопку
  не видит и на прямой POST получает 403, при этом карточку и даты видит нормально.
- POST от врача — 201; POST от тренера — 403 c `"Недостаточно прав"`.
- Дата окончания раньше даты начала — 422 с читаемым текстом ошибки (Pydantic
  `model_validator`, не `HTTPException` — код на фронте (`lib/api.ts`) это учитывает).
- Полный клик через headless Chrome: открыл форму → выбрал ТМО → ввёл дату →
  сохранил → карточка обновилась (`router.refresh()`), обе записи (УМО и ТМО)
  в истории, обе плашки статуса верны. Ноль ошибок в консоли браузера.

Для смоук-теста создал тестового врача `test-medic@demo.playerpro.local` (домен
`@demo.playerpro.local` — попадёт под `wipe_demo` при следующем `make seed-reset`,
отдельно чистить не нужно).
