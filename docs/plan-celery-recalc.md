## Решения, принятые в обсуждении 2026-09-07

- **В Celery уходит и батч, и live-пересчёт.** Нынешний `analytics_service.recalc_athlete`,
  который сейчас вызывается **в той же транзакции**, что и запись wellness/RPE, заменяется
  на постановку задачи в очередь **после коммита** записи. Плюс: сабмит отвечает быстрее и
  не держит соединение с БД на время пересчёта всей истории игрока; API-процесс перестаёт
  заниматься тяжёлой работой и может масштабироваться. Минус, принятый осознанно: игрок и
  тренерский дашборд несколько секунд (до отработки воркера) видят **прежние** Readiness /
  ACWR по затронутому дню. Компенсируется инвалидацией запросов на клиенте (см. «Мобильный
  клиент») и ночным прогоном как страховкой.
  *Отклонено:* «только батч, live оставить синхронным» — проще и без окна рассинхрона, но
  API-процесс продолжает ходить в БД на тяжёлый пересчёт, и требование «один воркер»
  частично сохраняется.
- **Планировщик — отдельный контейнер Celery Beat.** Сервис `beat` в docker-compose рядом
  с `worker`, расписание — `crontab(hour=NIGHTLY_RECALC_HOUR_UTC, minute=0)` в UTC.
  Переживает рестарт без пропуска суток (нынешний `asyncio.sleep` при рестарте после часа
  пересчёта теряет день — `docs/deploy.md`).
  *Отклонено:* системный cron на ВМ, дёргающий `celery call` — расписание уезжает из
  репозитория и образа. *Отклонено:* `celery worker -B` (встроенный Beat) — нельзя
  масштабировать воркеры, не размножив Beat.
- **Ручной `POST /api/v1/analytics/recalc` становится диспатчем.** Ставит задачу, отдаёт
  `202` + `task_id`. Добавляется `GET /api/v1/analytics/recalc/{task_id}` (админ) со
  статусом задачи и числом пересчитанных игроко-дней по завершении. Нужен result backend
  в Redis.
  *Отклонено:* fire-and-forget без `task_id` — админ не узнаёт результат. *Отклонено:*
  оставить синхронным — расходится с принципом «тяжёлое — в воркер».
- **Брокер и result backend — существующий Redis, разные логические БД.** OTP/rate-limit
  остаются на `redis://…/0`, брокер — `…/1`, result backend — `…/2`. Отдельный инстанс
  Redis для очереди на UAT-ВМ (2 CPU / 4 GB) преждевременен, как и managed-сервисы
  (`docs/deploy.md`).
- **Прямой переход без dual-path флага.** `_nightly_recalc_loop` из `app/main.py`
  удаляется полностью; одновременно в compose появляются `worker` + `beat`. Флаг
  `NIGHTLY_RECALC_ENABLED` сохраняется, но теперь гейтит регистрацию периодической задачи
  в расписании Beat, а не asyncio-задачу.
- **Задача-обёртка — тонкий слой, как роут.** `app/tasks/*` только достаёт сессию и зовёт
  `analytics_service`; бизнес-логики и запросов к БД в задаче нет. Слои
  `api|tasks → services → core` сохраняются.
- **Тесты идут через настоящий протокол запуска Celery.** Не подменяем постановку задачи
  на прямой `await` — `conftest` включает `task_always_eager=True` +
  `task_eager_propagates=True`, брокер `memory://`, backend `cache+memory://`, и `.delay()`
  в тестах реально исполняет задачу через eager-путь Celery. Асинхронная работа задачи
  всегда выполняется в выделенном потоке с собственным событийным циклом (мост sync→async,
  один и тот же механизм в проде и в тестах) — поэтому eager внутри работающего цикла
  pytest-asyncio не даёт `RuntimeError`. Redis-локи в eager-режиме — no-op (конкуренции
  нет). Реальная PostgreSQL сохраняется: задача в тестах ходит в `playerpro_test` через
  отдельный движок, привязанный к циклу моста; БД не мокируется.

## Зачем

1. **Убрать пересчёт из процесса API.** Сейчас и ночной прогон (asyncio-задача в
   `lifespan`), и live-пересчёт (в транзакции сабмита) исполняются внутри uvicorn. Отсюда
   жёсткое «один воркер uvicorn» в `docs/deploy.md`: при нескольких воркерах/репликах
   ночной прогон стартует в каждом процессе.
2. **Надёжное расписание.** Нынешнее держится на `asyncio.sleep` до 02:00 UTC — рестарт
   API после этого часа пропускает сутки пересчёта; после деплоя в это окно прогон надо
   дёргать руками (`docs/deploy.md`).
3. **Не блокировать сабмит.** `recalc_athlete` идёт «с первого дня данных игрока» и с
   годами истории дорожает; сейчас игрок ждёт его синхронно при каждом сабмите wellness/RPE.
4. **Задел под уведомления (ТЗ раздел 9).** Утренние напоминания, RPE-напоминание через
   N минут после события, дайджест алертов штабу — тем же Beat + воркером (см. «Открытые
   вопросы», в объём этой задачи не входит).

## Данные и миграции

**Не применимо.** Новых таблиц и полей нет, схема `DailyMetric` не меняется. Celery
хранит очередь и результаты в Redis, не в PostgreSQL. Миграции не создаются.

Единственное «состояние» — ключи в Redis:
- очередь брокера (`…/1`), TTL сообщений — дефолт Celery;
- результаты задач (`…/2`), `result_expires` = 24 ч (достаточно, чтобы админ опросил
  статус ручного прогона);
- Redis-локи `recalc:athlete:{id}` и `recalc:all` (см. «Аналитика»), TTL с запасом над
  временем прогона.

## API

Неймспейс `/api/v1/analytics`.

### Изменяется: `POST /analytics/recalc`

- Доступ: `require_org_admin` (как сейчас).
- Тело: пусто.
- Поведение: `recalc_all_task.delay()`, немедленный ответ.
- Ответ `202 Accepted`:
  ```json
  { "task_id": "5f2c…", "status": "queued" }
  ```
- Схема ответа: `RecalcDispatchOut { task_id: str, status: Literal["queued"] }`.
- Ошибки: `401` (нет токена), `403` (не админ), `503` — если брокер недоступен и задачу
  поставить не удалось (`kombu.exceptions.OperationalError`); тело
  `{"detail": "Очередь пересчёта недоступна"}`.

### Новый: `GET /analytics/recalc/{task_id}`

- Доступ: `require_org_admin`.
- Параметр пути: `task_id: str`.
- Поведение: `AsyncResult(task_id, app=celery_app)` → маппинг состояния.
- Ответ `200`:
  ```json
  { "task_id": "5f2c…", "state": "SUCCESS", "recalculated_days": 1284 }
  ```
  - `state ∈ {PENDING, STARTED, SUCCESS, FAILURE}` (строкой, как у Celery; `PENDING` =
    «не найдена или ещё не взята» — Celery их не различает, это документируем);
  - `recalculated_days` присутствует только при `SUCCESS`;
  - при `FAILURE` — поле `error: str` с типом исключения (без трейсбека).
- Схема: `RecalcStatusOut { task_id: str, state: str, recalculated_days: int | None = None,
  error: str | None = None }`.
- Ошибки: `401`, `403`. Несуществующий `task_id` отдаёт `200` с `state="PENDING"` —
  ограничение result backend Redis, отдельного `404` не делаем.

### Внутренние задачи (не HTTP)

- `analytics.recalc_athlete` — аргумент: `athlete_id: str` (UUID строкой). **Только id и,
  опционально, `end_date: str` (ISO).** Никаких данных wellness/RPE в аргументах (см.
  «Персональные и медицинские данные»). `acks_late=True`, `max_retries=3`,
  `retry_backoff=True`, автоповтор на `OperationalError`/`DBAPIError`.
- `analytics.recalc_all` — без аргументов (или `end_date: str`). `acks_late=True`.
  Периодический вызов регистрируется в `beat_schedule` только если
  `NIGHTLY_RECALC_ENABLED`.

Клиент за один запрос: ручной прогон — `POST` даёт `task_id`, дальше опрос `GET`; экрану
метрик отдельный запрос не нужен, он и так читает `DailyMetric` через `GET
/analytics/me/metrics` (см. «Мобильный клиент»).

## Права доступа

`app/core/authz.py` — **новых правил нет.**

- `POST /analytics/recalc` и `GET /analytics/recalc/{task_id}` — оба под
  `require_org_admin` (уже есть).
- IDOR-нюанс, фиксируем как принятый: `task_id` не привязан к организации, админ орг. A
  может опросить статус задачи, поставленной админом орг. B. Утечка минимальна — в ответе
  только число игроко-дней и состояние. Причина, по которой это не чиним здесь:
  `recalc_all` **и так глобален** — пересчитывает всех атлетов всех организаций, а не
  организацию вызвавшего (docstring роута «по организации» уже не соответствует коду). См.
  «Открытые вопросы».
- Медицинская детализация: задача читает `WellnessEntry` (в т.ч. `injury`/`symptom` —
  спецкатегория) и пишет `DailyMetric` (агрегаты: балл, зона, флаги). Разграничение
  medic/coach на уровне **чтения** `DailyMetric` не меняется — пересчёт не отдаёт данные
  наружу.

## Аналитика

- **Идемпотентность сохраняется** — `recalc_athlete` / `recalc_all` не меняются, только
  переезжают в воркер. Повторный прогон (Beat + ручной + live для одного игрока
  одновременно) обновляет строки `DailyMetric`, а не плодит.
- **Конкурентность.** Несколько задач, пересчитывающих один и тот же ряд параллельно, дают
  лишнюю нагрузку и риск ошибок сериализации PostgreSQL. Защита:
  - `recalc_athlete_task` берёт Redis-лок `recalc:athlete:{athlete_id}`; если занят —
    задача не выполняется повторно, а `raise Retry` с коротким backoff (ряд всё равно
    будет пересчитан либо занявшим лок прогоном, либо ретраем).
  - `recalc_all_task` берёт лок `recalc:all`; если занят — задача завершается со статусом
    `skipped` (в `result` — `{"skipped": true}`), не ждёт.
  - В eager-режиме (тесты) локи — no-op: `.delay()` исполняется синхронно, конкуренции нет,
    Redis для тестов не поднимается (`conftest` уже держит `OTP_STORE=memory` ровно ради
    этого).
  - Ночной `recalc_all` и live-таски одного игрока могут пересечься: лок на игрока
    сериализует их, идемпотентность гарантирует корректный итог.
- **Порядок «коммит → enqueue».** В `wellness_service` / `rpe_service` задача ставится
  **после** `db.commit()` записи. Иначе воркер прочитает БД раньше, чем строка
  зафиксирована, и пересчитает ряд без неё (ночной прогон потом исправит, но окно
  рассинхрона вырастет).
- **Терпимость к недоступному брокеру.** Постановка live-задачи обёрнута: если брокер
  недоступен, сабмит всё равно успешен (запись сохранена, стрик обновлён), ошибка
  логируется, ряд догонит ночной прогон. Это согласуется с офлайн-философией ТЗ
  (раздел 11): данные не теряются, метрики отстают.
- **Окно рассинхрона.** Между ответом на сабмит и отработкой воркера `DailyMetric` за
  затронутые дни содержит прежние значения. Типично < 1–2 с. Клиент инвалидирует и
  перезапрашивает метрики (см. ниже); ночной прогон — финальная сверка.

## Мобильный клиент

Новых экранов нет. Админского UI для ручного пересчёта в мобильном клиенте нет —
`POST /analytics/recalc` дёргается вручную (curl/Swagger), поэтому **новых строк i18n не
требуется**. Проверить при реализации: нет ли экрана «Пересчёт» в `mobile/src/app/` —
если появился, `ru.ts / en.ts / es.ts` обновляются все три.

Изменения:
- `mobile/src/api/hooks.ts` — мутации сабмита wellness и RPE после успеха
  `queryClient.invalidateQueries` для ключей метрик (`analytics/me/metrics`), стриков и
  тренерского дашборда (как сейчас), **плюс** одна отложенная перепроверка через ~3 с
  (`setTimeout` + повторный `invalidateQueries`, либо кратковременный `refetchInterval`),
  чтобы подхватить результат воркера. Без агрессивного поллинга.
- Состояние «пересчёт идёт» на экране метрик не показываем: если строка за сегодня
  секунду-другую ст'арая, экран показывает предыдущее значение без спиннера. Пустое
  состояние (данных ещё нет) и состояние ошибки сети — как сейчас, не трогаем.
- `mobile/src/api/types.ts` / `client.ts` — правки только если появится админский экран
  статуса (`RecalcDispatchOut` / `RecalcStatusOut`). По умолчанию — не трогаем.

- **Порядок деплоя:** поднять `redis` (уже есть) → `worker` → `beat` → выкатить `api` без
  `_nightly_recalc_loop`. Откат: вернуть предыдущий образ `api` (с asyncio-лупом),
  остановить `worker`/`beat`; очередь в Redis можно очистить (`celery purge`).

## Персональные и медицинские данные

- **Аргументы задач — только `athlete_id` (UUID) и даты (ISO-строка).** Ни полей
  wellness/RPE, ни `injury`/`symptom`, ни ФИО. Причина: тело задачи Celery сериализуется
  в брокер (Redis) и может попасть в логи воркера при `--loglevel=debug` и в
  `task_received`-события. Спецкатегория (152-ФЗ ст. 10) в очередь не кладётся.
- **`result` задачи — только число** (`recalculated_days`) и флаги состояния. Никаких
  баллов конкретных игроков, дат травм и т.п.
- **Логирование.** В задачах логируем `athlete_id` и счётчики, не содержимое записей.
  `--loglevel=info` в проде (не `debug`).
- **Согласие (`DataConsent`).** Не применимо: пересчёт не публикует данные и не меняет
  видимость — считает те же агрегаты, что и раньше, тем же кодом.
- **Аудит-лог.** Не применимо: пересчёт `DailyMetric` не является изменением статуса
  доступности/травмы (сейчас тоже не пишется). Ручной `POST /recalc` можно при желании
  отметить в аудите (админское действие) — см. «Открытые вопросы».
- **РФ-контур.** Redis-брокер — тот же self-hosted инстанс в том же контуре, что и
  сейчас для OTP. Внешних управляемых очередей нет (ТЗ раздел 10).

## Этапность

1. **Каркас Celery.** `celery_app.py`, конфиг, `worker`/`beat` в локальном compose,
   `make worker` / `make beat`. Пустая задача-пинг для проверки, что воркер берёт из
   очереди. Без изменения поведения пересчёта.
2. **Задачи пересчёта + Beat-расписание.** `app/tasks/analytics_tasks.py`, Redis-локи,
   регистрация периодической `recalc_all` по `NIGHTLY_RECALC_ENABLED`. Bootstrap
   async-движка в воркере. `_nightly_recalc_loop` ещё жив (параллельно) — снимаем в конце
   этапа.
3. **Переключение live-пути и роута.** `wellness_service` / `rpe_service` → enqueue после
   коммита (терпимо к недоступному брокеру); `analytics.py` → диспатч + `GET
   /recalc/{task_id}`; удаление `_nightly_recalc_loop` из `app/main.py`.
4. **Клиент.** Инвалидация + отложенная перепроверка метрик после сабмита.
5. **Инфра и документация.** stand/prod compose, `docs/deploy.md`, `docs/functionality.md`,
   `.env.example`, `backend/Dockerfile` CMD-комментарий.

## Риски

1. **Fork-safety async-движка в prefork-воркере Celery.** `app/database.py` создаёт
   `create_async_engine` на импорте; Celery форкает воркер-процессы, унаследованный пул
   asyncpg-соединений в дочернем процессе нерабочий («Future attached to a different
   loop», «connection was closed»). Митигация: `worker_process_init` → `runtime.reset()`
   (сброс унаследованных ссылок) + `ensure_loop()` (свой поток+цикл в этом процессе);
   движок задач отдельный, на `NullPool`, создаётся лениво на цикле-мосте; задачи-обёртки
   исполняют корутины `analytics_service` в этом цикле (не `asyncio.run` на каждый вызов).
   Проверено дымовым прогоном `recalc_all` / `recalc_athlete` в реальном воркере (solo и
   prefork). Локальный нюанс macOS: prefork виснет без
   `OBJC_DISABLE_INITIALIZE_FORK_SAFETY=YES` — выставлено в `make worker`, в Docker/Linux
   не требуется.
2. **Eager-режим в тестах против работающего цикла pytest-asyncio.** `task_always_eager`
   исполняет `.delay()` синхронно в текущем потоке, а тест уже под работающим event loop —
   `asyncio.run` / `run_until_complete` на нём дал бы `RuntimeError`. Митигация: мост
   sync→async всегда гоняет корутины задачи в **отдельном потоке с собственным циклом**
   (тот же механизм в проде и в тестах), поэтому eager-путь Celery работает без подмен.
   Движок SQLAlchemy для задачи привязан к циклу моста (в тестах — отдельный движок к
   `playerpro_test`, не мокируется). Мост закрывается session-scoped фикстурой.
3. **Окно рассинхрона метрик.** До отработки воркера дашборд/игрок видят прежние Readiness
   и зону по затронутому дню. Митигация: enqueue сразу после коммита, короткий backoff
   ретраев, инвалидация + отложенная перепроверка на клиенте, ночной прогон как сверка.
   Осознанно принято при выборе «батч + live».
4. **Брокер недоступен в момент сабмита.** Live-задачу не поставить. Митигация: обёртка —
   сабмит успешен, ошибка в лог, ряд догонит Beat. Но если и `beat`/`worker` лежат —
   метрики замирают надолго. Нужен минимальный мониторинг доступности воркера (см.
   «Открытые вопросы») и пункт в чек-листе деплоя.
5. **Конкурентные пересчёты одного ряда** (Beat × ручной × live) → нагрузка и возможные
   ошибки сериализации PostgreSQL. Митигация: Redis-локи на игрока и на `recalc:all`,
   идемпотентность, retry на `OperationalError`.
6. **Пропущенный запуск `worker`/`beat` при деплое** — молчаливая деградация: сабмиты
   проходят, метрики не считаются. Митигация: пункт в чек-листе `docs/deploy.md`,
   `restart: unless-stopped`, `depends_on`.
7. **Ресурсы UAT-ВМ (2 CPU / 4 GB).** Плюс два процесса (`worker` concurrency=2, `beat`) и
   Redis как брокер. Для MVP-объёмов терпимо; `--concurrency` держать в 1–2.
8. **Рассинхрон времени.** Beat считает `crontab` в UTC от системного времени контейнера —
   убедиться, что у контейнера UTC (сейчас у asyncio-лупа та же зависимость).
9. **Забыли `celery_result_backend` при `GET /recalc/{task_id}`.** Без backend статус не
   прочитать. Конфиг обязателен, дефолт задан.

## Открытые вопросы

- **Мониторинг очереди.** Flower / экспортер метрик / хотя бы healthcheck воркера — нужен
  до прода? Сейчас в плане только пункт чек-листа и логи. Вероятно, отдельная небольшая
  задача.
- **WebSocket-пуш пересчитанных метрик** (ТЗ раздел 10, Redis pub/sub). Естественное
  продолжение: воркер по завершении публикует в Redis, дашборд получает обновление без
  поллинга и отложенной перепроверки на клиенте. WS-слой сейчас не реализован — вне
  объёма этой задачи.
- **Задачи уведомлений** (ТЗ раздел 9): утренние напоминания wellness, RPE-напоминание
  через N минут после события, дайджест алертов штабу. Лягут на тот же Beat + воркер.
  Отдельный план, не расширяем объём здесь.
- **Инкрементальный пересчёт** (от последней изменённой даты, а не всей истории игрока) —
  давно отмечен в `functionality.md` 5.4 как «с годами данных». Ортогонален переезду в
  Celery, оставляем на потом.
- **Глобальность `recalc_all`.** Сервис пересчитывает всех атлетов всех организаций, хотя
  docstring роута говорит «по организации». Чинить ли scope здесь (и, как следствие,
  привязывать `task_id` к орг для `GET`-статуса) или отдельной задачей? Рекомендация —
  отдельной, чтобы не раздувать этот план.
- **Аудит ручного `POST /recalc`.** Писать ли админское действие в аудит-лог? Сейчас нет.
  Малое изменение, можно добавить на этапе 4, если решим «да».
