# План: общий каталог продуктов из пользовательских и расширение базы

Статус: **проектирование, код не начат.** Дата составления: 2026-11-11.

Дополняет `PlayerPro_TZ_final.md`: питания в ТЗ нет. Продолжает
`docs/plan-food-catalog.md` (наполнение справочника, этапы 1-5 сделаны, этап 6
«атрибуция OFF» не сделан) и этап 2 `docs/plan-women-health-nutrition.md` (дневник).
Текущее состояние: `docs/functionality.md`, строка «Дневник питания». Фича выключена
флагом `FEATURE_NUTRITION_ENABLED` и на проде не включалась.

Решения, принятые в обсуждении 2026-11-11:

- **Пользовательские продукты идут в общий пул через модерацию.** Игрок заводит
  продукт как сейчас, помечает «предложить в общий каталог», модератор в веб-кабинете
  проверяет и включает для всех. *Отклонено:* автоматический показ внутри команды
  (мусор и дубли расходятся по всей команде, личный режим ничего не получает) и
  «оставить личными» (тогда база растёт только руками).
- **Домашняя еда в общий каталог не предлагается.** `custom_kind = homemade` остаётся
  личным всегда: «мамин борщ» у каждого свой. Предлагать можно `new_product`,
  `restaurant` и `other`.
- **Расширение базового слоя идёт отдельно и параллельно**: ручной `CURATED` со 162 до
  400-500 позиций по российским таблицам (значения переносятся по одному, дамп книги
  не копируется, см. раздел 7 `plan-food-catalog.md`). USDA не берём: названия
  английские, продукты американские, перевод 7 тысяч позиций дороже, чем 300 руками.

## Зачем

Сейчас в каталоге 162 выверенных позиции и 1 663 штрихкода из Open Food Facts по
России (у 95% российских карточек OFF нет нутриентов, больше оттуда не взять).
Игрок, не нашедший продукт, заводит свой, но его работа пропадает для остальных: тот
же йогурт или протеин заводят по десять раз в каждой команде. Модерируемый общий пул
превращает пользователей в источник каталога, а ручной `CURATED` закрывает то, чего
в штрихкодах нет вообще: базовые продукты и блюда.

## Что уже есть

- `FoodItem` (`app/models/nutrition.py`): `source` (`curated` / `open_food_facts` /
  `custom`), `created_by` (NULL у общего каталога), `verified`, `category`,
  `custom_kind` с комментарием «подсказка для будущей модерации». Снимок нутриентов в
  `FoodLogEntry`, поэтому правка карточки модератором историю не ломает.
- `POST /nutrition/foods` и экран `mobile/src/app/food-create.tsx`: игрок уже заводит
  продукт с категорией и `custom_kind`. Видимость: `_visible_items` в
  `nutrition_service.py` отдаёт общий каталог плюс свои `custom`, чужие никогда.
- Ранжирование поиска: `curated`, затем свои, затем OFF; `verified` выше; префикс выше
  подстроки. Частичный уникальный индекс по штрихкоду только для слоя OFF.
- Платформенного админа нет: `GlobalRole.admin` это админ организации. Модератор
  каталога это новая сущность.
- Уведомления («колокольчик», `notifications_service.notify`) есть, новый тип
  добавляется одной строкой в enum и триггером.

## Данные и миграции

Одна миграция через `make migration m="food_item_moderation"`:

- `food_items.share_status` `String(16)`, NOT NULL, default `private`:
  `private` / `pending` / `approved` / `rejected`. Индекс частичный
  `(share_status) WHERE share_status = 'pending'`: очередь модерации маленькая,
  остальные строки индексу не нужны.
- `food_items.reviewed_by` FK users (SET NULL), `reviewed_at`, `reject_reason`
  `String(255)`. Причина отказа видна автору.
- `users.is_moderator` `Boolean` NOT NULL default false. Ставится скриптом
  `make set-moderator email=…` (по образцу `set_global_admin.py`), в UI не выдаётся.
- Откат: удалить колонки и индекс. Данных не теряем: все существующие `custom`
  получают `private`.
- Одобренный продукт **остаётся `source = custom`** с `created_by` автора, но
  `share_status = approved` и `verified = true`. Авторство нужно только модератору
  и для удаления аккаунта; в выдаче автора не показываем.
- Удаление аккаунта (`account_deletion_service.OWNED` содержит `FoodItem.created_by`):
  одобренные продукты надо **оставить** каталогу, иначе удаление одного автора
  выбивает продукты у всех. Перед удалением `OWNED`-строк: `UPDATE food_items SET
  created_by = NULL WHERE created_by = :id AND share_status = 'approved'`. Снимок
  в `FoodLogEntry` других игроков и так не зависит от строки каталога.
  `pending` и `rejected` удаляются вместе с аккаунтом.

## API

Пользователь:

- `POST /nutrition/foods`: новое поле `share: bool = false`. При `share = true` и
  `custom_kind != homemade` продукт создаётся в `pending`, иначе в `private`
  (`homemade` с `share = true` это 422 «Домашнюю еду в общий каталог не берут»).
  Лимит: не больше 20 продуктов в `pending` у одного автора (429, защита от спама).
- `GET /nutrition/foods/mine`: свои продукты со статусом и причиной отказа.
- `POST /nutrition/foods/{id}/share`: предложить уже существующий личный продукт
  (`private` → `pending`); `rejected` повторно предлагать нельзя (409), только завести
  заново с правками.
- `FoodItemOut` получает `share_status` (у чужих одобренных отдаём `approved`, чтобы
  клиент не показывал кнопку «предложить»).
- Видимость `_visible_items`: общий каталог, свои, **плюс `share_status = approved`**.
  Поиск: `approved` ранжируется вместе с OFF (ниже `curated` и своих), `verified`
  уже `true`.
- Штрихкод: при одобрении, если такой штрихкод уже есть у OFF-записи или другого
  одобренного продукта, сервер отвечает модератору 409 «дубль по штрихкоду» и
  предлагает отклонить. Уникальный индекс на `approved + barcode` не вводим:
  OFF-слой перезаливается, конфликт лучше разбирать человеку.

Модерация (новый роут `api/v1/moderation.py`, сервис `moderation_service.py`):

- `GET /moderation/foods?status=pending&limit=50&cursor=…`: очередь, старые первыми.
  В каждой строке подсказки: похожие по названию (`ILIKE` первых двух слов) и
  совпадение по штрихкоду, чтобы модератор видел дубль сразу.
- `PATCH /moderation/foods/{id}`: правка полей перед одобрением (название, бренд,
  категория, нутриенты). Автору правки видны, снимки в его дневнике не меняются.
- `POST /moderation/foods/{id}/approve`, `POST /moderation/foods/{id}/reject
  {reason}`. Оба пишут `reviewed_by`, `reviewed_at`, аудит-лог (`food.approve` /
  `food.reject`) и уведомление автору (`food_approved` / `food_rejected`).
- Все эндпоинты за `require_workouts_enabled`-подобной зависимостью
  `require_nutrition_enabled` и `require_moderator`.

## Права доступа

В `app/core/authz.py`: `require_moderator(user)`: `user.is_moderator`, иначе 403.
Модератор не получает доступа ни к чему, кроме каталога: роли в командах и организации
не трогаем. Чужой продукт в `pending`/`private`/`rejected` по-прежнему 404 для всех,
кроме автора и модератора.

Тесты обязательны: чужой `pending` 404; `approved` виден всем, в том числе личному
режиму; `homemade` не предлагается; лимит очереди; модератор без флага 403; после
удаления аккаунта автора одобренный продукт остаётся, `pending` исчезает.

## Аналитика

Не применимо: каталог не влияет на `DailyMetric`.

## Мобильный клиент

- `food-create.tsx`: переключатель «Предложить в общий каталог» (скрыт при
  `homemade`), подсказка «Проверим и добавим для всех, обычно за пару дней».
- Экран «Мои продукты» (из вкладки питания или профиля): список со статусами
  «Личный», «На проверке», «В каталоге», «Отклонён: причина», кнопка «Предложить» у
  личных.
- В поиске одобренные чужие продукты выглядят как обычные записи каталога.
- Уведомления `food_approved` / `food_rejected` в колокольчике, тап ведёт в
  «Мои продукты».
- i18n: ru/en/es.

## Веб-кабинет

Страница `/moderation/foods` в группе `(staff)`: доступ по `is_moderator` (из
`/auth/me`), для остальных пункта меню нет. Таблица очереди, карточка с правкой
полей, подсказки о дублях, кнопки «В каталог» / «Отклонить» с причиной. Это первый
экран в вебе, который не привязан к организации: лейаут `(staff)` сейчас ждёт
`org_id`, нужно разрешить модератора без команд.

## Персональные и медицинские данные

Продукт не ПДн. Автор в публичной выдаче не раскрывается. `reject_reason` пишет
модератор, пользовательского текста там нет. В аудит-лог попадают id продукта и
модератора, не содержимое карточки.

## Выкатка

- Под тем же `FEATURE_NUTRITION_ENABLED`. Перед включением на проде обязателен этап 6
  старого плана: атрибуция Open Food Facts в приложении (ODbL).
- Миграция `make upgrade`, первый модератор `make set-moderator`.
- Старые клиенты без поля `share` продолжают создавать `private`.

## Этапность

1. Бэкенд: миграция, статусы, видимость, лимит, удаление аккаунта, уведомления,
   модерация, тесты. **2-3 дня.**
2. Мобилка: переключатель, «Мои продукты», уведомления. **1 день.**
3. Веб: страница модерации, лейаут без организации. **1-1.5 дня.**
4. Контент: `CURATED` 162 → 400-500 позиций (крупы и гарниры, овощи, супы, выпечка,
   спортпит, фастфуд). Работа с таблицами, не код: **2-3 дня** на 300 позиций, с
   вычиткой пользователем выборки, как в `plan-exercise-catalog.md`.
5. Атрибуция OFF (этап 6 старого плана). **0.5 дня.**

Итого около двух недель с запасом; этапы 1-3 и 4 независимы.

## Риски

- **Модератора может не быть.** Очередь без человека копится, авторы ждут. Смягчение:
  лимит 20 в очереди и честная подсказка «обычно за пару дней»; если модерации нет
  месяцами, фичу «предложить» выключаем отдельным флагом, продукты остаются личными.
- **Дубли одобренных.** Два модератора одобрят одно и то же под разными названиями.
  Подсказки о похожих при одобрении снижают риск, слияние карточек не делаем.
- **Качество нутриентов.** Ошибка в одобренной карточке попадает во все дневники
  дальше (снимки прошлых записей не трогаются). Правка модератором возможна в любой
  момент, одобрение требует заполненных ККал и БЖУ (валидация схемы уже есть).
- **ODbL.** Пользовательские продукты не производная OFF, обязательства лицензии на
  них не распространяются; атрибуция OFF всё равно обязательна до включения фичи.
