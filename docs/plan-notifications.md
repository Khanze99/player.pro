# План: внутренние уведомления («колокольчик»)

Статус: **реализовано 2026-11-10** (бэкенд, мобилка, веб), миграция `20261110_1802_notifications_bell` к применению. Дата составления: 2026-11-10.

Отношение к ТЗ: реализует раздел 9 «Уведомления» и модель `Notification` из раздела 7
в части **in-app канала**. Push (expo-notifications, FCM/APNs) из раздела 9 в эту итерацию
не входит, но сервис строится так, чтобы push добавился вторым каналом без переделки
триггеров. Текущее состояние: в `docs/functionality.md` уведомлений нет; таблица
`notifications` создана baseline-миграцией, но ни один код в неё не пишет и не читает
(кроме удаления аккаунта).

Решения, принятые в обсуждении 2026-11-10:
- **Только колокольчик, без push.** Push требует токенов устройств, ключей FCM/APNs и
  настроек в сторах: это отдельная итерация. Здесь закладываем точку расширения: все
  триггеры зовут один `notifications_service.notify(...)`, push потом станет ещё одним
  получателем внутри него.
- **Риск тренеру/врачу приходит сразу, с дедупликацией**, а не утренним дайджестом:
  травма, о которой узнали на следующее утро, бесполезна. Дедупликация: одно
  уведомление на (получатель, игрок, повод, день).
- **Спортсмену: все четыре типа** (событие создано/изменено/отменено, напоминание об RPE,
  напоминание о wellness, смена статуса доступности). Напоминание о wellness без push
  полезно слабо, но оно же станет первым push-сценарием, поэтому делаем сразу.
- **Колокольчик в мобилке и в веб-кабинете.** Тренеры и врачи живут в вебе.
- **Без фича-флага**: включается сразу для всех, флаг в конфиге не заводим.
- Отклонено: дайджест (см. выше); WebSocket для живого счётчика (поллинг раз в минуту
  достаточен, WebSocket-инфраструктуры в проекте пока нет); уведомление о «не заполнил
  опрос» тренеру (шум: это и так видно в Squad Status).

## Зачем

Сейчас тренер узнаёт о проблеме, только если сам открыл Squad Status. Игрок узнаёт о
перенесённой тренировке, только если сам открыл календарь. Колокольчик переворачивает
это: важное приходит к человеку, а не человек ищет важное.

## Что уже есть

- `models/notification.py`: `id, user_id, type, payload(JSON), created_at, read_at`,
  индекс по `user_id`. Таблица пустая, на проде данных нет.
- `account_deletion_service` уже удаляет уведомления удаляемого пользователя.
- `dashboard_service._alerts`: коды причин риска (`low_sleep`, `high_load`, `injury`...).
  Переиспользуем те же коды и те же переводы на клиенте (`web/src/lib/reasons.ts`,
  мобильные i18n-ключи дашборда), чтобы формулировки в колокольчике и в Squad Status
  совпадали.
- Celery worker + beat (`docs/plan-celery-recalc.md`): live-пересчёт `DailyMetric` после
  сабмита и ночной прогон. Новые периодические задачи встают туда же.
- `notify_service.py` это **канал доставки OTP/инвайтов** (почта, SMS), к колокольчику
  отношения не имеет. Новый сервис называем `notifications_service.py`, чтобы не
  смешивать.
- `Organization.timezone` есть: по нему считаем «утро» для напоминания о wellness.

## Каталог уведомлений

Текст на сервере не хранится: в БД код типа и коды причин, текст собирает клиент через
i18n (ru/en/es), как в Squad Status. Медицинских подробностей (где болит, насколько,
текст `injury_details`) в уведомлении нет: только факт. Подробности открываются по тапу
на экране игрока, и туда пускает уже существующий authz.

### Тренеру и врачу (head_coach, coach, medic команд игрока)

| type | Когда | Откуда триггер | Дедуп-ключ |
|---|---|---|---|
| `athlete_injury` | в wellness отмечена травма (`injury=true`) | `wellness_service.create_entry` | `injury:{athlete}:{date}` |
| `athlete_illness` | в wellness отмечен симптом болезни (`symptom=true`) | то же | `illness:{athlete}:{date}` |
| `athlete_pain` | на карте боли есть точка с `severity >= 5` | то же | `pain:{athlete}:{date}` |
| `athlete_risk` | после live-пересчёта: Readiness в красной зоне и/или ACWR > 1.5 (`high_risk`) | задача `recalc_athlete` | `risk:{athlete}:{date}:{reason}` |

- `athlete_illness` добавлен сверх запроса: симптом болезни в продукте уже равнозначен
  травме по последствиям (флаг недоступности), молчать о нём странно.
- `athlete_risk.reasons` это коды из `_alerts`: `low_sleep`/`low_energy`/.../`high_load`.
  Readiness и ACWR дают **разные** дедуп-ключи: если утром упал Readiness, а вечером после
  RPE улетел ACWR, это два уведомления, второе несёт новую информацию.
- Риск считается **только на live-пересчёте** (после сабмита wellness/RPE), не на ночном
  прогоне: иначе игрок, неделю сидящий в красном ACWR, будил бы тренера каждую ночь.
- Отправитель-игрок сам себе уведомлений не получает; если игрок одновременно staff
  своей команды (редко), себя исключаем.

### Спортсмену

| type | Когда | Откуда триггер | Дедуп-ключ |
|---|---|---|---|
| `event_created` | тренер создал командное событие в будущем | `events_service.create_event` | нет |
| `event_updated` | изменились время, длительность, место или тип будущего события | `events_service.update_event` | нет |
| `event_cancelled` | будущее событие удалено | `events_service.delete_event` | нет |
| `rpe_reminder` | прошло 30 мин после конца события, RPE по нему нет, посещаемость не `absent`/`excused` | Beat, раз в 10 мин | `rpe:{event_id}` |
| `wellness_reminder` | по времени организации наступило 08:00, опроса за сегодня нет | Beat, раз в 15 мин | `wellness:{date}` |
| `availability_changed` | staff сменил статус доступности игрока | `availability_service.set_status` | нет |

- Получатели событий: участники команды с `team_role=athlete`, кроме автора. Правка
  только названия события уведомления не порождает: не шумим из-за опечатки.
- `event_cancelled` хранит в payload снимок (тип, название, начало): события уже нет,
  ссылаться не на что.
- Окно `rpe_reminder`: событие закончилось от 30 мин до 6 ч назад. Шире не надо: через
  сутки напоминание бессмысленно, а задача должна быть дешёвой.
- `wellness_reminder` для личного режима (без организации) считается по
  `settings.default_timezone` (Europe/Moscow). Час напоминания: `settings.wellness_reminder_hour`
  (по умолчанию 8). Настройка часа самим пользователем: открытый вопрос.

## Данные и миграции

Расширяем существующую `notifications` (таблица пустая, данных для переноса нет):

| Поле | Тип | Зачем |
|---|---|---|
| `team_id` | UUID FK teams, nullable, `ondelete=CASCADE` | фильтр «только команды, где я сейчас состою»; личный режим = NULL |
| `athlete_id` | UUID FK users, nullable, `ondelete=CASCADE` | о ком уведомление; удаление аккаунта игрока само забирает уведомления о нём у тренеров (152-ФЗ) |
| `event_id` | UUID FK events, nullable, `ondelete=SET NULL` | ссылка для перехода; при отмене снимок в payload |
| `dedup_key` | String(128), nullable | идемпотентность триггеров |
| `user_id` | добавить `ondelete=CASCADE` | сейчас без него |
| `payload` | JSON -> JSONB | единообразие, дешевле сравнивать |

Ограничения и индексы:
- `uq_notification_user_dedup` UNIQUE (`user_id`, `dedup_key`) WHERE `dedup_key IS NOT NULL`.
  Вставка через `INSERT ... ON CONFLICT DO NOTHING`: повторный пересчёт, ретрай задачи
  Celery или два параллельных воркера не создадут дубль. Это и есть гарантия дедупликации,
  а не проверка «уже есть?» в коде.
- `ix_notification_user_created` (`user_id`, `created_at DESC`): лента.
- `ix_notification_user_unread` (`user_id`) WHERE `read_at IS NULL`: счётчик.
- Старый `ix_notifications_user_id` удаляется (покрыт составным).

Хранение: ночная задача удаляет уведомления старше 90 дней (`settings.notification_retention_days`).
Колокольчик не архив.

Миграция: `make migration m="notifications колокольчик"` -> ревью -> `make upgrade`;
downgrade возвращает схему baseline (данные новых колонок теряются, это допустимо).

## API

Префикс `/api/v1/notifications`, всё только про текущего пользователя.

```
GET  /notifications?cursor=<opaque>&limit=30     лента, новые сверху
GET  /notifications/unread-count                 {"count": 3}
POST /notifications/{id}/read                    204
POST /notifications/read-all                     204
```

Элемент ленты (`NotificationOut`):

```json
{
  "id": "...",
  "type": "athlete_risk",
  "created_at": "2026-11-10T07:42:00Z",
  "read_at": null,
  "team_id": "...",
  "athlete": {"id": "...", "name": "Иван Петров"},
  "event": {"id": "...", "type": "training", "title": "...", "planned_start": "..."},
  "reasons": ["low_sleep", "high_load"],
  "status": "unavailable"
}
```

- Имя игрока подставляется при чтении (join по `athlete_id`), не хранится в payload:
  переименование сразу видно, персданные не дублируются.
- `event` для `event_cancelled` собирается из снимка в payload, `id` = null.
- Пагинация курсором по (`created_at`, `id`), `limit` 1..50.
- Чужой `id` в `/read` -> **404**, не 403: не подтверждаем существование чужих записей.
- Лента и счётчик отфильтрованы: уведомления с `team_id` показываются, только пока
  пользователь состоит в этой команде (переход в другой клуб, `docs/plan-player-transfer.md`,
  снятие с команды). Отдельной чистки при снятии не нужно.

## Права доступа

- Читать и отмечать: только владелец (`user_id == current_user.id`) плюс фильтр по
  текущему членству. Проверка живёт в запросе сервиса (`notifications_service._visible`),
  а не в `core/authz.py`: это не ролевое правило, а «только свои строки», и отдельная
  функция дублировала бы тот же WHERE.
- Получателей риска выбирает сервис: staff (head_coach, coach, medic) команд, где игрок
  числится athlete. Admin, создавший команду, в ней head_coach и получает. Admin организации
  без командной роли уведомлений о рисках **не** получает: он менеджер клуба, не участник тренировочного
  процесса (как в `ensure_can_view_sensitive`).
- Медицинская детализация: в уведомлении только факт («отметил боль»). Где и насколько
  больно, текст травмы видны на экране игрока по существующим правилам. Тренер и врач
  получают одинаковые уведомления; разведение медика и тренера сохраняется на уровне
  экрана, куда ведёт уведомление.
- Спецкатегории (цикл, питание, состав тела, `DataConsent`) уведомлений не порождают,
  согласие не затрагивается.

## Аналитика

На `DailyMetric` и формулы не влияет, пересчёт не нужен. Задача `recalc_athlete`
получает флаг `notify: bool` (True из `enqueue_recalc_athlete`, False из ночного
`recalc_all`); после коммита пересчёта при `notify=True` сравнивает метрику дня с
порогами и зовёт `notifications_service`. Повтор задачи идемпотентен благодаря
`dedup_key`.

## Мобильный клиент

- **Где колокольчик**: правый верхний угол шапки главного экрана, справа от `TeamBadge`,
  у игрока (`(tabs)/index.tsx`) и у тренера (`CoachHome.tsx`). Не на всех вкладках:
  шапки у вкладок разные, а главный экран это точка входа. Новый компонент
  `components/NotificationBell.tsx`, иконка `BellIcon` в `Icons.tsx`.
- **Бейдж**: есть непрочитанные -> красный кружок с числом (больше 9 -> «9+»); нет -> просто
  колокольчик без отметок.
- **Счётчик**: `useUnreadCount()` с `refetchInterval: 60_000` и рефетчем при возврате
  приложения в foreground; после сабмита wellness/RPE и действий тренера инвалидируется.
- **Экран** `app/notifications.tsx`: группы «Сегодня / Вчера / Ранее», непрочитанные с
  акцентной точкой и чуть ярче, кнопка «Прочитать все», пулл-ту-рефреш, догрузка курсором.
  Тап: отметить прочитанным и перейти:
  `athlete_*` -> `athlete/[id]`; `event_*` -> календарь (экрану события нужны все поля
  расписания, в уведомлении только краткое описание); `rpe_reminder` -> `rpe?eventId=`; `wellness_reminder` -> `wellness`;
  `availability_changed` -> профиль.
- **Пустое состояние**: иконка колокольчика и «Новых уведомлений нет». **Ошибка**: текст и
  «Повторить».
- i18n: `notifications.*` в `ru.ts`, `en.ts`, `es.ts`; коды причин берутся из уже
  существующих ключей дашборда.

## Веб-кабинет

- Колокольчик в `Navbar.tsx`, в правой группе перед именем пользователя. Клик открывает
  поповер с последними 10 и ссылкой «Все уведомления» на страницу `(staff)/notifications`.
- BFF-роуты `web/src/app/api/notifications/*` по образцу существующих.
- Поллинг счётчика раз в 60 с, только пока вкладка видима.
- Переход из уведомления об игроке ведёт в паспорт игрока в вебе.

## Выкатка

- **Без фича-флага** (решение 2026-11-10): фича включена сразу для всех. Откат, если
  понадобится, через релиз, а не через конфиг.
- Старые мобильные клиенты: эндпоинты новые, существующие контракты не меняются, старые
  версии просто не видят колокольчика.
- Старых данных нет (таблица пустая). Ретроспективно за прошлые дни уведомления не
  создаём.
- Beat: две новые записи в `beat_schedule` (rpe раз в 10 мин, wellness раз в 15 мин) и
  чистка в ночной задаче. Деплой: перезапуск `worker` и `beat` (`docs/deploy.md`).

## Персональные и медицинские данные

- В payload и в аргументы Celery-задач не кладём текст травмы, точки боли, значения
  метрик: только коды и id (правило из `analytics_tasks.py`).
- В логи не пишем payload уведомлений, только `type` и id.
- Аудит-лог: **не применимо**, уведомление производное и ничего не меняет; исходные
  изменения статусов уже аудируются.
- Согласие (`DataConsent`): **не применимо**, спецкатегории не участвуют.
- Удаление аккаунта: `ondelete=CASCADE` по `user_id` и `athlete_id`; проверить, что
  `account_deletion_service` не конфликтует (он удаляет явно, каскад подстрахует).

## Этапность

1. Бэкенд-ядро: модель, миграция, сервис `notify`, API ленты.
2. Триггеры тренеру/врачу: травма, болезнь, боль, риск.
3. Триггеры спортсмену: события, статус доступности, напоминания RPE и wellness (Beat).
4. Мобилка: колокольчик, экран, i18n.
5. Веб: колокольчик в навбаре, поповер, страница.

Этапы 4 и 5 можно начинать параллельно этапу 2-3, как только готов контракт этапа 1.

```
                       -> контракт описан, совпадает с разделом «API»

                       mark_read, read_all, cleanup) + authz ensure_owns_notification
                       -> make lint чист
4. [python-senior]     роуты /notifications + регистрация в router.py
                       -> в роутах нет логики и запросов к БД
5. [python-senior]     триггеры staff: wellness (injury/illness/pain), recalc_athlete(notify)
                       -> ручной сабмит на стенде создаёт ровно одно уведомление каждому staff
6. [python-senior]     триггеры athlete: events create/update/delete, availability,
                       Beat-задачи rpe_reminder/wellness_reminder, чистка 90 дней
                       -> повторный прогон задачи не создаёт дублей
7. [tester]            тесты (см. ниже) -> make test зелёный
8. [security-auditor]  медданные в payload/логах, IDOR на /read, фильтр по членству,
                       каскад при удалении аккаунта
9. mobile              NotificationBell, экран, хуки, i18n x3 -> web и native проверены
10. web                навбар, поповер, страница, BFF -> проверено в браузере
11. [code-reviewer]    ревью целиком
```

Обязательные тесты:
- Дедуп: два сабмита/два прогона задачи -> одно уведомление; Readiness и ACWR в один день -> два.
- Получатели: staff всех команд игрока получают, admin без командной роли и сам игрок нет,
  чужая команда нет.
- Ночной `recalc_all` уведомлений не создаёт.
- `rpe_reminder`: нет при уже сданном RPE, при `absent`/`excused`, вне окна; есть ровно один.
- `wellness_reminder`: граница часа по таймзоне организации, личный режим по дефолтной.
- События: правка только названия не уведомляет; правка времени уведомляет; прошлое событие нет.
- Доступ: чужой id -> 404; после снятия с команды уведомления команды пропадают из ленты
  и счётчика.
- Удаление аккаунта игрока забирает уведомления о нём у тренеров.
- Payload не содержит `injury_details` и данных точек боли.

## Риски

- **Шум.** Команда из 25 человек с плохим сном даст тренеру 10 уведомлений до завтрака.
  Смягчение: дедуп по дню и причине; если окажется много, следующим шагом группировка
  в одно «у 6 игроков риск» (см. открытые вопросы).
- **Беззвучность без push.** Напоминание о wellness игрок увидит, только открыв
  приложение. Принято сознательно, push следующей итерацией.
- **Поллинг.** 60 с x число активных клиентов: дешёвый запрос по partial-индексу, при
  текущих объёмах несущественно.
- **Таймзоны.** Напоминания по времени организации; у игроков на выезде в другом поясе
  напоминание придёт «не в 8». Приемлемо для первой версии.

## Открытые вопросы

- Порог боли: сейчас `severity >= 5` на любой точке. Подтвердить с врачом клуба.
