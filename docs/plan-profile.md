## Решения, принятые в обсуждении 2026-09-07

- **Аватар — приватный, с серверной обработкой.** Загрузка через multipart-эндпоинт,
  файл в локальную статику на volume, в БД — только имя файла. Отдаём через
  **авторизованный** `GET /users/{user_id}/avatar`, а не публичный `/static` (как
  у гербов организаций): лицо человека — персональные данные, доступ по угадываемой
  ссылке недопустим. Сервер обрезает в квадрат и снимает всю метадату, включая
  EXIF/GPS (фото с базы утекает геолокацией). Новые зависимости: `Pillow`,
  `python-multipart`.
  *Отклонено:* публичный `/static/avatars/<uuid>.jpg` как у гербов — проще, но фото
  доступно без токена.
- **Набор полей.** На чтение: email, телефон, глобальная роль, роли в командах,
  «в приложении с {дата}». На редактирование: ФИО (уже есть), дата рождения, пол,
  амплуа (`position`, колонка уже есть), **рост и вес**. Рост/вес — sensitive-scope
  `body_metrics`: штабу видны только по согласию игрока, себе — всегда.
  *Отклонено:* минимальный набор без роста/веса — по решению обсуждения включаем.
- **Пол.** Для новых пользователей — **обязательный шаг онбординга** (экран нельзя
  пропустить, надо явно выбрать вариант). Существующим — поле в профиле, задают
  сами, когда захотят; без баннеров-напоминаний. Вариант «Предпочитаю не указывать»
  (`not_specified`) остаётся допустимым выбором и на онбординге — самодекларация из
  плана women-health не нарушается, «обязательность» относится к факту вопроса, а не
  к раскрытию пола.
  *Отклонено:* серверный флаг `onboarding_sex_asked` и баннер-напоминание
  существующим — не заводим лишнюю колонку, пока продукт этого не потребовал.
- **Роль.** Показываем глобальную роль (Админ / Персонал / Игрок) **и** список
  «команда → роль в команде» (Главный тренер, Тренер, Врач, Игрок). Без организации —
  «Личный аккаунт».
  *Отклонено:* только глобальная роль — «Персонал» ничего не говорит врачу и тренеру.
- **Фича-флаг не заводим.** Изменения аддитивные и низкорисковые, как и брендинг,
  который выкатывался без флага. Единственная предпосылка — примонтированный volume
  под каталог аватаров; если к деплою его нет, вводим `FEATURE_AVATARS` как
  временный рубильник только для файловой части.

## Зачем

Профиль сейчас — ФИО, язык, PIN, выход. Пользователь не видит даже собственный
email и свою роль, хотя сервер их отдаёт (`/auth/me` уже содержит `email`,
`global_role`, `org_id`). Нет ни аватара, ни даты рождения, ни антропометрии —
данных, которые ожидаются в любом спортивном приложении и нужны штабу для работы
с составом. Отдельная дыра: поле `sex` есть в БД и в клиенте (от него зависит показ
раздела «Цикл»), но **его негде задать** — ни в онбординге, ни в профиле, поэтому
де-факто оно всегда `not_specified`.

## Данные и миграции

Одна миграция, сгенерировать `make migration m="profile avatar height weight"` из
`backend/`, отревьюить, применить `make upgrade`.

`users`:
| колонка | тип | примечание |
|---|---|---|
| `avatar_path` | `String(256)` null | имя файла в каталоге аватаров (не URL). Аватар доступен любой роли, поэтому на `User`, а не на `AthleteProfile`. Меняется при каждой перезагрузке фото → сам служит cache-busting-сигналом клиенту |

`athlete_profiles`:
| колонка | тип | примечание |
|---|---|---|
| `height_cm` | `SmallInteger` null, CHECK 100–250 | |
| `weight_kg` | `Numeric(4,1)` null, CHECK 30–250 | 0.1 кг точности |

`birthdate` и `sex` уже есть — миграции не требуют.

Откат (`make downgrade`) — drop трёх колонок. Бэкофилл не нужен: всё nullable,
`sex` уже с дефолтом. Существующие пользователи: `sex = not_specified`, повторный
онбординг им не показывается.

Каталог файлов: `backend/media/avatars/` (**вне** `/static`-mount — не раздаётся
статикой). Обязан быть на примонтированном volume, иначе аватары исчезнут при
следующем релизе (та же ловушка, что с `static/branding`). Имя файла:
`{user_id}_{8 hex}.webp` — случайный суффикс меняет URL при замене фото.
Индексов новые поля не требуют (выборок по ним нет).

## API

Все ответы — существующие схемы, расширяем их.

### `MeOut` (+ `build_me_out`)
Добавить:
- `created_at: datetime` — «в приложении с».
- `has_avatar: bool` (и/или `avatar_url: str | None` = `"/api/v1/users/{id}/avatar"`
  когда файл есть).
- `teams: list[TeamMembershipOut]` — `{team_id, team_name, team_role}`. Один
  join `TeamMembership → Team` на `/auth/me`; N маленькое, но это горячий путь —
  держать одним запросом.

### `AthleteProfileIn` / `AthleteProfileOut`
Добавить `height_cm: int | None`, `weight_kg: Decimal | None` (валидация границ
как в CHECK). `upsert_profile` уже корректно обрабатывает частичный `PUT`
(`exclude_unset`).

### Аватар
- `POST /users/me/avatar` — `multipart/form-data`, поле `file`. Проверки: MIME в
  `{image/jpeg, image/png, image/webp}` (HEIC не принимаем — клиент экспортирует
  JPEG), размер ≤ 5 МБ, картинка декодируется `Pillow`. Обработка: обрезка по
  центру в квадрат, ресайз ≤ 512×512, ре-энкод в WEBP, **вся метадата снимается**
  (пересоздаём изображение из пиксельных данных). Пишет файл, ставит
  `User.avatar_path`, старый файл удаляет, аудит `profile.avatar.set`. Ответ —
  обновлённый `MeOut`.
- `DELETE /users/me/avatar` — удаляет файл, чистит колонку, аудит
  `profile.avatar.clear`. `204`.
- `GET /users/{user_id}/avatar` — авторизованный. Доступ: сам себе, либо
  `is_org_admin` над орг. цели, либо есть общая команда (в любую сторону, любая
  роль — игроку нормально видеть лицо своего тренера). Возвращает `FileResponse`
  (`image/webp`) с `Cache-Control: private, max-age=…`. Нет файла → `404`
  (незаполненный аватар — норма, не ошибка), текст нейтральный.

### `GET /users/athletes/{athlete_id}/profile`
`height_cm` / `weight_kg` включать в ответ **только** если проходит
`ensure_can_view_sensitive(db, viewer, athlete_id, ConsentScope.body_metrics)`;
иначе — `null`. `birthdate`, `position`, `sex`, `baseline_resting_hr` остаются под
обычным `ensure_can_view_athlete` (не спецкатегория). `GET /users/me/profile` —
всегда всё.

Коды ошибок: `400` (не картинка / битый файл / MIME), `413` (превышен размер),
`403` (`ensure_can_view_*`), `404` (нет аватара / профиль не заполнен). Пагинация
не применима.

## Права доступа

`backend/app/core/authz.py`:
- Новая `ensure_can_view_user_avatar(db, viewer, target_id)` — self / org-admin /
  общая команда в любую сторону. Шире, чем `ensure_can_view_athlete` (тот —
  только staff над athlete): аватар видят и игроки друг у друга и у штаба.
- `height_cm` / `weight_kg` — переиспользуем `ensure_can_view_sensitive(scope=
  body_metrics)`. Разведение medic/coach и «нет согласия ≡ нет данных» уже внутри.
- `POST|DELETE /users/me/avatar`, запись роста/веса — только про себя
  (`CurrentUser`), доп. правил нет.
- Медицинская детализация от тренерской: рост/вес — за `body_metrics`, как и
  задумано в CLAUDE.md; тренер без согласия их не видит вообще.

## Аналитика

**Не применимо** — `avatar`, `birthdate`, `sex`, `height_cm`, `weight_kg` в расчёт
`DailyMetric` не входят. Единственное профильное поле, влияющее на Readiness
(`baseline_resting_hr`), не трогаем. Связка «вес ↔ доступная энергия» для RED-S
отложена в этап 3 плана women-health и здесь не делается.

## Персональные и медицинские данные

- Аватар — персональные данные, **не спецкатегория**. Достаточно авторизации,
  `DataConsent` не нужен. EXIF/GPS снимается на загрузке. Аудит `profile.avatar.set`
  / `profile.avatar.clear` (жизненный цикл файла).
- Рост/вес — спецкатегория `body_metrics`. Штабу — только через
  `ensure_can_view_sensitive`. Себе — всегда. Изменение значений не аудируем
  (как и прочие правки профиля/wellness сейчас); аудит sharing уже в
  `consent_service`.
- `birthdate`, `sex` — персональные, не спецкатегория; без гейта согласия. Тренеру
  `birthdate` виден как `position`.
- Не логировать: байты изображения, дату рождения, вес.

## Выкатка

- Миграция вручную `make upgrade` до деплоя.
- `Pillow`, `python-multipart` → `requirements.txt`, пересборка образа бэкенда.
- `backend/media/` на примонтированном volume — иначе аватары не переживут релиз.
- Фича-флага нет. Порядок: бэкенд → клиент. Старый клиент новые поля `MeOut`
  игнорирует; новый клиент против старого бэкенда — эндпоинты аватара `404`,
  обрабатываем мягко.
- Старые данные: все колонки nullable, `sex` уже с дефолтом; существующим
  онбординг-шаг пола не показывается, поле доступно в профиле.

## Риски

- **`not_specified` неоднозначен** (человек отказался vs его не спрашивали). Снято
  тем, что обязателен шаг только для новых, серверного флага и напоминаний нет.
  Если продукт захочет добивать существующих `not_specified` — понадобится колонка
  `onboarding_sex_asked`.
- **Volume под `media/` не примонтирован** → аватары теряются при деплое (как гербы).
- **HEIC с iOS** — `Pillow` без `pillow-heif` не читает. Решение: клиент отдаёт
  JPEG (`expo-image-picker`), бэкенд HEIC отклоняет.
- **Auth-заголовки в `Image` RN** — поддерживаются, но кеширование ведёт себя
  по-разному; возможно, потребуется `expo-image` с `headers`.
- **`AthleteProfile` хранит данные не-атлетов** — косметический долг имени, не
  переименовываем в этом плане.
- **Рост `MeOut` join'ом команд на каждом `/auth/me`** — дёшево, но горячий путь;
  держать одним запросом, не N+1.
