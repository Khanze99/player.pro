## Зачем

Отдельно взятые цикл-трекер и счётчик калорий — посредственные клоны существующих
приложений. Ценность появляется на стыке с ядром AMS: связка «потребление энергии ↔
нагрузка ↔ цикл ↔ Readiness» даёт раннюю диагностику **RED-S** (относительный дефицит
энергии в спорте), чего не даёт ни одно приложение общего назначения.

## Ключевая находка на старте

**В текущей authz нет понятия «согласие».** `ensure_can_view_athlete`
(`backend/app/core/authz.py`) пускает по роли и общей команде, а `is_org_admin`
проходит сквозь все проверки. Для менструальных данных это неприемлемо: админ
организации — это менеджер клуба, он не должен видеть их по умолчанию никогда.

Обе фичи упираются в один общий фундамент, который строится первым.

## Этап 0. Согласие как примитив авторизации

Без этого нельзя писать ни строчки первых двух фич.

### Модель `DataConsent`

Отдельная таблица, а не флаг в профиле:

| поле | смысл |
|---|---|
| `athlete_id` | чьи данные |
| `scope` | `cycle` \| `nutrition` \| `body_metrics` — гранулярно, питание не открывает цикл |
| `audience` | `none` \| `medic` \| `coach` — два уровня, а не булев флаг |
| `granted_at` / `revoked_at` | активное согласие = `revoked_at IS NULL` |
| `policy_version` | версия текста согласия на момент дачи |

Принципы:

- **Отсутствие записи = запрет.** Никакого «по умолчанию включено».
- **Отзыв — не удаление**, а проставление `revoked_at`. История нужна для 152-ФЗ.
- Каждое изменение — в существующий `audit_service`.

### Новая функция авторизации

`ensure_can_view_sensitive(db, viewer, athlete_id, scope)`:

- сам игрок — всегда;
- `medic` — при активном согласии с `audience` = `medic` или `coach`;
- `coach` / `head_coach` — только при `audience = coach`;
- **`admin` — нет.** Сознательное расхождение с обычным `ensure_can_view_athlete`,
  покрыто отдельным тестом.

### 152-ФЗ

Данные о цикле — специальная категория персданных (ст. 10). Нужны: отдельный текст
согласия с версионированием, фиксация факта и времени, отзыв в один тап, данные не
покидают контур. Ложится на уже выбранную self-hosted инфраструктуру без изменений.

### `AthleteProfile.sex`

`female` | `male` | `not_specified`, самодекларация, необязательное. Не «женский
функционал», а входной параметр: цикл-трекинг предлагается при `female`, но никогда
не навязывается.

## Этап 1. Цикл

**Данные.** `CycleLog` (дата, тип события: начало/конец менструации, симптом),
`CycleSettings` (средняя длина цикла, **гормональная контрацепция** — принципиально
меняет картину, поэтому поле обязательное).

**Игроку:** календарь, прогноз следующей менструации, свои симптомы и — главное —
личная корреляция фазы с её собственными Readiness и нагрузкой. У нас уже есть
история метрик на каждого, в трекерах общего назначения такого нет.

**Тренеру (при согласии уровня `coach`):** только фаза и флаг «есть симптомы,
влияющие на тренировку». Детализация — только `medic`. Это тот же принцип
разграничения медицинской и тренерской детали, что уже записан в CLAUDE.md.

**Чего делать не будем.** Никаких автоматических предписаний нагрузки по фазе.
Мета-анализ McNulty et al. (2020) показывает тривиальный усреднённый эффект фазы на
работоспособность при огромном межиндивидуальном разбросе. Строить на этом
рекомендации тренеру — выдавать шум за сигнал.

**Клинически ценное здесь одно:** аменорея (нет менструации 3+ месяца) — красный флаг
RED-S. Идёт `medic`, не тренеру.

## Этап 2. Питание

### База продуктов

FatSecret Platform API **не подходит**: коммерческий, хостится в США, данные о питании
уходят за контур — конфликт со 152-ФЗ и с принципом собственной инфраструктуры из ТЗ.

**Open Food Facts** — открытая база (ODbL), выгружается дампом и поднимается у себя,
содержит российские товары со штрихкодами. Плюс своя таблица для блюд, которых там
нет, и пользовательские рецепты.

### Данные

`FoodItem` (на 100 г: ккал/Б/Ж/У, источник), `FoodLogEntry` (дата, приём пищи,
продукт, граммы), `NutritionTarget` (цели по калориям и БЖУ).

### Ввод

Поиск по названию, сканер штрихкода (`expo-camera` в SDK 57 умеет barcode и входит в
Expo Go — новых нативных зависимостей не появляется), «повторить вчерашний завтрак»,
недавние продукты. Скорость решает всё: 40 секунд, как у опроса, иначе дневник никто
вести не будет.

## Этап 3. Связка — ради чего это нужно AMS

**Energy Availability:**

```
EA = (потреблённая энергия − энергозатраты на тренировку) / тощая масса
```

Энергозатраты оцениваем из того, что уже есть: `session_load`, длительность, тип
события. Потребление даёт дневник. Низкая EA (<30 ккал/кг тощей массы) — основной
механизм RED-S, а RED-S проявляется ровно тем, что уже измеряется: падение Readiness,
нарушения цикла, рост травматизма, просадка перфоманса.

Три фичи замыкаются в один экран для врача: «низкая доступность энергии + аменорея +
падающий Readiness» — ранняя диагностика, а не набор виджетов.

## Риски, заложенные в дизайн

**Расстройства пищевого поведения.** Счётчик калорий в руках спортсменов — известный
фактор риска. Решения: не показывать агрессивный дефицит как цель, не выводить вес и
калории тренеру в детализации (только `medic` и только при согласии), флаги низкой EA
направлять врачу, а не в командный дашборд.

**Согласие под давлением.** Если тренер видит, кто дал согласие, а кто нет —
согласие перестаёт быть добровольным. Тренеру не видно даже наличие или отсутствие
согласия: игрок без согласия выглядит ровно как игрок, у которого нет данных.

## Открытые вопросы

1. **Текст согласия** — нужен юрист по 152-ФЗ. Шаблон предложить можно, проверку он
   не заменяет.
2. **Тощая масса** — для честной EA нужен состав тела (калипер/биоимпеданс). Без него
   только относительный тренд «потребление против затрат», без абсолютного порога 30.
3. **`sex` задним числом** — у существующих игроков поля нет: спрашивать при следующем
   входе или оставить `not_specified` до первого обращения к фиче.
