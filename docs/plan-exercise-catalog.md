# План: справочник упражнений (импорт датасета)

Статус: **этап 1 (модель+миграция+импорт+тест) сделан, 2026-10-10.** Дата составления: 2026-10-10.

Что по факту получилось при реализации:
- Бесплатный MT без ключа (Google Translate через `deep-translator` — мгновенный
  `TooManyRequests` с общего IP песочницы; MyMemory — работает, но путает термины,
  напр. `3/4 sit-up` → «3/4 **приседания**», т.е. squat вместо crunch) на живых
  данных подтвердил риск из раздела «Риски» — решили переводить вручную.
- Вручную переведено **150 из 1324** названий (`scripts/exercise_translations.json`,
  ключ — external_id). Остальные 1174 — `name_ru`/`name_es` = `name_en` как честная
  заглушка, а не угаданный перевод. Доведение до 100% — отдельная фоновая задача,
  не блокирует текущий этап.
- Импорт прогнан на dev-базе: 1324 строки, повторный прогон не плодит дубли
  (идемпотентность подтверждена вручную, не только тестом).

Дополняет ТЗ — раздела про библиотеку упражнений/конструктор тренировок в
`PlayerPro_TZ_final.md` нет, идея обсуждалась отдельно в чате (личный + клубный режим,
сборка тренировки из упражнений). Этот план закрывает только первый, инфраструктурный
шаг — данные; конструктор тренировок, API и экраны — отдельная подготовка поверх этого
фундамента, когда до неё дойдёт очередь.

`docs/functionality.md` фичу не упоминает — её нет вообще, ни модели, ни эндпоинта.
Ближайший по устройству справочник — продукты питания
(`docs/plan-food-catalog.md`, `app/models/nutrition.py::FoodItem`,
`scripts/import_foods.py`) — схема и импорт ниже повторяют его механику.

Решения, принятые в обсуждении 2026-10-09/10:
- Источник — датасет [exercises-dataset](https://github.com/hasaneyldrm/exercises-dataset)
  (MIT на данные/код, медиа — Gym Visual по отдельным условиям, см. «Риски»).
  1324 упражнения, без дублей по `id`, без пропусков в переводах инструкций.
- Схема повторяет `FoodItem`: `source` (`exercises_dataset` / `custom` — второй
  зарезервирован под будущую личную/клубную фичу, сегодня не используется),
  `external_id` = `id` из датасета, частичный уникальный индекс
  `(external_id) WHERE source='exercises_dataset'` → повторный прогон импорта —
  upsert, а не дубли (как `uq_food_items_off_barcode`).
- Поле `category` датасета отбрасываем — проверено на всех 1324 записях, оно во
  100% случаев совпадает с `body_part`; хранить дважды бессмысленно.
- `body_part` → новый закрытый enum `ExerciseBodyPart` (10 значений: `back`,
  `cardio`, `chest`, `lower_arms`, `lower_legs`, `neck`, `shoulders`, `upper_arms`,
  `upper_legs`, `waist`). **Не переиспользуем `BodyRegion`** (карта боли/травмы,
  21 значение) — там анатомическая точка боли, здесь категория для подбора
  упражнения; смешение сломает оба UI и обе формулы, где они участвуют.
- `equipment`, `target`, `muscle_group` → обычный `String`, не enum. 28/19/29
  уникальных значений с длинным хвостом из единичных вхождений
  (`"elliptical machine"`, `"stepmill machine"`) — фильтр по ним пока не строим,
  закрывать enum'ом сейчас преждевременно; вернуться к этому на этапе UI библиотеки.
- `secondary_muscles` (у всех записей непустой список) → `ARRAY(String)`. Первое
  использование Postgres `ARRAY` в проекте — осознанно: альтернатива (строка через
  запятую) хуже без выгоды, а парсить её обратно на каждый запрос дороже.
- Имена (`name`) в датасете только на английском; `instructions`/`instruction_steps`
  — на 10 языках, включая ru/en/es, без пропусков у всех 1324 записей. Решение:
  `name_ru`/`name_es` получаем машинным переводом `name_en` сразу при импорте, без
  ревью носителем — риск терминологии зафиксирован в «Риски».
- Инструкции храним в двух видах на каждый из 3 языков: цельный текст
  (`instructions_<lang>: Text`) и пошаговый список (`steps_<lang>: ARRAY(Text)`) —
  у датасета оба поля готовы, собственная логика разбивки не нужна, а пошаговый
  список пригодится будущему экрану тренировки.
- Картинка/GIF: храним только путь (`image_path`, `gif_path` — относительные пути
  из датасета вида `images/0001-2gPfomN.jpg`) и текст атрибуции. **Сами файлы не
  копируем и не раздаём на этом шаге** — хостинг медиа и экран, где это увидит
  пользователь, требуют отдельного решения по атрибуции Gym Visual (см. «Риски»).
  Колонки готовы принять путь, когда решение будет принято.
- Импортируем все 1324 записи без фильтрации — в отличие от Open Food Facts здесь
  нет проблемы мусорных дублей и пустых карточек, курировать нечего.
- `created_by` (nullable FK → `users`) заводим сейчас по аналогии с
  `FoodItem.created_by`, хотя сегодня всегда NULL — чтобы не делать вторую миграцию,
  когда дойдём до личных/клубных упражнений.

## Зачем

Фундамент для будущего конструктора тренировок (личный и клубный режим — обсуждалось
отдельно, в этот план не входит). Сегодняшняя задача — только данные: таблица,
миграция, одноразовый идемпотентный импорт 1324 упражнений с переводом на ru/en/es.

## Что уже есть

Ничего. Ни модели `Exercise`, ни упоминания в `docs/functionality.md`. Повторяем
устройство справочника продуктов — он прошёл тот же путь (внешний датасет → таблица →
скрипт-импортёр → `make <цель>`), см. `docs/plan-food-catalog.md`.

## Данные и миграции

Таблица `exercises`:

| Колонка | Тип | Примечание |
|---|---|---|
| `id` | UUID, pk | |
| `source` | `ExerciseSource` | `exercises_dataset` \| `custom`; default `exercises_dataset` |
| `external_id` | `String(16)`, nullable | id из датасета, напр. `"0001"` |
| `name_en` / `name_ru` / `name_es` | `String(255)` | en — оригинал, ru/es — MT |
| `body_part` | `ExerciseBodyPart` | новый enum, 10 значений |
| `equipment` | `String(64)` | |
| `target` | `String(64)` | основная целевая мышца |
| `muscle_group` | `String(64)` | |
| `secondary_muscles` | `ARRAY(String)` | |
| `instructions_en` / `_ru` / `_es` | `Text` | цельный текст |
| `steps_en` / `_ru` / `_es` | `ARRAY(Text)` | пошаговый список |
| `image_path` | `String(255)`, nullable | относительный путь из датасета |
| `gif_path` | `String(255)`, nullable | |
| `attribution` | `String(255)`, nullable | `"© Gym visual — https://gymvisual.com/"` |
| `created_by` | UUID, nullable, FK `users` | NULL у сидовых записей |
| `created_at` | `DateTime(timezone=True)` | |

Индексы:
- `Index("ix_exercises_body_part", "body_part")` — под будущий фильтр библиотеки.
- Частичный уникальный `(external_id) WHERE source='exercises_dataset'` — идемпотентный
  реимпорт, механика как у `uq_food_items_off_barcode`.

Новые enum'ы в `app/models/enums.py`: `ExerciseSource` (`exercises_dataset`, `custom`),
`ExerciseBodyPart` (10 значений выше).

Миграция — только `make migration m="exercises catalog"` с ревью файла перед
`make upgrade`. Откат (`make downgrade`) — чистый `drop table`, данных не жалко: таблица
полностью воссоздаётся повторным импортом.

## Импорт

`backend/scripts/import_exercises.py`, по устройству аналогичен `import_foods.py`:

- Источник — `data/exercises.json` датасета, путь передаётся аргументом (`--file`), в
  репозиторий не кладём (17 МБ, как и дамп OFF).
- `name_ru`/`name_es` — машинный перевод `name_en` на этапе импорта (конкретный
  провайдер MT — деталь реализации, не блокирует план).
- Upsert по `external_id` батчами, дедуп внутри батча перед отправкой — то же, что
  `_flush()` в `import_foods.py`.
- Новая цель `make exercises file=...` в `backend/Makefile`.

## API / Мобильный клиент / Права доступа

Изначально этот шаг не планировал эндпоинтов. По факту добавлен один узкий кусок —
раздача медиа (лицензия на Gym Visual подтверждена пользователем напрямую,
2026-10-11): `GET /exercises/{id}/image`, `GET /exercises/{id}/gif`
(`app/api/v1/exercises.py`, `app/services/exercise_service.py`). За `require_consented`,
как все приватные ресурсы — не из-за чувствительности данных (контент одинаковый для
всех), а чтобы не открывать лишнюю публичную поверхность без причины. Файл отдаётся
через свой эндпоинт, а не голой статикой (`/static`), чтобы при смене хранилища
(CDN/объектное хранилище) URL для клиента не менялись.

Атрибуция Gym Visual эндпоинтом не закрывается — он отдаёт байты файла, а не
интерфейс; текст атрибуции в UI нужно показать там, где картинка/GIF реально
отрендерены, а экрана с этим пока нет.

Контракт библиотеки упражнений (список/поиск/фильтр), личные/клубные упражнения и
конструктор тренировки — всё ещё отдельная `/preparing` поверх этого фундамента.

## Риски

- **Атрибуция Gym Visual.** Медиа в датасете идёт по условиям «180×180 + атрибуция —
  бесплатно, остальное — платно у gymvisual.com». Сегодня файлы не копируются и не
  показываются — риска нет. Как только появится эндпоинт/экран, отдающий
  `image_path`/`gif_path` конечному пользователю: (а) свериться с условиями
  gymvisual.com напрямую — сам датасет прямо пишет «клонирование репозитория не даёт
  лицензии», (б) показать атрибуцию в UI. Блокирует не этот шаг, а следующий.
- **Машинный перевод названий без ревью.** 1324 имени переведены MT без вычитки
  носителем — спортивная терминология может разойтись с привычной в РФ. Не блокирует
  импорт, но вычитку нужно запланировать до того, как это увидит тренер или врач.
- **`ExerciseBodyPart` vs `BodyRegion` — спутать легко**, у обеих 1–2 общих слова
  (`chest`, `shoulders` vs `shoulder`). Разнести явным комментарием в `enums.py`, как
  уже сделано у `BodyRegion`.

## Медиа: скачивание, не git (решено 2026-10-13)

137 МБ картинок/GIF (2648 файлов) в git не кладём — та же логика, что с
`exercises.json` (раздел выше), только втрое крупнее: бинарники не диффятся,
каждый реимпорт датасета добавлял бы в историю ещё одну полную копию. Git LFS
рассматривали — на машинах разработчиков не установлен, это новая инфраструктура
в проекте под разовую задачу. Решение: `make exercises-media` качает тот же
tarball с GitHub и раскладывает `images/`/`videos/` в `backend/media/exercises`
(`.gitignore` уже накрывает `backend/media/`); идемпотентно — повторный запуск
ничего не перекачивает, если каталог уже заполнен.

Лицензия на само медиа (Gym Visual) подтверждена пользователем напрямую с
правообладателем 2026-10-11 — не только условиями редистрибуции датасета.

## Открытые вопросы

1. Кто и когда делает ручную вычитку MT-переводов названий — до показа в UI или
   после, по жалобам пользователей.
2. Раздача медиа есть (`GET /exercises/{id}/image`/`.../gif`), но ни один экран
   это не показывает — атрибуция Gym Visual в интерфейсе появится вместе с ним.
3. Дамп `exercises.json` в репозиторий не кладём (аналог OFF-дампа) — подтвердить,
   что это ок и файл просто передаётся вручную аргументом `make exercises file=...`.
