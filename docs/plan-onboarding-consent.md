Статус: **реализовано, шаги 1–7 пройдены.** Дата составления: 2026-09-03, дата завершения: 2026-09-03.

Итог ревью (шаг 7, code-reviewer): архитектура и слои соблюдены, 213/213 тестов зелёных,
security-auditor находок не оставил. Найдена и закрыта одна существенная проблема —
см. «Закрытая находка» ниже. Также убран неиспользуемый алиас `CurrentUserConsented`
из `app/api/deps.py` (гейт и так работает через `dependencies=[Depends(require_consented)]`
на уровне роутера — алиас был мёртвым кодом).

### Закрытая находка: PIN-вход обходил гейт на клиенте

Обнаружено ревью: раздел «Выкатка» ниже обещает, что у существующих пользователей при
первом запросе после релиза `require_consented` вернёт 403 и клиент выведет на экран
`consent`. Это работало только для входа через OTP (`routeOnboarding()` в
`mobile/src/app/_layout.tsx`). Но пользователь, уже поставивший PIN на устройстве
(весь текущий пул), входит через `mobile/src/app/(auth)/pin.tsx`, который после
верного PIN сразу ставил `status: 'active'`, минуя проверку согласий — первый же запрос
к любому гейченному эндпоинту падал 403 без обработки на клиенте (тихая пустая загрузка).

Исправлено: `pin.tsx` после успешного обмена refresh→access дополнительно запрашивает
`/auth/me`; если `terms_accepted`/`health_consent_accepted` не оба `true` — ведёт на
`/(auth)/consent?next=active` (без смены `session.status`, чтобы не столкнуться с
параллельным редиректом `AuthGate`). `consent.tsx` после успешного гранта, если пришёл с
`next=active`, сам ставит `session.status = 'active'` — обычный путь онбординга
(`profile-setup`) не трогается. При недоступной сети — тот же permissive-дефолт, что и в
`routeOnboarding()`: не блокируем вход локально, сервер всё равно защищён.

Дополняет `PlayerPro_TZ_final.md` — в самом ТЗ раздела про юридический гейт согласий нет
вообще (проверено: ни «согласи», ни «152-ФЗ», ни «consent» в тексте ТЗ не встречаются).

Отношение к существующему коду: в проекте уже есть `DataConsent` /
`consent_service.py` / `mobile/src/app/privacy.tsx` (docs/plan-women-health-nutrition.md,
этап 0) — но это **другой примитив**: гранулярное разрешение игрока показать
тренеру/врачу цикл/питание/метрики (`scope` × `audience: none|medic|coach`,
отзываемо в любой момент). Фича этого плана — бинарный гейт «принял/не принял» при
регистрации, без которого пользователь не может пользоваться приложением вообще.
Смешивать их в одной таблице нельзя: audience-лестница не имеет смысла для «принял ToS».

Решения, принятые в обсуждении 2026-09-03:
- Чекбокс 2 (данные о здоровье) показывается **всем без исключения** при регистрации,
  а не только будущим `athlete` — роль на этом шаге ещё не выбрана (`org-choice` идёт
  позже), клиент единый для всех ролей.
- Тексты Пользовательского соглашения и Политики конфиденциальности пишу я как
  **черновик**, помечаю явно как требующий проверки юристом перед публикацией —
  не финальный юридический документ.
- Серверная защита обязательна: гейт не только на экране, но и в API — иначе
  обходится прямым вызовом эндпоинтов, минуя мобильный клиент.
- Согласие законного представителя за несовершеннолетних — **отложено**, зафиксировано
  ниже как открытый риск, эта фича его не закрывает.

## Зачем

152-ФЗ ст. 9 требует явного согласия на обработку персональных данных, ст. 10 —
**отдельного** явного согласия на обработку специальных категорий (данные о здоровье:
wellness, RPE, травмы, боль). Сейчас в приложении данные собираются без какого-либо
согласия — юридическая дыра, закрывающая которую нельзя откладывать: она не про UX,
а про законность самого сбора данных, которые уже пишутся в БД.

## Что уже есть

- `DataConsent` / `consent_service.py` / `/consents/me` — сравнение см. выше, не трогаем.
- `settings.consent_policy_version` — версия текста **только** для `DataConsent`,
  для новой фичи нужны свои версии (см. «Данные»).
- Онбординг-роутинг в `mobile/src/app/_layout.tsx` (`routeOnboarding`): после верификации
  OTP решает, вести ли на `profile-setup` или сразу на `pin-setup`, читая `GET /auth/me`.
- `get_current_user` (`backend/app/api/deps.py`) уже отсекает `status != active`, но
  ничего не знает о завершённости онбординга — активный, но не давший согласий
  пользователь сегодня может дёргать любой эндпоинт.
- Юридических текстов (Пользовательское соглашение, Политика конфиденциальности) нет
  нигде в репозитории — прямо отмечено как незакрытая задача в комментарии
  `app/config.py` рядом с `feature_cycle_enabled`.

## Данные и миграции

Новая таблица `policy_consents`, структура — по образцу `DataConsent` (immutable
история, `revoked_at` вместо удаления), но без `audience`:

| поле | смысл |
|---|---|
| `id` | PK |
| `user_id` | FK → `users.id` |
| `kind` | `terms` \| `health_data` — новый enum `PolicyConsentKind`, отдельно от `ConsentScope` |
| `policy_version` | версия текста на момент дачи согласия |
| `granted_at` / `revoked_at` | активное согласие = `revoked_at IS NULL` |

Индексы: `(user_id, kind)`, `(user_id, kind, revoked_at)` — как у `DataConsent`.

Новые настройки в `app/config.py`:
- `terms_policy_version: str` — версия Пользовательского соглашения + Политики
  конфиденциальности (чекбокс 1, ст. 9).
- `health_consent_policy_version: str` — версия текста согласия на спецкатегорию
  (чекбокс 2, ст. 10). Отдельно от `consent_policy_version` (тот — про `DataConsent`,
  семантически другая фича, нельзя схлопывать: смена текста ToS не должна переспрашивать
  согласие на sharing цикла, и наоборот).

`GET /auth/me` (`MeOut`) — добавить `terms_accepted: bool`, `health_consent_accepted: bool`
(признак «есть активное согласие текущей версии»), чтобы клиент решал маршрут онбординга
за один существующий запрос, без лишнего похода в `/consents/policy`.

Миграция — `make migration m="onboarding_consent_gate"` (autogenerate), ревью, `make upgrade`.

## API

Новый модуль `backend/app/schemas/policy_consent.py` + сервис
`backend/app/services/policy_consent_service.py` (grant/revoke/get_active/status —
по образцу `consent_service.py`, каждое изменение — в `audit_service`, как у
`DataConsent`). Роуты — в существующем `backend/app/api/v1/consent.py`, домен один
(«согласия»), только новые пути:

```
GET  /api/v1/consents/policy      → {terms: {granted, policy_version, granted_at},
                                      health_data: {...}}
PUT  /api/v1/consents/policy      body: {kind: terms|health_data, granted: bool}
                                   → статус обоих kind после изменения
```

`granted: false` — отзыв (симметрично существующему `audience: none` в
`ConsentSetIn`). Отзыв `terms` или `health_data` не удаляет аккаунт, но переводит
пользователя обратно за серверный гейт (см. «Права доступа») — данные не удаляются,
это отдельный процесс (право на удаление, вне объёма этой фичи).

Тексты соглашений отдаю как статический контент мобильного клиента (см. «Мобильный
клиент»), backend их не хранит и не отдаёт — только версию.

## Права доступа

`get_current_user` не трогаем (единственная ответственность — валидный токен + активный
статус). Добавляется отдельная зависимость `require_consented` в `app/api/deps.py`:

```python
async def require_consented(user: CurrentUser, db: DbSession) -> User:
    if not await policy_consent_service.has_all(db, user.id):
        raise HTTPException(403, "Требуется согласие на обработку персональных данных")
    return user

CurrentUserConsented = Annotated[User, Depends(require_consented)]
```

Применяется через `dependencies=[Depends(require_consented)]` в `router.include_router(...)`
(`backend/app/api/v1/router.py`) на все роутеры **кроме** `auth` и `consent` (там же лежит
и новый `/consents/policy` — иначе он сам себя блокирует). Список исключений короткий
и явный — тест на authz проверяет, что новый роутер, добавленный без пометки, не
проскочит негейченным (итерация по `router.routes`, см. «Тесты»).

## Мобильный клиент

Новый экран `mobile/src/app/(auth)/consent.tsx` — два независимых чекбокса (нельзя нажать
«Продолжить», пока не отмечены оба), тексты — по формулировке из задачи:

1. «Я принимаю [Пользовательское соглашение] и даю согласие на обработку моих
   персональных данных в соответствии с [Политикой конфиденциальности]»
2. «Я даю согласие на обработку данных о моём самочувствии, физической нагрузке и
   готовности (специальная категория персональных данных) в целях предоставления
   функций приложения»

Ссылки в квадратных скобках — переходы на статические экраны
`mobile/src/app/terms.tsx` и `mobile/src/app/privacy-policy.tsx` с текстом-черновиком
(готовлю его, помечаю заголовком «Черновик — требует проверки юристом перед
публикацией»; уже существующий `privacy.tsx` — это экран управления
audience-согласиями, не трогаем и не путаем название).

Место в потоке: `welcome → otp → consent → profile-setup → org-choice/pin-setup`
(до имени — соглашаться должен раньше, чем что-либо вводить). `routeOnboarding()` в
`_layout.tsx` получает третье состояние поверх текущих двух:

```
если новый пользователь:
  нет terms_accepted || нет health_consent_accepted → /(auth)/consent
  иначе нет ФИО                                     → /(auth)/profile-setup
  иначе                                              → /(auth)/pin-setup
```

Экран доступен и приглашённым (админ мог задать ФИО заранее) — согласие даёт только
сам человек, за него это сделать нельзя, даже если профиль уже заполнен админом.

Локализация: `ru.ts`/`en.ts`/`es.ts` — тексты чекбоксов и заголовков экранов терминов/
политики (сам юридический текст — только на `ru`, версия для `en`/`es` — вне объёма,
открытый вопрос ниже).

## Персональные и медицинские данные

- Каждый grant/revoke — в `audit_service`, как у `DataConsent`.
- В `policy_consents` не хранится ничего сверх факта согласия — не текст, не IP,
  не устройство (можно добавить `granted_from_ip`/`user_agent` при необходимости —
  сейчас не запрашивалось, отмечаю как открытый вопрос).

## Выкатка

Фича-флага не ставлю: это юридический гейт, а не экспериментальная функция — включать
частично для части пользователей означает часть пользователей обрабатывать без согласия,
что хуже, чем не делать фичу вообще. Обратная совместимость: пользователи, уже прошедшие
онбординг до релиза (`status=active`, старее записей `policy_consents` нет), при первом
после обновления запросе `require_consented` получат 403 и будут выведены на экран
`consent` — то есть существующим пользователям тоже придётся один раз явно согласиться.
Это ожидаемо и обязательно (иначе их данные так и остаются без согласия), но стоит
предупредить сразу: у всей текущей базы пользователей при выкатке будет разовый экран
согласия при следующем входе.

## Риски

- **Обход через прямой вызов API до полного релиза мобильного клиента** — закрыт
  серверным гейтом (шаг 3), не зависит от UI.
- **Массовый повторный онбординг существующих пользователей** при выкатке (см.
  «Выкатка») — ожидаемо, но продукту стоит знать заранее, чтобы не читать как баг.
- **Забытый роутер без гейта в будущем** — закрыт регресс-тестом (шаг 5), а не
  дисциплиной разработчика.
