# План: санитизация email-идентификатора при приглашении/входе

Статус: **проектирование, код не начат.** Дата составления: 2026-10-23.

Багфикс, не фича из ТЗ. Раздел ТЗ 2.3/3.4 описывает сам механизм приглашения
по телефону/почте; эта правка не меняет контракт и не дополняет ТЗ — закрывает дефект
нормализации входного значения. В `docs/functionality.md` инвайты отдельно не описаны.

Решения, принятые в обсуждении 2026-10-23:
- Чиним в одном месте — `normalize_identifier()` в `backend/app/services/auth_service.py:32`.
  Это общая функция и для OTP-входа (`request_otp`/`verify_otp`), и для приглашений
  (`invitations_service.create_invite` вызывает её же). Фикс там закрывает проблему
  сразу в обоих потоках, без дублирования логики на мобильном клиенте.
- Санитизация на мобильном клиенте (`invite.tsx`) не нужна: `identifier.trim()` достаточно
  для UX, реальная нормализация и валидация — backend-ответственность (как и для телефона).
- Объём мусора, который чистим: `mailto:` префикс (включая `?subject=...&body=...` хвост
  mailto-ссылки) и обёртка в угловые скобки `<email>`. Формат `"Имя <email>"` — вне объёма,
  это другой кейс копирования (контакт, не ссылка), не просили.

## Зачем

Админ/тренер приглашает человека, вставляя почту в поле инвайта. Если скопировать
не отображаемый текст письма, а саму `mailto:`-ссылку (или адрес обёрнутый в `<...>`),
в поле попадает `mailto:ivan@example.com` или `<mailto:ivan@example.com>`. Текущий
`_EMAIL_RE` это пропускает как «валидный email» (двоеточие перед `@` не запрещено regex'ом),
поэтому в `Invitation.identifier` сохраняется буквально `mailto:ivan@example.com`.
Когда приглашённый входит обычным OTP со своей настоящей почтой `ivan@example.com`,
`consume_for_user` ищет совпадение по точному значению и не находит — инвайт не применяется,
роль не выставляется.

## Что уже есть

- `normalize_identifier()` (`auth_service.py:32`): `strip().lower()`, матчит `_EMAIL_RE`
  либо, после чистки пробелов/дефисов/скобок, `_PHONE_RE`. Для телефона мусор уже чистится
  (`re.sub(r"[\s\-()]", "", value)`), для почты — нет.
- Используется в трёх местах: `request_otp`, `verify_otp` (оба в `auth_service.py`),
  `create_invite` (`invitations_service.py:51`).
- Мобильный `invite.tsx`: поле `identifier` без собственной валидации формата, только
  `trim()` и проверка длины ≥3 для кнопки отправки.

## Правка

В `normalize_identifier`, перед проверкой на email/phone — если `value` начинается с
`mailto:` (case-insensitive, после strip), отрезать префикс и всё после `?` (query
mailto-ссылки), затем снять обёртку в `<` `>` если есть. После этого — тот же путь
проверки `_EMAIL_RE`/`_PHONE_RE`, что и сейчас.

Эффект: и `request_otp`/`verify_otp` (вход по ссылке из письма — тот же баг на входе,
не только в инвайте), и `create_invite` получают одинаково чистый `ivan@example.com`.

## Контракт

Не меняется. `POST /organizations/{id}/invitations` и `/auth/otp/request` принимают тот же
`identifier: str`, просто шире нормализуют значение до валидации. Коды ошибок те же (422
на нераспознанный identifier).

## Права доступа

Не применимо — правило доступа к созданию инвайта не меняется, правится только
нормализация значения внутри уже существующей проверки.

## Мобильный клиент

Не применимо — фикс полностью на backend, мобильный экран инвайта не трогаем.

## Персональные и медицинские данные

Не применимо — добавочной обработки медицинских/персональных данных не вводит,

## Выкатка

Без фича-флага: чистый багфикс обратной совместимости, старые pending-инвайты с уже
сохранённым «грязным» `identifier` (`mailto:...`) новым кодом сами себя не починят —
по решению не трогаем существующие записи (их мало, это первый репортнутый кейс);
если встретятся проблемные старые инвайты — почистить вручную через SQL при необходимости.

## Тесты

- `normalize_identifier("mailto:Ivan@Example.com")` → `("email", "ivan@example.com")`.
- `normalize_identifier("<mailto:ivan@example.com>")` → то же.
- `normalize_identifier("mailto:ivan@example.com?subject=Hi")` → то же.
- Регрессия: обычный `"ivan@example.com"` и телефон продолжают работать как раньше.
- Интеграционный: создать инвайт с `mailto:`-мусором → пользователь логинится реальной
  почтой → инвайт консюмится (`test_invites.py`).
